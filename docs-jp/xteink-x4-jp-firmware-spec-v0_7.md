## 1. 背景と目的

### 1.1 経緯

AliExpress 等の国際流通品として販売される Xteink X4 の一部は、工場出荷時に
**USBフラッシュ書き込みが無効化 (ロック)** されている。日本語圏には、このロック品に
カスタムファームウェアを導入し、さらに日本語UI化まで到達した記録が存在しない。

2026-08-09、上流への日本語翻訳 PR (#2940) が**方針上の理由でクローズ**された。
翻訳の品質ではなく、CJK 字形が同梱フォントに含まれないことが理由である (§8.2)。
これを受け、**独立したフォークとして日本語版を公開する**方針に転換した。

### 1.2 目的

1. スマートフォンで作成したメモ / TODO (Markdown) を X4 上で快適に閲覧する
2. Markdown のチェックボックスを端末上でトグルできるようにする
3. **UI を日本語化する** ← v0.2 時点で達成
4. **フォントを別途用意しなくても日本語で使える状態で配布する** ← v0.5 で追加
5. 上記を **SDカード経由で導入可能なファームウェア** として公開する

### 1.3 非目的 (スコープ外)

- USBフラッシュロックそのものの解除 (技術的に不可能、かつ不要)
- PDF のネイティブレンダリング
- Bluetooth 機能の復活
- **上流へのマージを前提とした設計上の妥協** ← v0.5 で追加

## 3. 上流フォントの字形収録範囲 — **v0.5 の中核的発見**

**PR #2940 がクローズされた技術的根拠であり、フォーク設計の出発点。**

### 3.1 組み込みフォントの intervals

`scripts/fontconvert.py:43-89` で定義される範囲:

ASCII / Latin-1 / Latin Extended-A / Latin Extended-B (ベトナム語・欧州サブセット) /
ベトナム語拡張 / 一般句読点 / 結合分音記号 / **キリル 0x0400-0x04FF** / 数学記号

ギリシャ (0x0370-0x03FF) は L80 で**コメントアウト**されている。

### 3.2 フォント別の収録状況 (実測)

ヘブライ・アラビアは intervals ではなく `--additional-intervals` により
フォントスタックに合成されている (`convert-builtin-fonts.sh:42-83`)。

| フォント | 用途 | キリル | ヘブライ | アラビア | CJK |
|---|---|---|---|---|---|
| `ubuntu_10` / `ubuntu_12` (regular+bold) | **UI** | ✅ | ✅ | ✅ | ❌ |
| `notosans_8_regular` | **UI** | ✅ | ✅ | ✅ | ❌ |
| `notoserif` / `notosans` 12-18 | **本文** | ✅ | ❌ | ❌ | ❌ |

### 3.3 この事実が意味すること

**上流の言語受け入れ基準は「非ラテンか否か」ではなく「UIフォントに字形があるか」。**

ヘブライ語 (#2068) とアラビア語 (#2599) の UI 翻訳が受け入れられたのは、
UI フォントに字形が同梱されているため。キリル4言語 (RU/UK/BE/KK) も同様。
**CJK だけが一切含まれない。**

`cjk` / `hangul` は SD カードフォントのプリセット (`fontconvert_sdcard.py:54-56`)
にのみ存在する。

**メンテナの判断は一貫しており、恣意的な扱いではない。**この線引きを技術的に
覆すことはできない。したがって**フォーク側で UI 用字形を自前で用意する**のが
唯一の解となる (§4.1)。

## 4. フォーク設計

### 4.1 フォントアーキテクチャ — **UI固定 / 本文可変**

**設計の中核。上流がクローズした理由をそのまま解決する構造。**

| 用途 | フォント | 配置 | 理由 |
|---|---|---|---|
| **UI 文字列** | 日本語サブセットを**焼き込み** | Flash | フォント未設定でも日本語UIが成立する。「読めないUIから抜け出せない」事故が原理的に起きない |
| **本文** | ユーザーが選ぶ SD フォント | SDカード | 好みの書体で読めるべき。明朝/ゴシックの選択は読書体験の核心 |
| **ファイル名・書名** | **本文フォント**を使用 | SDカード | 何の文字が入るか事前に определ できないため、サブセットでは足りない |

#### 解決される問題

| v0.4 までの制約 | v0.5 での解決 |
|---|---|
| 12pt が UI と本文Small で共有され、片方だけ最適化できない | **UI と本文が完全に分離**。相互干渉が消える |
| SDフォントに 8/10/12pt が無いと UI が □ になる | **UI は Flash 上のフォントで描画**。SD の状態に依存しない |
| UI用に軽量化すると書名・ファイル名が表示できない | **ファイル名は本文フォント経由**。フル字形が使える |
| 日本語UIにフォント準備が必須 | **不要**。焼き込み済み |

#### 容量計画

必要文字数 = japanese.yaml に出現する文字 + 動的生成される文字。

**動的生成される文字を忘れないこと。**翻訳ファイルに現れないが UI フォントで
描画される:

- `%s` `%d` `%zu` `%u` `%.2f%%` に埋まる値 (数字、記号)
- 日付・時刻表示
- バッテリー残量、ページ番号
- 単位記号 (%, MB, KB)
- エラーコード

**ASCII 95文字は全て含める。**3サイズ2種でも数十KB程度であり、削る意味がない。

概算: 1文字あたり 150〜200 B (8/10/12pt × regular/bold 合計) と仮定すると、
1,000字で 150〜200 KB、3,000字で 450〜600 KB。**残 Flash 911 KB に対し、
1,000字前後なら余裕、3,000字でも収まる見込み。**(要実測)

#### 容量の捻出

**31言語分の翻訳文字列を削除する** (§4.2)。加えて `--strip-unused` が
未使用キーを除去するため、実際の削減量は yaml のサイズより大きい可能性がある。

### 4.2 対応言語の削減

## 5. 書き込み・復旧手順 (確立済み)

### 5.1 ⚠️ ロック品における書き込み経路の要点

**本プロジェクト最大の知見。**

| 経路 | 1.4系→1.4系 | 1.4系→1.5系 | 備考 |
|---|---|---|---|
| ファイルブラウザから `.bin` 直接実行 | ○ | — | 1.4.1 で成功実績あり |
| Settings > SD Card Firmware Update | ○ | **× Invalid firmware file** | 公式RC3でも同様に失敗 |
| **Escape Hatch > Flash Firmware** | ○ | **○** | **唯一の突破口** |
| 電源+上ボタン (OEMブートローダー) | × | × | ストック時のみ有効 |
| USB Web Flasher | × | × | ロックのため不可 |

> **1.4.1 の SD更新機能は 1.5系イメージを受け付けない。**
> 自作ビルド・公式RC3 の双方で「Invalid firmware file」を再現。
> ファイルサイズは PC 上の原本と 1 バイト単位で一致 (5,495,888 B)。
>
> **解決策**: Debug ページから **Escape Hatch (recovery, 0.4 MB)** を取得し、
> 通常の SD 更新でこれを書き込む。起動後のメニューから `Flash Firmware` を選び、
> SD 上の `.bin` を指定すれば 1.5系が書き込める。
> 一度 1.5 系に上がれば、以降は通常の SD Card Firmware Update が使える。

### 5.2 標準的な書き込み手順 (1.5系運用時)

1. `.pio\build\default\firmware.bin` を **`update.bin`** にリネーム
2. SDカードの**ルート**に配置
3. 端末で 設定 > システム > SDカードファームウェア更新 を実行

### 5.3 復旧経路の確保 (必須)

| ファイル | 用途 |
|---|---|
| `escape-hatch.bin` | **緊急脱出・世代跨ぎの書き込み** |
| `crosspoint_1.4.1_update.bin` | 安定版への復帰 |
| `crosspoint_1.5rc3_update.bin` | 公式1.5系への復帰 |
| `stock_english_update.bin` | 純正 (英語) への復帰 |
| `stock_chinese_v6.2.4_update.bin` | 純正 (中国語 / 出荷時) への復帰 |

> **運用ルール**: SDカードのルートに `update.bin` を**常設しない**。
> 書き込み時のみリネームして配置する。誤爆防止のため。

### 5.4 既知の障害と対処

| 現象 | 原因 | 対処 |
|---|---|---|
| Invalid firmware file | 1.4系が1.5系イメージを拒否 | **Escape Hatch を使用** |
| Escape Hatch で "No .bin files" | SDカード未挿入 / 認識前 | 挿入して**再起動** |
| SD更新で "Error 9" | 既知の未解決バグ | **文鎮化ではない**。再起動して再試行 |
| 1.2.0 系で OTA が常に失敗 | RAM不足による TLS+書き込みの競合 | **1.2.0ベースを導入しない** |
| SDカードのフォーマット不能 | 書き込み過多による物理故障 | カード交換。**MLC 推奨** |
| **develop 移行後に初回起動が遅い** | **キャッシュ形式の更新 (book.bin 8→10 / section.bin 32→37) による全再生成** | **正常。データ損失ではない** |

### 6.2 【F-2】Markdown チェックボックス トグル — ✅ 完了 (2026-08-13)

> **詳細は `docs-jp/f2-markdown-checkbox.md` v0.2 を参照。**

`.md` 内の `- [ ]` を端末上で `- [x]` にする。電源ボタン短押しでトグル、
側面ボタンでチェックボックス間を移動。SD 上のファイルに1バイトだけ書き戻す。

**上流ではスコープ外が確定している** (SCOPE.md の「No typed notes, journals, or editors」、
ROADMAP の「Writing / authoring tools」)。フォークで実装した。

| 項目 | 実測 |
|---|---|
| Flash | +2,142 B (5,593,069 B / 85.3%) |
| RAM (静的) | ±0 |
| 体感 | ページ送りと同程度。引っかかりなし |

#### アーキテクチャ上の重要事実

TXT / EPUB / XTC は完全に別クラス。共通基底 `ReaderActivity` は入口の振り分けのみ。
**実装先は `TxtReaderActivity`。**TXT が視覚行1本につき `drawText` 1回の
行単位描画であることが本機能にとって有利に働いた。

#### 中核となる設計上の性質

`- [ ]` と `- [x]` は**ファイル長が変わらない。**差分は角括弧内の1バイトのみ。
したがってバイトオフセットも `pageOffsets` キャッシュも無効化されない。
ファイル全体を RAM に載せる必要もない。

#### 描画コスト (実測に基づく訂正)

TXT 1ページの描画は定常状態で 1591ms。**トグル時の下限は約 870ms。**

- E-Ink パネル転送 548ms は物理時間で削れない
- `txt_prewarm` 269ms も省略できない。`renderPage()` の描画スコープの
  destructor がフォントキャッシュを破棄するため、飛ばすと全グリフがミスする

**v0.5 まで記載していた「1591ms → 100ms 程度」は誤りである。**

グレースケールの部分更新は API レベルで不可能 (`displayGrayBuffer` に窓指定版が無い)。
BW の窓更新 (`FreeInkDisplay::displayWindow`) は SDK に実装があるが EXPERIMENTAL 扱いで、
`GfxRenderer.h:181` の宣言はコメントアウトされたまま。
**配線と罠は `docs-jp/f2-deferred-partial-update.md` に調査済みで保留。**

#### 実装上の罠 (再発防止)

次に TXT リーダーの折り返しや入力に触るとき、以下は必ず踏む。

1. `ReaderUtils::detectPageTurn` は `longPressButtonBehavior == OFF` (既定) のとき
   **`wasPressed` で発火する。**`wasReleased` と混ぜると入力が届かない
2. `render()` 内でカーソル状態を無条件に初期化すると、`requestUpdate()` で自分を打ち消す
3. **折り返しに影響する変更を入れたら `CACHE_VERSION` を上げる。**
   検証項目にビューポートはあるが折り返しアルゴリズムを表すものが無く、
   古い `pageOffsets` が黙って再利用される
4. `buildPageIndex()` と `render()` は**同じ折り返しをしなければならない**

**第1段階 (推奨)**: トグル時は `loadPageAtOffset` を呼ばず、
`currentPageLines[i]` の文字列だけ書き換えて `renderPage()`。**AAパスは省略。**
グレースケールの部分更新は API レベルで不可能
(`displayGrayBuffer` に窓指定版が無い)。**見込み: 1591ms → 100ms 程度**

**第2段階 (任意)**: `HalDisplay::displayWindow` と
`GfxRenderer::displayWindow` を配線。SDK に `FreeInkDisplay::displayWindow`
実装済み (**EXPERIMENTAL**)。`GfxRenderer.h:169` にコメントアウトされた宣言あり。
`screenRectToAlignedMemRect()` (8px整列) も既存。残像の実機検証が必須。

### 6.3 【F-3】TXT の文字コード自動判別 (Shift-JIS) — ✅ 完了 (2026-08-13)

**現象**: Shift-JIS の `.txt` が `◆?` と半角英字の交互で文字化けする。

**重要性**: **青空文庫のテキストは Shift-JIS。**日本語ユーザーは全員当たる。

#### 採った方式: 初回オープン時に変換してキャッシュする

**リーダー本体には一切手を入れていない。**`Txt` が「読むパス」を差し替えるだけで、
下流から見れば「最初から UTF-8 のファイル」になる。

| タイミング | 走る処理 | コスト |
|---|---|---|
| 初回オープン | 判定 (先頭4KB) + 変換 (8KB ずつストリーミング) | 1〜2秒 |
| 2回目以降 | 何も走らない | **ゼロ** |

1行ずつ変換する方式は**採らなかった。**開くたびに負担が乗るうえ、
変換で長さが変わるため `pageOffsets` と F-2 の `markOffset` が壊れる。

#### 判定の順序

1. BOM `EF BB BF` → UTF-8 (BOM は変換時に除去)
2. BOM `FF FE` / `FE FF` → UTF-16。**対象外。**変換しない
3. 全バイトが 0x80 未満 → ASCII。変換しない
4. 厳密な UTF-8 妥当性検査に通る → UTF-8。変換しない
5. Shift-JIS として妥当 → Shift-JIS
6. どちらでもない → UTF-8 とみなす (現状維持)

実際の日本語 Shift-JIS は先頭バイトが 0x81-0x9F に集中し、これは UTF-8 では継続バイトなので
単独では現れない。**UTF-8 を先に試す判定は十分に堅い。**
UTF-8 検査は overlong・サロゲート・U+10FFFF 超も弾く (Shift-JIS を誤読したときに出る形のため)。

#### 変換表

`scripts/gen_cp932_table.py` が `lib/Utf8/Cp932Table.h` を生成する。
Python の組み込み `cp932` コーデックのみを使い、外部データの取得は不要。

| 項目 | 値 |
|---|---|
| エントリ | 11,340 (定義済み 9,604) |
| **サイズ** | **22,680 B (22.1 KB)** |
| 引き方 | 減算2回とインデックスのみ。**探索なし** |

定義済み 9,604 の内訳は JIS X 0208 6,879 + NEC特殊文字 83 + NEC選定IBM拡張 374 +
IBM拡張 388 + 外字領域 1,880。CP932 として過不足がないことを Python で検算済み。

> **表を SD に置かない判断 (記録)**
> 速度は一括ロードで解決できるが、`.bin` のみの配布 (§4.4) が崩れ、
> 表の置き忘れで青空文庫が黙って読めなくなる。**§4.1 で潰した事故と同型。**
> 規模もフォント1個の 1/300 で、SD に逃がす理由が成り立たない。
> なお**フラットな表は「Flash を使って CPU を買う」選択**であり、低速な端末では正しい。

#### キャッシュの構成

/.crosspoint/txt_<hash>/
├── content.u8 変換後の本文 (ヘッダなし。先頭がオフセット 0)
└── encoding.bin 14 B: magic / version / 元サイズ / 変換後サイズ / 文字コード


**不変条件: 「sidecar が無い = まだ一度も正常に判定できていない」。**

| 判定に至った経路 | sidecar |
|---|---|
| 空ファイル / UTF-8 / ASCII / 判定不能 / Shift-JIS 変換成功 | **書く** (結論に達している) |
| 読み込み失敗 / OOM / 変換失敗 / sidecar 書き込み失敗 | **書かない** (結論ではなく失敗) |

`encoding.bin` は必ず最後に書き、変換後サイズを `content.u8` の実サイズと照合する。
途中で失敗した場合は `content.u8` を削除する。**中途半端なキャッシュを「有効」と誤認させない。**

> **この不変条件を曖昧にして一度踏んだ。**当初 sidecar を Shift-JIS のときだけ書いていたため、
> UTF-8 ファイルでは常に「未判定」と見なされ、開くたびにポップアップと
> E-Ink リフレッシュ (約550ms) が走り、**Quick Resume も毎回無効化されていた。**

**既知の制約**: sidecar とファイルを結びつけているのはサイズだけ (`index.bin` と同じ規則)。
同じバイト数の別の文字コードのファイルに差し替えると、記録された判定のまま読まれる。

#### F-2 との整合

**変換を経由しているファイルでは F-2 (チェックボックス) を無効化する。**

`isMarkdown = hasMarkdownExtension(...) && !txt->isConverted();`

理由: `writeCheckbox()` は元ファイルにオフセットを指定して書き戻すが、
オフセットは**変換後のファイル**のものなので、そのまま書くと元ファイルが壊れる。
`.md` はスマホ由来で UTF-8 なので実害はない。

| 項目 | 値 |
|---|---|
| Flash | **+25,290 B** (変換表 22,680 B + コード約 2,600 B) |
| RAM (静的) | ±0 |

### 6.6 【F-6】日本語UIの描画性能 — ✅ 原因特定・対策済み

#### 原因 (計装による実測で確定)

```
CJK文字を含む文字列 → SDフォントへ経路変更 (resolveTextFontId)
  → UI経路には prewarm が存在しないため interval 表が空
    → 全グリフが必ずミス
      → 1グリフごとに openFileForRead + 2 seek + 2 read
        → キャッシュは overflow リング 8スロットのみ
```

**システムタブだけが収束しない理由**: 異なり字数 91 > リング容量。
古典的なスラッシング。

#### 誤っていた仮説 (記録として残す)

| 仮説 | 結果 |
|---|---|
| フォントファイルが大きいから遅い | **誤り**。8/10pt を 97.5% 削減しても改善せず |
| `truncatedText` の O(n²) が効いている | **誤り**。全41フレームで `truncate_loop entered=0` |
| 行数が多いから遅い | **誤り**。異なり字数がリング容量を超えているため |

#### 対策と効果

`SdCardFont.h` の `OVERFLOW_CAPACITY` を 8 → 128。

| | cap=64 | cap=128 |
|---|---|---|
| グリフミス | 82 | **0** |
| ヒット率 | 80% | **100%** |
| SD I/O | 949 ms | **0 ms** |
| **フレーム総時間** | **1546 ms** | **577 ms** |

577ms = E-Ink 転送 548ms + 計算 29ms。**物理限界に到達。**

#### ⚠️ UI サブセット焼き込みによる影響

**§4.1 の設計では、UI 文字列が SD 経路を通らなくなる。**
したがって **F-6 の問題自体が UI からは消える。**

ただし**ファイル名・書名は本文フォント (SD) 経由**のままなので、
リング容量の問題はファイルブラウザ等に残る。cap=128 は維持する。

### 6.7 【F-7】TXT の折り返しが O(n²) — ✅ 完了 (2026-08-13)

#### 原因

`loadPageAtOffset()` の折り返しループが、候補位置ごとに `line.substr(0, breakPos)` を作って
**最初から測り直していた。**400文字の段落なら約370反復 × 平均215文字。
加えて `line = line.substr(skipChars)` が O(n²) の memcpy を生んでいた。

上流 Issue #2650 は空席 (修正 PR #2158 は著者が自己クローズ)。**フォークで修正した。**

#### 採った方式

`GfxRenderer` に折り返し用のプリミティブを1つ追加した。

size_t findWrapOffset(int fontId, const char* text, int maxWidth,
EpdFontFamily::Style style, bool preferSpace, int extraWidth) const;


前から1文字ずつ幅を積み、超えた位置を返す。**幅の計算をリーダー側に持ち出していない。**
フォント解決・カーニング・丸めは `GfxRenderer` の責務であり、そこから出すと必ずずれる。

実装上の要点:

- **固定小数点のまま積む。**SD経路は最後に1回しか `fp4::toPixel()` を呼ばない。
  ピクセル単位で足し込むと丸め誤差で結果が変わる
- **`resolveTextFontId()` は文字列全体に対して1回だけ呼ぶ。**
  この関数はテキスト全体を走査して CJK の有無でフォントを切り替えるため、
  走査位置ごとに呼ぶと途中でフォントが変わる
- **RTL は旧経路にフォールバックする。**`resolveVisualText()` が bidi 並べ替えを行うため、
  前進スキャンのオフセットが logical 位置に対応しない。RTL 行のみ O(n²) のまま

#### 実機での等価性検証

**折り返しの結果が変わらないことを、旧実装と突き合わせて確認した。**
シリアルが使えない端末のため、結果は SD の `/wrap-verify.txt` に書き出す方式を採った。

| ファイル | 行数 | 不一致 | old | new | speedup |
|---|---|---|---|---|---|
| 英語 (組込フォント、切れ目なしトークン) | 304 | **19** | 10792 ms | 59 ms | **180.3x** |
| 日本語 (SD フォント、チェックボックス含む) | 237 | **0** | 206 ms | 16 ms | 12.5x |

**19件の不一致はすべて同一原因**で、リガチャペア (ﬀ / ﬁ / ﬂ) の中間が折り返し位置に来たケース。
旧実装はペアを分断する位置で折り、新実装はペアの手前で折る。**差は常に1文字。**

**新実装を採用した。**リガチャの分断は組版として不正ではなく、発生条件
(組込フォント かつ 1行に収まらない語) も稀。日本語は SD フォント経路にリガチャが無いため影響ゼロ。

**`CACHE_VERSION` を 4 → 5 に上げた。**折り返し結果が変わりうるため。

#### 段階A: 索引構築中にファイルを開き直さない

`Txt::readContent()` が呼ばれるたびに `openFileForRead()` していた (217ページなら217回)。
**`buildPageIndex()` の間だけハンドルを保持する**ようにした。

スコープを限定した理由: **F-2 の書き戻しが同じファイルを `O_RDWR` で開く。**
セッション全体で保持すると衝突しうる。索引構築とトグルは同時に起きない。

#### 実測 (112KB / 217ページ)

| 段階 | 初回オープン |
|---|---|
| F-7 前 | **約 7分** |
| F-7 後 | 約 45秒 |
| **段階A 後** | **約 15〜20秒** |

**通算 約25倍。**そして計算量が O(n²) から O(n) になったことが本質で、
1MB 級のファイルでも数時間から約2分になった。

| 項目 | 値 |
|---|---|
| Flash | +802 B (F-7) / +282 B (段階A) |
| RAM | ±0 |

#### 残っているコスト

折り返しはもうボトルネックではない。15〜20秒の内訳は概算で:

| 処理 | 217ページ分 |
|---|---|
| `ensureSdCardFontReady()` (70ms/回) | **約15秒** |
| seek + 8KB 読み | 約4秒 |
| 折り返し | ほぼゼロ |

**8KB 読んで1ページ分 (日本語で約900B) しか使っていない**ため、約9倍の重複がある。
対策は3つあり、いずれも保留:

| # | 内容 | 参照 |
|---|---|---|
| 1 | **索引の遅延構築** — 体感をゼロにする | `docs-jp/f9-lazy-page-index.md` |
| 2 | チャンクの使い回し — 17秒 → 3〜5秒 | 同 §10 |
| 3 | 等幅フォントなら表引きを省く | 同 §10 |

#### ⚠️ この関数に次に触るときの前提

1. `findWrapOffset()` は**リガチャペアの中間では折らない**
2. `[ ]` / `[x]` / `[X]` を**すべて `x` の幅として測る** (F-2 §2.4)
3. `buildPageIndex()` と `render()` は**同じ折り返しをしなければならない** (F-2 §3.4)
4. **折り返しの結果が変わったら `CACHE_VERSION` を上げる** (F-2 §3.3)

> `findWrapOffset()` は**上流 Issue #2949 の解決にもそのまま使える。**
> 「`wrappedText` が半角スペースでしか折り返さない」問題で、
> ボタンヒントの切り詰め・Lyra 系の4件・訳文への半角スペース埋め込みが一括で解消する見込み。

### 6.8 ボタンヒントの寸法制約 — **枠拡張では解決できない**

> **この節は「枠を広げればいいのでは」という発想を封じるための記録である。**
> 数値を残さないと同じ調査を繰り返すことになる。

#### #2928 の実装と、日本語での限界

`BaseTheme::drawHintLabel()` が新設され、Base / Lyra の両方から呼ばれる。

```
constexpr int textPadding = 4;
const int maxTextWidth = boxWidth - (textPadding * 2);
if (textWidth <= maxTextWidth) { 1行で中央寄せ; return; }
const auto lines = renderer.wrappedText(fontId, label, maxTextWidth, 2);
```

| 項目 | 実測 |
|---|---|
| 折り返しの実装 | **`wrappedText` を使用** (`BaseTheme.cpp:174`) |
| 折り返し位置 | **半角スペースのみ** (`GfxRenderer.cpp:1632` `remaining.find(' ')`) |
| 折り返せない場合 | `GfxRenderer.cpp:1660-1666` で `truncatedText()` を1行 push して return |
| 切り詰めの中身 | `utf8RemoveLastChar` で末尾から削り `…` を付す。UTF-8 境界は守る |
| **副作用** | **`textPadding` 導入で収容幅が 106 → 98 px に狭まった** |

**日本語ラベルは空白を含まないため、2行折り返しのパスに入らない。**
必ず「単語1個が幅超過」の分岐に落ち、1行の切り詰めになる。
**F-6 §6.1 ② および上流 Issue #2949 と同じ根。**

#### 枠の寸法 (実測)

| テーマ | 枠幅 | フォント | 実効テキスト幅 | 決まり方 |
|---|---|---|---|---|
| **BaseTheme** | 106 px | UI_10 (10pt) | **98 px** | `constexpr int buttonWidth = 106` (固定) |
| **LyraTheme** | 80 px | SMALL (8pt) | **72 px** | `constexpr int buttonWidth = 80` (固定) |
| Lyra3CoversTheme | 同上 | 同上 | 同上 | LyraTheme を継承。未オーバーライド |
| **RoundedRaffTheme** | 215 px に2ラベル | SMALL (8pt) | 実質 ~91 px | `(pageWidth - 40 - 10) / 2` (**動的**) |

X4 のボタン X 座標: Base `{25, 130, 245, 350}` / Lyra `{58, 146, 254, 342}`。
いずれも `constexpr` のハードコードで、**物理ボタンの位置に対応しているため動かせない。**

#### 【結論】枠拡張では解決できない

| 検証 | 結果 |
|---|---|
| BaseTheme のボタン間ギャップ | `[-1, 9, -1]` — **ボタン1↔2 と 3↔4 は既に 1px 重なっている** |
| X 座標を動かさずに広げられる幅 | 均一にするなら **105 px = 現状より狭い**。つまり **1px も広げられない** |
| 6文字 (ダウンロード) に必要な幅 | テキスト 125 px = 枠 133 px |
| 4ボタン分 | **133 × 4 = 532 px > 画面幅 480 px** |
| 動的計算を導入した場合の最良値 | 枠 108 px / テキスト 100 px = **4.81 文字** (現状 4.70 から **+0.1 文字**) |

**左右余白をゼロにしても物理的に不可能。**

### 6.9 【F-8】青空文庫記法への対応 (優先度: 高 / 段階分け)

> **詳細設計は `docs-jp/f8-aozora-notation.md` を参照。**

#### なぜやるのか

**日本語の著作権切れ文学は、事実上すべて青空文庫にある。**
青空文庫のテキストは独自のプレーンテキスト記法を持ち、**ルビが
`漢字《かんじ》` という形で本文中に直接書かれている。**
TXT リーダーが `《》` を解釈できれば、EPUB に変換せずそのまま読める。

#### 記法の実測 (石原莞爾『最終戦争論』/ 112,650 B / Shift-JIS)

| 記法 | 出現数 | 例 |
|---|---|---|
| ルビ `《》` | 47 | `真面目《しんめんぼく》` |
| ルビ範囲指定 `｜` | 5 | `包囲｜殲滅《せんめつ》` |
| 注記 `［＃...］` | 77 | `［＃１字下げ］` |
| 外字 `※［＃...］` | 2 | `※［＃「衄のへん＋絆のつくり」、U+8845、62-12］` |

#### 段階分け

| 段階 | 内容 | 難易度 |
|---|---|---|
| **前提** | **F-3 (文字コード自動判別)** — 青空文庫は Shift-JIS。これが無いと読めない | 中 |
| **段階1** | 記法の除去 (ルビを出さず `《》` `｜` `［＃］` を消す。外字は U+xxxx から復元) | **低** |
| 段階2 | ルビの描画 | **調査次第** |
| 段階3 | 注記への対応 (見出し・字下げ) | 中 |

**段階1 だけでも実用価値がある。**現状は `《しんめんぼく》` が本文中にそのまま
表示されて読みにくい。文字列処理のみで描画層に触れないため、リスクが低い。

#### 段階2 の未確認事項

TXT / EPUB は完全に別クラスであり、`#2665` のルビ実装が `TextBlock` /
`Page::render()` 側にある場合、**TXT リーダーからは使えないおそれがある。**

ただし **2026-08-10 の実機確認で、EPUB のルビ行は行高が可変になっていた。**
同じ仕組みが TXT から使えるなら難易度は下がる。**着手前に調査すること。**

#### Plan B — PC 側で EPUB に変換 (動作確認済み)

`tools/aozora2epub.py` (2026-08-10 作成)。
青空文庫形式 (Shift-JIS / UTF-8 自動判別) → ruby 付き EPUB 3.0。
『最終戦争論』でルビ44・見出し15・段落244 を変換、記法の残存ゼロ。

**F-8 が完成するまでの実用解として配布できる。**

### 9.2 ⚠️ 日本語Windows環境での必須設定 (最も詰まりやすい箇所)

```powershell
$env:PYTHONUTF8 = "1"
pio run
```

**原因**: `scripts/git_branch.py` が `platformio.ini` を読む際にエンコーディングを
指定しておらず、日本語Windows では cp932 で開こうとして失敗する。
**→ PR #2897 でマージ済み。develop ベースなら不要になっているはず (要確認)。**

**`"1"` の意味**: 数値ではなく ON/OFF のフラグ。

**有効範囲**: そのターミナルウィンドウを閉じるまで。
「昨日は通ったのに今日は同じエラー」はほぼこれが原因。

恒久設定する場合:

```powershell
[Environment]::SetEnvironmentVariable("PYTHONUTF8", "1", "User")
```

## 附録C: フォントのライセンス

| フォント | ライセンス | 注意点 |
|---|---|---|
| UDEV Gothic | SIL OFL 1.1 | **Reserved Font Name "UDEV Gothic"** |
| Noto Serif JP | SIL OFL 1.1 | Google Fonts は RFN 非設定が原則。ただし Adobe 由来 (Source Han) は要確認 |

**OFL の定義では、Modified Version に「フォーマットの変更、あるいは新しい環境への
移植」が含まれる。**TTF → `.cpfont` への変換はこれに該当するため、
**生成した `.cpfont` は Modified Version。**

したがって:

- **個人利用は制限なし**
- **再配布時は RFN のあるフォントを改名する必要がある**
- 各コピーに著作権表示とライセンス全文を同梱する必要がある
  (UDEVGothic の場合、派生元の BIZ UDゴシック / JetBrains Mono 分も)

**RFN が制限するのは名前のみで、再配布そのものは自由。**

> ### ⚠️ v0.5 での新たな論点
>
> **UI サブセットを Flash に焼き込む場合、それも「再配布」に該当する。**
> ファームウェアバイナリにフォントデータが含まれるため、
> **ライセンス表示の同梱と、RFN 対象フォントの改名が必要。**
> 焼き込むフォントの選定時に、この点を確認すること。

## 附録D: 既存フォント構成 (v0.4 時点。参考記録)

```
/fonts/NotoSerifJP/
  NotoSerifJP_8.cpfont      51 KB  UDEVGothic 軽量(338文字)  ← UI 小文字・著者行
  NotoSerifJP_10.cpfont     68 KB  UDEVGothic 軽量           ← UI リスト行
  NotoSerifJP_12.cpfont  3,754 KB  UDEVGothicHS フル         ← UI 見出し + 本文Small
  NotoSerifJP_14.cpfont  4,934 KB  Noto Serif JP Medium      ← 本文 Medium
  NotoSerifJP_16.cpfont  6,119 KB  Noto Serif JP Medium      ← 本文 Large
  NotoSerifJP_18.cpfont  7,620 KB  Noto Serif JP Medium      ← 本文 Extra Large
```

**同一ファミリー内でサイズごとに書体を混在させる手法**が実機で動作確認済み。
公式ドキュメントに記載のない使い方。

**成立する理由**: インターバルテーブルはサイズ(ファイル)単位でファミリー単位ではなく、
フォントIDが内容ハッシュを含むため、サイズごとに中身が違ってもIDが衝突しない。

> **v0.5 での位置づけ**: §4.1 の UI/本文分離により、この構成は**本文専用**になる。
> 8/10/12pt を UI 用に確保する必要がなくなるため、
> **本文フォントは 12〜18pt のみで足りる。**
