## 1. (a) 規則 1 個あたりの実測

コンパイラに出させた（`ShowSz<N>` の不完全型で値を吐かせる）:

| | バイト |
|---|---|
| `sizeof(CssStyle)` | **104** |
| `sizeof(std::string)` | 24 |
| `sizeof(std::pair<const std::string, CssStyle>)` | 128 |
| ★ `sizeof(_Hash_node<pair<const string, CssStyle>, true>)` | ★ **136** |

保持は `std::unordered_map<std::string, CssStyle, ...> rulesBySelector_` なので、
**規則 1 個 = ヒープ確保 1 回・136 バイト**。
これに加えて bucket 配列（要素数ぶんのポインタ、**1 個の連続確保**）と、
短縮最適化に入らない長いセレクタの文字列。

★ `MAX_RULES = 1500` は **1500 × 136 = 204,000 B**。
起動直後の空きヒープは約 **130 KB** なので、
**上限そのものが端末の容量を超えている。**

### 104 B の内訳が示すもの

`CssStyle` の 18 性質のうち、`margin` と `padding` の 8 フィールドは
`CssLength`（`float value` ＋ `CssUnit unit`）= **8 B × 8 = 64 B** を占める。
★ **104 B の 6 割が余白の `float`** である。

## 2. ★ 現物で「実際に残る数」を数えた

解析側の 2 つのフィルタをそのまま写した計数（`anySet()` 相当の性質判定と、
セレクタの拒否文字 `"+>[:#~* "`、キーは大小無視で合併）:

| 本 | 規則ブロック | ★ **保持される規則** | ★ **バイト** | 上限到達 |
|---|---|---|---|---|
| `saishu-sensoron.epub` | 0 | **0** | 0 | ─ |
| `テスト文章.epub`（一太郎） | 30 | **40** | 5,440 | ─ |
| `季節の台所.epub`（一太郎） | 30 | **40** | 5,440 | ─ |
| `…AozoraEpub3.epub` | 2,278 | ★ **536** | ★ **72,896** | 到達せず |
| `最終戦争論でんでん.epub` | 1,935 | ★ **501** | ★ **68,136** | 到達せず |

捨てられている数も出た（AozoraEpub3 の例）:
**性質を 1 つも持たない 744 ブロック**、**セレクタが扱えない 1,753 個**。
★ **既存のフィルタは 2,278 → 536 まで、よく効いている。**
それでも **536 × 136 = 72,896 B。**

### ★ これが答え

| | |
|---|---|
| 起動直後の空きヒープ | 約 **130,000 B** |
| CSS 規則の常駐 | ★ **72,896 B（56%）** |
| 残り | 約 57,000 B |
| そこから出ていくもの | **フレームバッファの貸出 48,000 B**、section 構築、フォントの常駐表、ページ要素 |

★ **48 KB の貸出を引くと 9 KB しか残らない。**
だから section が組めずに **1/1** になり、ページ送りで
**203 バイトのグリフが取れずに abort する。**

★ **「CSS の枚数でも本の大きさでもなく規則の数で割れる」というご観察の理由**:
費用が**規則 1 個 = 136 B** で決まっているから。
バイト数では割れない（AozoraEpub3 は 171 KB で 536 規則、
でんでんは 147 KB で 501 規則 ── 比例していない）。

## 4. (c) `0x421b36d5` の解決 ── ★ 条件付きで報告する

```
0x421b36d5 → __gxx_personality_v0        (libsupc++/eh_personality.cc:463)
0x421b3345 → read_sleb128                (libgcc/unwind-pe.h:169)
```

★ **ただしこれは「いまの .elf」に対する解決で、落ちた実機のイメージではない。**
実機は `cb253ff3` のビルド（§5 参照）で、その `.elf` は
その後のビルドで上書きされている。libsupc++ の番地は**ビルドごとに動く**ので、
**関数名を断定してはならない。**

**断定できること**: 2 つの番地は **912 バイト離れた、同じ例外処理・巻き戻し
コードの領域**にある。つまり **別の命令・同じ機構** ──
`-fno-exceptions` で確保に失敗した `operator new` が
`__throw_bad_alloc` → `std::terminate` → `abort` に落ちる経路である。
★ **そしてログ末尾が確保そのものを名指ししている**（203 B のグリフ × 11 行）ので、
記号名は今回ほとんど情報を足さない。

★ **手順の修正**: 控えの `.bin` の隣に **`.elf` も保存する。**
番地を解決できるのは、そのイメージの `.elf` があるときだけである。

    を両方探す。印があって版が古ければ「版文字列だけが古い」。
    印が無ければ「そのビルドに入っていない」。

★ **羅闇さんの提案が、設計として正しかった。**

我々の案1は「本を閉じるときにキャッシュを解放する」だった。
解放そのものは合っていたが、**置き場所が間違っていた**:

| | 置き場所 | 払う人 | 得る人 |
|---|---|---|---|
| **我々の案** | 本を閉じるたび | ★ **本を読む人全員**（次のページで SD 再読み込み） | ネットワークを開く人だけ |

★ **代償を払う場所を、効く場所に移した。**
これは「何をするか」ではなく「どこでするか」の指摘で、
**我々は前者だけを見ていた。**

**一般化して記録する価値がある形**:

> ★ **代償のある対策を入れるとき、「誰が払い、誰が得るか」を分けて書く。
> 一致していなければ、置き場所が間違っている。**

解放は本を閉じるときも「正しく動く」ので、
**試験では区別がつかない** ── 区別がつくのは
「次のページが遅くなるのは誰か」を**数えたときだけ**である。
