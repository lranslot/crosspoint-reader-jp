## 1. 対象と方針

### 1.1 経緯

AliExpress 等の国際流通品として販売される Xteink X4 の一部は、工場出荷時に
**USBフラッシュ書き込みが無効化 (ロック)** されている。日本語圏には、このロック品に
カスタムファームウェアを導入し、さらに日本語UI化まで到達した記録が存在しない。

2026-08-09、上流への日本語翻訳 PR (#2940) が**方針上の理由でクローズ**された。
翻訳の品質ではなく、CJK 字形が同梱フォントに含まれないことが理由である (§9.1)。
これを受け、**独立したフォークとして日本語版を公開する**方針に転換した。

### 1.2 目的・非目的

**目的**:

1. スマートフォンで作成したメモ / TODO (Markdown) を X4 上で快適に閲覧する
2. Markdown のチェックボックスを端末上でトグルできるようにする
3. UI を日本語化する
4. **フォントを別途用意しなくても日本語で使える状態で配布する**
5. 上記を **SDカード経由で導入可能なファームウェア** として公開する

**非目的 (スコープ外)**:

- USBフラッシュロックそのものの解除 (技術的に不可能、かつ不要)
- PDF のネイティブレンダリング
- Bluetooth 機能の復活
- **上流へのマージを前提とした設計上の妥協**

### 1.3 上流との関係

**本文レンダリングの改善は受理され、UI 翻訳は全滅している。**この非対称が
フォークの存在理由である。

| 領域 | 状況 |
|---|---|
| **本文レンダリング** | 活発に受理。#2288 / #2652 / #2665 / #2710 / #2768 / #2781 がマージ済み |
| **UI 翻訳** | 全滅。韓国語 (#1609 / #2208)、中国語 (#2273)、日本語 (#2940) がいずれもクローズ |
| CJK UI フォント | #505 / #1059 クローズ、#2521 (フォールバック) のみマージ |

CJK 言語ファイルは**一度もマージされていない** (2026-08-10 時点)。
**境界はフォントであって翻訳品質ではない** (§5.1)。

本プロジェクトは上流に敵対しない。一般性のある修正は PR として戻す
(実績: PR #2897 マージ済み)。日本語固有の機能はフォークに留める。

### 1.4 ベースの固定と追随の方針

**ベースは upstream/develop `81028d58` で固定する。常時追随はしない。**

| 項目 | 内容 |
|---|---|
| フォーク | `lranslot/crosspoint-reader-jp` (ブランチ `main`) |
| ベース | upstream/develop **`81028d58`** (2026-08-10 時点) |
| ローカル | `D:\dev\crosspoint-reader-jp` |
| ライセンス | MIT (上流を継承) |

**`git rebase upstream/develop` を実行しない。**上流で日本語に効く変更が入った
時点で、その都度判断する。リリースごとに「ベース: upstream develop `<SHA>`」を
明記して状態を可視化する。追随を検討する際の材料は §9.3。

#### 退避先 (触らない)

### 2.5 書き込みと復旧の手順

#### ⚠️ ロック品における書き込み経路 — **本プロジェクト最大の知見**

| 経路 | 1.4系→1.4系 | 1.4系→1.5系 | 備考 |
|---|---|---|---|
| ファイルブラウザから `.bin` 直接実行 | ○ | — | 1.4.1 で成功実績あり |
| Settings > SD Card Firmware Update | ○ | **× Invalid firmware file** | 公式RC3でも同様に失敗 |
| **Escape Hatch > Flash Firmware** | ○ | **○** | **唯一の突破口** |
| 電源+上ボタン (OEMブートローダー) | × | × | ストック時のみ有効 |
| USB Web Flasher | × | × | ロックのため不可 |

> **1.4.1 の SD更新機能は 1.5系イメージを受け付けない。**
> 自作ビルド・公式RC3 の双方で「Invalid firmware file」を再現。
> ファイルサイズは PC 上の原本と 1 バイト単位で一致 (5,495,888 B)。
>
> **解決策**: Debug ページから **Escape Hatch (recovery, 0.4 MB)** を取得し、
> 通常の SD 更新でこれを書き込む。起動後のメニューから `Flash Firmware` を選び、
> SD 上の `.bin` を指定すれば 1.5系が書き込める。
> 一度 1.5 系に上がれば、以降は通常の SD Card Firmware Update が使える。

#### 標準的な書き込み手順 (1.5系運用時)

1. `.pio\build\default\firmware.bin` を **`update.bin`** にリネーム
2. SDカードの**ルート**に配置
3. 端末で 設定 > システム > SDカードファームウェア更新 を実行

> **運用ルール**: SDカードのルートに `update.bin` を**常設しない**。
> 書き込み時のみリネームして配置する。誤爆防止のため。

#### 復旧経路の確保 (必須)

| ファイル | 用途 |
|---|---|
| `escape-hatch.bin` | **緊急脱出・世代跨ぎの書き込み** |
| `crosspoint_1.4.1_update.bin` | 安定版への復帰 |
| `crosspoint_1.5rc3_update.bin` | 公式1.5系への復帰 |
| `stock_english_update.bin` | 純正 (英語) への復帰 |
| `stock_chinese_v6.2.4_update.bin` | 純正 (中国語 / 出荷時) への復帰 |

#### 既知の障害と対処

| 現象 | 原因 | 対処 |
|---|---|---|
| Invalid firmware file | 1.4系が1.5系イメージを拒否 | **Escape Hatch を使用** |
| Escape Hatch で "No .bin files" | SDカード未挿入 / 認識前 | 挿入して**再起動** |
| SD更新で "Error 9" | 既知の未解決バグ | **文鎮化ではない**。再起動して再試行 |
| 1.2.0 系で OTA が常に失敗 | RAM不足による TLS+書き込みの競合 | **1.2.0ベースを導入しない** |
| SDカードのフォーマット不能 | 書き込み過多による物理故障 | カード交換。**MLC 推奨** |
| develop 移行後に初回起動が遅い | キャッシュ形式の更新による全再生成 | **正常。**データ損失ではない |

### 2.6 ⚠️ 設計上の絶対制約

> ### ⚠️ OTA および SDカード更新機能を削除してはならない
>
> ロック品には USB の逃げ道が存在しないため、この機能を失った時点で
> **更新手段が完全にゼロになる。**

| 制約 | 理由 |
|---|---|
| **ファイル全体をメモリに載せない** | ESP32-C3 の RAM 制約。PSRAM が無い |
| 1.2.0 系をベースにしない | ロック品X4でOTAが詰む既知事例あり |
| フォント名は英数字・ハイフンのみ | `/fonts/<FamilyName>/` のパス制約 |
| **英語の翻訳を削除しない** | フォント破損時の避難先。消すと復旧手段を失う |
| **UI フォントを Flash から外さない** | 日本語UIが SD 依存に戻り、上流と同じ問題を抱える |
| 残 Flash を使い切らない | **アプリ区画 (6,553,600 B) の上限であり、OTA が食う分ではない。**`partitions.csv` で `app0` / `app1` が各 `0x640000` と別々に確保されているため、更新用の領域は最初から確保済み。残りは純粋にアプリを大きくできる余地 |
| **実機検証は人間が行う** | ビルドが通っても動くとは限らない。確認項目を列挙して止まる |

## 3. この端末で分かっていること

> **機能に属さない、端末そのものの性質を集めた節。**
> 新機能の可否は、ほぼここに書いてある数値で決まる。
> **数値は実測値。分からないものは「未計測」と書いてある。**

### 3.1 画面

| 項目 | 値 | 出典 |
|---|---|---|
| 解像度 | 480 × 800 (ポートレート) | — |
| フレームバッファ | **48,000 B** (800 × 480 ÷ 8)。**1枚のみ** | `-DEINK_DISPLAY_SINGLE_BUFFER_MODE=1` |
| `FAST_REFRESH` | **約 548 ms** (パネル転送、実測) | F-2 の計装 |
| `HALF_REFRESH` | **1720 ms** | `HalDisplay.h:16` のコメント |
| `FULL_REFRESH` | 未計測 | — |
| TXT 1ページの描画 (定常) | **1591 ms** (内訳は §6.2) | F-2 の計装 |

**全画面書き換えのコストが設計を縛る。**548 ms は物理時間であり、コードでは
削れない。したがって:

- **1操作あたり1回しか画面を書き換えられない。**索引の進捗で再描画すると
  1ページ 1.7 秒になり、217ページで約6分かかる (→ §8.5)
- 連続操作の途中で `displayWithRefreshCycle` が N 回に1回 `HALF_REFRESH` を
  使うため、**1720 ms の全画面フラッシュが混ざる**。これは妥当な挙動

#### ⚠️ 部分更新は API レベルで事実上できない

| 層 | 状態 |
|---|---|
| `FreeInkDisplay::displayWindow(x,y,w,h,turnOffScreen)` | **実装済み** (`FreeInkDisplay.cpp:753-770`)。ただしヘッダに `EXPERIMENTAL` |
| `HalDisplay::displayWindow` | **存在しない** |
| `GfxRenderer::displayWindow` | 宣言が `GfxRenderer.h:181` に**コメントアウト**されたまま |
| グレースケールの窓更新 | **不可能。**`displayGrayBuffer` に窓指定版が無い |

さらに **`_inGrayscaleMode` の間は窓指定が無視され、全画面 `HALF_REFRESH`
(1720 ms) に落ちる** (`Ssd1677Driver.cpp:497-504`)。AA が有効だとページ描画の
最後が `displayGrayBuffer()` なのでパネルは常にグレースケール状態にあり、
**そこで窓更新を呼ぶと現状より遅くなる。**

座標変換 `screenRectToAlignedMemRect()` (8px 整列・向き回転) は既に本番稼働中
なので、配線自体は50行前後の見込み。**調査済みで保留**
(`docs-jp/f2-deferred-partial-update.md`)。

### 3.2 入力

#### 物理構成

ADC 抵抗ラダー (`XteinkAdcLadder`)。**6ボタンが2本の ADC ピンに多重化**されている
(Back/Confirm/Left/Right が group 1、Up/Down が group 2)。X3 と X4 で同一。

**同一グループ内の同時押しは区別できない。**

#### ⚠️ `InputManager` は差分方式で、イベントを溜めない

```cpp
void InputManager::update() {
  pressedEvents = 0;              // 毎回クリア
  ...
}
void InputManager::applyStateChange(const uint8_t state, ...) {
  pressedEvents = state & ~currentState;   // 代入。前回のイベントは消える
```

**`update()` の呼び出し間隔より短い押下は、原理的に存在しなかったことになる。**
人がボタンを押して離すのは 100〜200 ms なので、**1周が 200 ms を超えると
押下が消え始める。**

EPUB の背景組版を計測したところ、盲目時間は平均 477 ms / 最大 957 ms だった。
**押下が丸ごと飲まれる。**

> `wasPressed()` / `wasReleased()` は `InputManager.cpp:456` の
> `return releasedEvents & (1 << buttonIndex);` で、**読み取りで状態を消さない
> const 関数。**同じ周で複数回読める。

#### `MappedInputManager` のラッチ (`010c4603`)

上の差分方式を、1周が長くなっても耐えるようにした層。

| 項目 | 値 |
|---|---|
| 粒度 | **物理ピン単位** (`LATCH_PIN_COUNT = BTN_POWER + 1`) |
| 保持 | 押下・解放それぞれ。最初の読み取りで消費 |
| 期限 | **`LATCH_MAX_AGE_MS = 1500`** |
| 破棄 | **アクティビティ遷移で全破棄** (`clearLatches()`) |

**論理ボタンではなく物理ピンで持つ。**同じピンが設定 (リマップ・側面レイアウト)
によって別の論理ボタンを担うため、論理側で持つと1つの押下を二重に数えたり
取り落としたりする。

**ピーク用メソッド**: `wasReleasedPeek()` はラッチを消さずに同じ答えを返す。
**ガード専用** — 「別のボタンも離されたなら処理を飛ばす」のように、
エッジの所有権が次の処理にある場合だけ使う。通常の入力処理が使うと、
消費されないエッジが次の周でもう一度発火する。

#### ⚠️⚠️ ラッチの限界 — **サンプルされなかったエッジは作れない**

**ラッチは「長い1周をまたいでエッジを届ける」ものであって、
「サンプルされなかったエッジを作り出す」ことはできない。**

`gpio.update()` は1周に1回しか呼ばれない。1周が押下時間より長くなると、
押して離す動作がサンプルとサンプルの間に丸ごと収まり、差分が立たない。
**ラッチに記録するものが存在しない。**

実際にこれを踏んだ: F-9 フェーズ2 で省電力により CPU が 10 MHz に落ち、
1周が 1.3〜2.8 秒になった結果、**ラッチがあるのにボタンが完全に効かなくなった**
(→ §3.4、§8.4)。

#### SDK の `beginAsync()` を採らなかった理由

SDK には背景ポーリング用の API がある
(`freeink-sdk/libs/hardware/InputManager/include/InputManager.h:159`)。
FreeRTOS タスクを立てて `pollMs` ごとにサンプルし、押下をキューに溜める。
**用途としては正しく、E-Ink のリフレッシュ中の押下を拾うために作られている。**

採らなかった理由は3つ。

| # | 理由 | 根拠 |
|---|---|---|
| 1 | **排他的である** | ヘッダに明記: *"When async polling is active the app must NOT call `update()`/`wasPressed()` itself; the task owns the edge state. Drain with `popPress()` instead."* |
| 2 | **押下しか溜まらない** | 公開 API は `popPress()` / `popTouchTap()` / `popSwipe()` の3つで、**解放に相当するものが無い。**`detectPageTurn` は設定次第で `wasReleased` を使うため、置き換えられない |
| 3 | **呼び出し箇所が多すぎる** | **253 箇所 / 47 ファイル** → 下記 |

**呼び出し箇所の数え方 (定義を固定する)**

> **`src/` 配下の `.cpp` / `.h` から、`wasPressed` / `wasReleased` / `isPressed` /
> `getHeldTime` の4つを単語境界で数えた出現数。`src/MappedInputManager.{h,cpp}`
> (定義そのもの) を含む。**

| | 出現数 |
|---|---|
| `wasPressed` | 100 |
| `wasReleased` | 96 |
| `isPressed` | 33 |
| `getHeldTime` | 24 |
| **合計** | **253 (47 ファイル)** |

参考値 (同じ4 API、同じ数え方で範囲を変えたもの):

| 範囲 | 定義ファイルを含む | 除く |
|---|---|---|
| **`src/` のみ** | **253 / 47ファイル** | 231 / 45ファイル |
| `src/` + `lib/` | 269 / 49ファイル | 247 / 47ファイル |
| + `freeink-sdk/libs/` | 289 / 53ファイル | 267 / 51ファイル |

> **以前の調査 (F-2 着手前) も同じ定義で 253 箇所だった。**
> 内訳の配分は当時と少し違う (当時 `wasPressed` 99 / `wasReleased` 93 /
> `isPressed` 37 / `getHeldTime` 24)。入力ラッチの実装で呼び出しが入れ替わった
> ためで、**総数が一致しているのは偶然ではなく、ラッチが呼び出し側を
> 1箇所も変えずに済んだことの裏返しである。**
>
> 2026-10-21 に再計測。**この節の数値を引用するときは、必ず上の定義を添えること。**
> 範囲や API の取り方で 231〜289 まで動く。

**1 と 3 が組み合わさると、全面書き換えしか選択肢が無くなる。**
`MappedInputManager` 側でラッチする方式なら、呼び出し側は1箇所も変わらない。

> **採らなかった記録として残す。**入力が消える問題に再度ぶつかったとき、
> 「SDK に機能があるのに使っていない」ことを疑うのは自然であり、
> そのたびにこの3点を調べ直すのは無駄である。

### 3.3 タスク構成

| タスク | 走るもの |
|---|---|
| メインタスク | `loop()`、`ActivityManager::loop()` |
| **レンダータスク** | **`render()`** |

**`ActivityManager` が `RenderLock` を取ってから `render()` を呼ぶ**
(`ActivityManager.cpp:53` 付近)。したがって:

- **`render()` の中は `RenderLock` 保持下**である
- **`loop()` は保持していない。**メンバを触るなら自分で取る
- `requestUpdate()` は `xTaskNotify` でレンダータスクを起こすだけ。**待たない**
- `requestUpdateAndWait()` は待つ。**`RenderLock` を持ったまま呼ぶと詰む**

#### アクティビティの寿命

| 遷移 | `onExit()` | `onEnter()` |
|---|---|---|
| 戻る (`Pop`) | ✅ 呼ばれる (`ActivityManager.cpp:174`) | — |
| 置換 (`Replace`) | ✅ 呼ばれる。**スタック上の全アクティビティにも**(`:140`) | ✅ |
| **メニューを開く (`Push`)** | **❌ 呼ばれない** (`:145` で move のみ) | — |
| **スタックから復帰** | — | **❌ 呼ばれない** (`:104-106`) |

**`Push` / 復帰ではインスタンスがそのまま生き続ける。**状態は保たれ、
`initialized` も `true` のままなので初期化は走らない。**これは意図した挙動**で、
メニューから戻ったリーダーが索引を作り直さないのはこのためである。

アクティビティは**ヒープ確保され、`onExit()` の後に `delete` される。**
`onEnter()` で確保したものは `onExit()` で解放する。FreeRTOS タスクは
`onExit()` で `vTaskDelete()` する。

### 3.4 電源

| 定数 | 値 | 出典 |
|---|---|---|
| `IDLE_POWER_SAVING_MS` | **3000 ms** | `HalPowerManager.h:33` |
| `LOW_POWER_FREQ` (PSRAM あり) | 80 MHz | `HalPowerManager.h:29` |
| **`LOW_POWER_FREQ` (PSRAM なし = X4)** | **10 MHz** | `HalPowerManager.h:31` |
| 通常周波数 | `begin()` 時の `getCpuFrequencyMhz()` を記録して戻す | `HalPowerManager.cpp:20` |
| `BATTERY_POLL_MS` | 1500 ms | `HalPowerManager.h:34` |

**X4 は PSRAM 非搭載なので 10 MHz に落ちる。**3秒間操作が無いと
`setPowerSaving(true)` が呼ばれ、`main.cpp` のループ末尾が `delay(50)` も加える。

#### ⚠️ 「急いで終わって寝る」が省電力になる

**16分の1のクロックで16倍の時間動くのは、省電力ではない。**

実測: F-9 フェーズ2 で索引を背景構築したところ、1ページ 80 ms が **約 1.3 秒**に
なり、217ページで **5〜10分** (実測は約10分) かかった。本来 18〜20秒である。

さらに 1周が押下時間を超えるため、**入力が完全に壊れた** (→ §3.2 の限界)。

`Activity::skipLoopDelay()` を `override` して `true` を返している間、
ループ末尾の待ちと省電力が抑止される。

```cpp
// TxtReaderActivity.h
bool skipLoopDelay() override { return !indexComplete; }
```

**抑止するのは必要な間だけにする。**終わったら通常の省電力に戻す。
EPUB は `section && section->isBuilding() && !buildHeapPaused` という
ヒープゲート付きの条件を使っている (`EpubReaderActivity.h:217`)。

### 3.5 ストレージ

#### SD は 512 バイトのセクタ単位で書く

**4バイト書いても500バイト書いても、書き込みにかかる時間は同じ。**

| 保存件数 | バイト数 | 書き込みコスト |
|---|---|---|
| 1件 | 4 B | 同じ |
| **16件** | **64 B** | **同じ** |
| 128件 | 512 B | 同じ (上限) |
| 129件 | 516 B | **セクタ2つ分になる** |

これが `progress.bin` に読書履歴16件を持てる理由 (§4.3)。**128件まで無料。**

> SPIFFS (設定ファイル) 側は逆に**書き込み回数を絞る**。セクタの消去回数に
> 上限があるため、値が変わったときだけ書く。

#### ⚠️ SdFat はスレッドセーフではない

**すべての SD アクセスは `HalStorage` を通す。**`SdSpiCard` が SPI バスの状態を
同期なしの `m_spiActive` で追っているため、2つのタスクが同時に呼ぶと
FreeRTOS の `xTaskPriorityDisinherit` assert を踏んで panic する (SdFat issue #518)。

`HalStorage` が `storageMutex` で直列化し、`HalFile` の全メソッドがそれを取る。

#### ファイルハンドルの寿命とデストラクタ

`-DDESTRUCTOR_CLOSES_FILE=1` なので、`FsFile` のデストラクタが自動で `close()`
する。**ローカル変数に明示的な `close()` は書かない。**

`HalFile` も同じ性質を持つ。**`HalFile::Impl` のデストラクタが
`StorageLock` を取ってから `file.close()` を呼ぶ** (`HalStorage.cpp:71-74`)。
したがって:

- **`Txt` のデストラクタが走れば、保持していた逐次読み込みハンドルは必ず閉じる。**
  `endSequentialRead()` が呼ばれなくても、メンバ破棄だけで閉じる
- `Txt` にユーザー定義デストラクタは無い (暗黙 default) が、
  それで十分である

明示的な `close()` が要るのは3つの場合だけ:
同じパスを `Storage.remove()` する前 / 同じ `FsFile` 変数を開き直す前 /
メンバ変数を意図した時点で解放するとき。

#### 逐次読み込みの開き直しコスト

**`openFileForRead()` 1回で約 130 ms** (実測)。TXT のページ組版が 70〜90 ms
なので、**1ページごとに開き直すと組版より開き直しの方が高い。**

`Txt::beginSequentialRead()` / `endSequentialRead()` で1本のハンドルを持ち回る。
`beginSequentialRead()` は既に開いていれば no-op なので、ティックをまたいで
生き残る。

## 4. リーダーの構造

> **縦書き (F-5) とルビ (F-8 段階2) の判断に必要な土台。**

### 4.1 TXT / EPUB / XTC は別クラス

**共通基底 `ReaderActivity` は入口の振り分けのみ。**実装は共有されない。

| リーダー | 描画の粒度 | 最終ページで「次へ」 |
|---|---|---|
| **TXT** (`TxtReaderActivity`) | **視覚行1本につき `drawText` 1回** (実測 約75回/ページ) | **`onGoHome()` を直接呼ぶ。**確認なし。即座に閉じる |
| **EPUB** (`EpubReaderActivity`) | `Page::render()` が単語・ラン単位 (実測 約2,900回/ページ) | `EndOfBookOptions` (次の本 / ホーム / 留まる / 再描画) |
| **XTC** (`XtcReaderActivity`) | — | `EndOfBookOptions` |

**この非対称が設計判断を左右する:**

- **TXT の行単位描画は F-2 に有利だった。**1行だけ別の `drawText` で
  マーカーを描けば済む
- **ルビは EPUB 側 (`TextBlock` / `ParsedText`) にある。**TXT から到達できるかは
  未調査 (§7.2)
- **禁則処理も EPUB 側にある** (§4.4)
- TXT に終了画面が無いことは F-2 の設計に影響した (§6.3)

### 4.2 TXT のページ模型

#### ⚠️ 1ページ = N 行、行高は一定

**これが TXT リーダーの最も基本的な前提である。**

```cpp
// initializeReader()
viewportWidth  = screenWidth - orientedMarginLeft - orientedMarginRight;
viewportWidth -= markerWidth;                      // .md のときだけ正の値
const int viewportHeight = screenHeight - orientedMarginTop - orientedMarginBottom;
const int lineHeight = renderer.getLineHeight(cachedFontId);   // = advanceY
linesPerPage = viewportHeight / lineHeight;
if (linesPerPage < 1) linesPerPage = 1;
```

- **`viewportWidth`** は折り返しの上限として `findWrapOffset()` に渡される
- **`linesPerPage`** は `viewportHeight / lineHeight` の**割り算1回**
- **幅と高さは独立した2つのスカラ**であり、互いを参照しない

`loadPageAtOffset(offset, outLines, nextOffset)` が1ページ分を組み、
`outLines` の本数が `linesPerPage` に達したら止めて `nextOffset` を返す。

#### 縦書きはこの前提を保ち、ルビはこれを壊す

| | **F-5 縦書き** | **F-8 段階2 ルビ** |
|---|---|---|
| 1ページ = 固定数のセル | **保たれる。**1em の等間隔 | ❌ **壊れる。**ルビの有無で行高が可変 |
| `linesPerPage = viewportHeight / lineHeight` | 割る対象が入れ替わるだけ (`viewportWidth / columnWidth`) | ❌ **割り算が成立しない** |
| 折り返しの上限 | `viewportWidth` → `viewportHeight` に差し替え | 同じだが**ルビ幅を加味**する必要がある |
| 送り量の計算 | **単純化する** (全角一律 1em) | ❌ **複雑化する** (ルビ幅が親文字幅を超える判定) |
| `pageOffsets` / F-9 | そのまま使える | 行高可変への追従が必要 |

**縦書きは「等間隔のマスに1文字ずつ置く」モデルで、横書きのプロポーショナル
配置より単純である。**一方ルビは、`loadPageAtOffset()` と索引が依存している
「行高は定数」という前提を破壊する。詳細な見積もりは §7.1 / §7.2。

#### 読書位置はバイトオフセットで持つ (F-9 フェーズ1)

```cpp
size_t currentOffset = 0;        // これが正本
int currentPage = 0;             // currentOffset から導出 (表示用)
```

**ページ番号は全ページを数え終わらないと意味を持たない。**オフセットなら
索引が無くても意味を持つ。これが遅延構築を可能にした中核の発想 (§6.7)。

### 4.3 キャッシュの構成

```
/.crosspoint/txt_<hash>/
├── index.bin      ページ索引           "TXTI" v5
├── progress.bin   読書位置と履歴       "PTXP" v1
├── encoding.bin   文字コード判定の記録 "TXEC" v3   15 B
└── content.u8     変換後の本文 (Shift-JIS だった場合 / 青空記法を除去した場合)
```

#### `hash` の正体

```cpp
// Txt.cpp:28
const size_t hash = std::hash<std::string>{}(filepath);
cachePath = cacheBasePath + "/txt_" + std::to_string(hash);
```

**ファイルパスの `std::hash`。**したがって**ファイルを移動・改名すると
別のハッシュになり、読書位置と索引を失う。**内容は見ていない。

#### `index.bin` の検証項目 — **8つ。mtime もハッシュも無い**

| 順 | 項目 |
|---|---|
| 1 | magic `"TXTI"` |
| 2 | `CACHE_VERSION` (**現在 5**) |
| 3 | **ファイルサイズ** |
| 4 | `viewportWidth` |
| 5 | `linesPerPage` |
| 6 | `cachedFontId` |
| 7 | `cachedScreenMargin` |
| 8 | `cachedParagraphAlignment` |

続いて `numPages` (uint32) と、ページ先頭オフセット (uint32 × numPages)。

**折り返しアルゴリズムを表すものが1つも無い。**これが §8.2 の罠の源である。

> **F-2 がこれに救われた。**`- [ ]` ↔ `- [x]` はファイル長が変わらないので、
> 1バイト書き戻しても索引は無効化されない。**ファイル長が変わらない設計に
> した判断がそのまま効いた。**

#### `progress.bin` の形式

```
uint32 magic ("PTXP") | uint8 version | uint8 count | uint16 reserved | uint32 offset × count
```

**8バイトのヘッダ + 直近16ページ分のオフセット。最大 72 バイト。**
`PROGRESS_MAX_OFFSETS = 16`。再開直後から**16ページ戻れる。**

16件にした理由は §3.5 (SD は512バイト単位なので128件まで無料)。
16で足りるのは、**履歴の目的が「索引が追いつくまでの数秒を埋めること」**だから。

**新旧の判別はファイルサイズで行う。**4バイトなら旧形式 (ページ番号)、
それより大きければ新形式。旧形式は次回オープン時に移行する。

#### `encoding.bin` — **15 バイト**

```
uint32 magic ("TXEC") | uint8 version | uint32 元サイズ | uint32 変換後サイズ
| uint8 文字コード | uint8 記法除去フラグ
```

> **v0.7 は「14 B」と書いていたが、現在は 15 B である。**
> F-8 段階1 で `stripped` フラグ1バイトが加わり、`ENCODING_VERSION` が
> 3 になった。2026-10-21 に `Txt::writeEncodingInfo()` を読んで確認。

**不変条件: 「sidecar が無い = まだ一度も正常に判定できていない」** → §8.2。

#### 各ファイルのバージョンと、いつ上げたか

| ファイル | 現在 | 経緯 |
|---|---|---|
| `index.bin` "TXTI" | **v5** | **v3 → v4**: F-2 でマーク幅の正規化を入れたとき。`viewportWidth` が同じ値のまま折り返しが変わるため (§8.2)。**v4 → v5**: F-7 で折り返しを O(n) 化したとき。リガチャ境界の扱いが変わるため。**F-9 フェーズ2 では上げていない** — 折り返しは変えておらず、構築の順序だけを変えたため |
| `progress.bin` "PTXP" | **v1** | F-9 フェーズ1 で新設。旧形式 (4バイトのページ番号) はサイズで判別して移行 |
| `encoding.bin` "TXEC" | **v3** | F-3 で新設。F-8 段階1 で `stripped` フラグを追加して v3 に |

> **EPUB 側は別系統**: `book.bin` v10 / `section.bin` v37 (develop ベース時点)。

### 4.4 折り返しの仕組み

#### `findWrapOffset()` — F-7 で新設したプリミティブ

```cpp
size_t findWrapOffset(int fontId, const char* text, int maxWidth,
                      EpdFontFamily::Style style = REGULAR,
                      bool preferSpace = true, int extraWidth = 0) const;
```

**前から1文字ずつ幅を積み、`maxWidth` を超えた位置を返す。**
`maxWidth` は**軸を知らない単なるスカラ**である (→ F-5 で使い回せる根拠)。

実装上の要点:

- **固定小数点のまま積む。**SD 経路は最後に1回しか `fp4::toPixel()` を呼ばない。
  ピクセル単位で足し込むと丸め誤差で結果が変わる
- **`resolveTextFontId()` は文字列全体に対して1回だけ呼ぶ。**走査位置ごとに
  呼ぶと途中でフォントが変わる
- **リガチャペアは不可分。**旧実装は ﬀ / ﬁ / ﬂ の中間で折れたが、前進スキャンは
  ペアを消費してから幅を知るので、ペアの手前で折る。差は常に1文字
- **RTL は旧経路にフォールバックする。**`resolveVisualText()` が bidi 並べ替えを
  行うため、前進スキャンのオフセットが logical 位置に対応しない。
  RTL 行のみ O(n²) のまま

#### 折り返し位置の決まり方 — **禁則処理は無い**

超えたときに返すのは2つのうちどちらか:

```cpp
if (preferSpace && lastFittingSpace > 0) return lastFittingSpace;
return lastFittingOffset;     // 直前のコードポイント境界
```

- **英語**: 半角スペース位置を優先する
- **日本語**: スペースが無いので `lastFittingOffset` に落ちる。
  つまり**任意の文字境界で折る**

**したがって、いまの横書き日本語でも `。` や `」` が行頭に来る。**

#### ⚠️ 禁則処理は存在する。ただし EPUB 側

`lib/Epub/Epub/ParsedText.cpp:62-122` に実用水準の実装がある
(2026-10-21 に確認)。

```cpp
bool isNoBreakBeforeCjkPunctuation(uint32_t cp);  // 行頭禁則: 、。」』】）！？ 全36文字
bool isNoBreakAfterCjkPunctuation(uint32_t cp);   // 行末禁則: 「『【（〈《 全18文字
bool hasCjkBreakOpportunityBetween(uint32_t leftCp, uint32_t rightCp);
std::vector<size_t> cjkCharacterBreakByteOffsets(const std::string& text);
```

全角・半角の両方を網羅しており、述語は純粋な `switch` で状態を持たない。
`utf8IsCjkBreakable()` は既に共有ヘッダ `lib/Utf8/Utf8.h:29` にある。

**ただし `namespace { }` の中にある** (同ファイル L18-263)。翻訳単位の外から
呼べないので、**共有ヘッダへの抽出が必要**。機械的な移動で済む。

> **TXT に禁則を入れるなら、縦書きとは独立に、横書きにも効く改善として
> やるべきである。**縦書き固有のコストではない。

#### `wrappedText()` との違い

| API | 折り返し | 切り詰め | クランプ |
|---|---|---|---|
| `findWrapOffset` | **文字境界** (日本語可) | — | — |
| `wrappedText` | **半角スペースのみ** | あり (`…`) | — |
| `truncatedText` | — | あり (UTF-8 対応) | — |
| `drawCenteredText` | なし | なし | **なし** (画面外にはみ出す) |
| `BaseTheme::drawPopup` | なし | なし | **なし** (`w` が画面幅超で `x` が負に) |

**`wrappedText()` は依然スペース専用である。**ボタンヒントの溢れ (§6.9) と
上流 Issue #2949 はこれが根。**`findWrapOffset()` がそのまま使える** (§9.2)。

## 5. フォーク設計

### 5.1 フォントアーキテクチャ — **UI固定 / 本文可変**

**設計の中核。上流がクローズした理由をそのまま解決する構造。**

| 用途 | フォント | 配置 | 理由 |
|---|---|---|---|
| **UI 文字列** | 日本語サブセットを**焼き込み** | Flash | フォント未設定でも日本語UIが成立する。「読めないUIから抜け出せない」事故が原理的に起きない |
| **本文** | ユーザーが選ぶ SD フォント | SDカード | 好みの書体で読めるべき。明朝/ゴシックの選択は読書体験の核心 |
| **ファイル名・書名** | **本文フォント**を使用 | SDカード | 何の文字が入るか事前に決定できないため、サブセットでは足りない |

#### なぜこれが唯一の解なのか

**上流の言語受け入れ基準は「非ラテンか否か」ではなく「UIフォントに字形があるか」。**

ヘブライ語 (#2068) とアラビア語 (#2599) の UI 翻訳が受け入れられたのは、
UI フォントに字形が同梱されているため。キリル4言語 (RU/UK/BE/KK) も同様。
**CJK だけが一切含まれない** (§3.6)。

(`truncatedText()` の省略記号)。

> A-1 の調査では、**翻訳ファイルに現れない非 ASCII は4字だけ**だった
> (`…` `«` `»` `°`)。数字・`%`・`/`・`:`・`.`・`-`・`MB`・`KB` はすべて ASCII 95字に含まれる。

#### 常用漢字まで焼かない判断

数値上は成立する (+1,906字 / 546 KB)。**それでも採らない。**

**常用漢字では書名・人名を救えない。**実例として『最終戦争論』の著者
「石原莞爾」の **莞・爾はいずれも常用漢字ではない。**中途半端に広げると
「たいてい出るが時々出ない」という最も分かりにくい状態になる。
**ファイル名・書名は本文フォント経由**という線引きを守る。

### 5.2 対応言語の削減

**英語 + 日本語のみを残す。**

| 言語 | 扱い | 理由 |
|---|---|---|
| 英語 | **必ず残す** | フォント破損時・想定外事態の避難先。消すと復旧手段を失う (§2.6) |
| 日本語 | 主対象 | — |
| その他30言語 | 削除 | 日本語版フォークに不要。Flash を UI フォントに回す (**323 KB**) |

### 5.3 配布形式

**`.bin` のみ。**

USBロック品でもロック無しでも、SD 経由なら**同じ手順が使える**。
分岐が無いことが利点。逆 (USB 前提) はロック品を排除してしまう。

**この方針が2つの判断を決めた:**

- CP932 変換表を SD に置かず Flash に焼いた (§6.2)。置き忘れで青空文庫が
  黙って読めなくなる事故を避ける
- UI フォントを Flash に焼く (§5.1)。同型の事故を避ける

配布物: `update.bin` / 導入手順書 (日本語主体) / 推奨する本文用フォントの案内。
**UI フォントを焼き込むため、フォント一式の同梱は必須ではない。**

### 6.2 【F-3】TXT の文字コード自動判別 (Shift-JIS)

**何を**: Shift-JIS の `.txt` を初回オープン時に UTF-8 へ変換し、
キャッシュに置く。**リーダー本体には一切手を入れていない。**`Txt` が
「読むパス」を差し替えるだけで、下流から見れば最初から UTF-8 のファイルになる。

**なぜ**: **青空文庫のテキストは Shift-JIS。**日本語ユーザーは全員当たる。
放置すると `◆?` と半角英字の交互で文字化けする。

| タイミング | 走る処理 | コスト |
|---|---|---|
| 初回オープン | 判定 (先頭4KB) + 変換 (8KB ずつストリーミング) | 1〜2秒 |
| 2回目以降 | 何も走らない | **ゼロ** |

**1行ずつ変換する方式は採らなかった。**開くたびに負担が乗るうえ、変換で
長さが変わるため `pageOffsets` と F-2 の `markOffset` が壊れる。

#### 判定の順序

1. BOM `EF BB BF` → UTF-8 (BOM は変換時に除去)
2. BOM `FF FE` / `FE FF` → UTF-16。**対象外。**変換しない
3. 全バイトが 0x80 未満 → ASCII。変換しない
4. 厳密な UTF-8 妥当性検査に通る → UTF-8。変換しない
5. Shift-JIS として妥当 → Shift-JIS
6. どちらでもない → UTF-8 とみなす (現状維持)

実際の日本語 Shift-JIS は先頭バイトが 0x81-0x9F に集中し、これは UTF-8 では
継続バイトなので単独では現れない。**UTF-8 を先に試す判定は十分に堅い。**
UTF-8 検査は overlong・サロゲート・U+10FFFF 超も弾く (Shift-JIS を誤読したときに
出る形のため)。

#### 変換表

`scripts/gen_cp932_table.py` が `lib/Utf8/Cp932Table.h` を生成する。
Python の組み込み `cp932` コーデックのみを使い、外部データの取得は不要。

| 項目 | 値 |
|---|---|
| エントリ | 11,340 (定義済み 9,604) |
| **サイズ** | **22,680 B (22.1 KB)** |
| 引き方 | 減算2回とインデックスのみ。**探索なし** |

定義済み 9,604 の内訳は JIS X 0208 6,879 + NEC特殊文字 83 + NEC選定IBM拡張 374 +
IBM拡張 388 + 外字領域 1,880。CP932 として過不足がないことを Python で検算済み。

> **表を SD に置かない判断 (記録)**
> 速度は一括ロードで解決できるが、`.bin` のみの配布 (§5.3) が崩れ、
> 表の置き忘れで青空文庫が黙って読めなくなる。規模もフォント1個の 1/300。
> **フラットな表は「Flash を使って CPU を買う」選択**であり、低速な端末では正しい。

**実測**: Flash **+25,290 B** (表 22,680 B + コード約 2,600 B)。RAM (静的) ±0。
`test/encoding_detect/` に判定と変換のテストを追加 (11ケース)。

### 6.3 【F-2】Markdown チェックボックス トグル

> **設計メモ 2本 (`f2-markdown-checkbox.md` / `f2-checkbox-investigation.md`) は
> 本節と §8 に全件移送して削除した。**`git log --all -- docs-jp/f2-*.md` で辿れる。

**何を**: `.md` 内の `- [ ]` を端末上で `- [x]` にする。電源ボタン短押しで
トグル、側面ボタンでチェックボックス間を移動。**SD 上のファイルに1バイトだけ
書き戻す。**

**なぜ**: **プロジェクトの原点。**スマホで作った TODO を端末で消化する。
上流ではスコープ外が確定している (`SCOPE.md` の「No typed notes, journals,
or editors」、`ROADMAP.md` の「Writing / authoring tools」。さらに ROADMAP に
**「But it was on the old roadmap is not a valid argument」**と明記)。

#### 中核となる設計上の性質

**`- [ ]` と `- [x]` はファイル長が変わらない。**差分は角括弧内の1バイトのみ。
したがってバイトオフセットも索引キャッシュも無効化されない (§4.3)。
**ファイル全体を RAM に載せる必要もない。**

#### 確定した仕様

| ボタン | チェックボックスがあるとき | 無いとき |
|---|---|---|
| **電源・短押し** | **トグル** (設定が「チェック切替」のとき) | 何も起きない |
| **側面** | 次/前のチェックボックスへ | 通常のページ送り |
| 前面4つ | ページ送り・戻る | 同左 |

**原則: カーソルが実際に動くときだけ消費する。**状態ではなく**結果**で決める。
チェックボックスが0個/1個、末尾で「次へ」、先頭で「前へ」のときは消費せず
ページ送りに渡す。**死んだボタンを作らないための規則。**「押しても何も起きない」は
ユーザーには故障と区別が付かない。

マーカーは **ASCII の `>`**。`▶` (U+25B6) は組み込みにも SD の `cjk` にも無い
(§3.6)。**`>` は ASCII なので、チェックボックス記法 `- [ ]` 自体が描画できて
いればマーカーも必ず描画できる。論理的に破綻しない。**

検出は正規表現を使わない手書き:
`先頭の ' ' / '\t' を読み飛ばす → '-' / '*' / '+' → ' ' → '[' → ' ' / 'x' / 'X' → ']'`。
`]` の後は問わないので `- [ ]の直前に…` のように直後が日本語でも正しく検出される。

設定項目は `SHORT_PWRBTN::CHECKBOX = 5` を **enum の末尾に**追加
(`settings.json` に index で永続化されるため。途中挿入は既存設定を黙って
別物に解釈させる)。

#### 描画コスト (実測)

TXT 1ページの描画は定常状態で **1591 ms**。内訳:

| 処理 | 実測 | トグル時 |
|---|---|---|
| txt_load_page | 233 ms | 省略可 (要フラグ) |
| **txt_prewarm** | **269 ms** | **省略不可** |
| txt_scan_pass | 1 ms | prewarm と一体 |
| txt_bw_draw | 50 ms | 全行必要 |
| txt_aa | 422 ms | 省略可 |
| **txt_eink** | **548 ms** | **省略不可 (物理時間)** |
| txt_save_progress | 63 ms | 省略可 |

**トグル時の現実的な下限は約 870 ms** (269 + 50 + 548)。

> **v0.5 まで記載していた「1591ms → 100ms 程度」は誤りである。**
> `txt_prewarm` を省略できないのは、`renderPage()` の描画スコープの
> destructor がフォントキャッシュを破棄するため。飛ばすと全グリフがミスし、
> F-6 で潰したスラッシングが再発する。

**実機では「快適。ページ送りと同程度で引っかかりなし」**だったため、
最適化の優先度は当初より下がった。

**実測**: Flash **+2,142 B**。RAM (静的) **±0** (追加した状態はすべて
インスタンスメンバ = ヒープ)。

#### 実機で確認できたこと

記法のゆれ (`-` / `*` / `+`) / インデント (スペース・タブ) / `[x]` `[X]` の検出 /
**偽物の除外** (`-[ ]` / `- []` / `- [y]` / `[ ]` はいずれも素通り) /
カーソルの着地点 (前方から入れば先頭、後方から入れば末尾) /
**ファイルへの書き戻し** (PC で開き直して確認) / 総ページ数が変わらないこと。

`docs-jp/tests/f2-test.md` に確認用の `.md` がある。
**節 6-d が幅の正規化の本当の検証** (6-b / 6-c は検証にならない)。

#### 既知の残り (判断済み)

| # | 内容 | 判断 |
|---|---|---|
| 1 | `- [ ]` が単独で1行を占める | 既存の折り返しが `]` の後ろのスペースで折るため。1行分の無駄で壊れてはいない。**優先度低** |
| 2 | 未トグルの `[X]` 行が右に数px はみ出す | 幅の正規化の代償 (§8.1)。トグルすれば解消。**許容** |
| 3 | **最終ページで「次へ」を押すとホームに戻る** | 最終ページにチェックボックスが無い場合、例外処理が発動しない。**現状維持と決定** |
| 4 | トグルがリフレッシュ周期を消費する | `displayWithRefreshCycle` が N 回に1回 `HALF_REFRESH` を使う。**妥当** |

**#3 を現状維持にした理由**: 進捗は毎回の描画で保存されるので開き直せば戻る。
「本文の終わりまで来たら閉じる」はページ送りだけで使っていたときと同じ挙動。
ここを塞ぐと「最後まで来たのに閉じられない」という別の不便が生まれる。

### 6.4 【F-6】日本語UIの描画性能

**何を**: `SdCardFont.h` の `OVERFLOW_CAPACITY` を 8 → **128**。

**なぜ (計装による実測で確定)**:

```
CJK文字を含む文字列 → SDフォントへ経路変更 (resolveTextFontId)
  → UI経路には prewarm が存在しないため interval 表が空
    → 全グリフが必ずミス
      → 1グリフごとに openFileForRead + 2 seek + 2 read
        → キャッシュは overflow リング 8スロットのみ
```

**システムタブだけが収束しない理由**: 異なり字数 91 > リング容量 8。
古典的なスラッシング。

**実測**:

| | cap=8 (元) | cap=64 | cap=128 |
|---|---|---|---|
| グリフミス | — | 82 | **0** |
| ヒット率 | — | 80% | **100%** |
| SD I/O | — | 949 ms | **0 ms** |
| **フレーム総時間** | 1546 ms | — | **577 ms** |

577 ms = E-Ink 転送 548 ms + 計算 29 ms。**物理限界に到達。**

#### 誤っていた仮説 (記録として残す)

| 仮説 | 結果 |
|---|---|
| フォントファイルが大きいから遅い | **誤り。**8/10pt を 97.5% 削減しても改善せず |
| `truncatedText` の O(n²) が効いている | **誤り。**全41フレームで `truncate_loop entered=0` |
| 行数が多いから遅い | **誤り。**異なり字数がリング容量を超えているため |

> **UI サブセット焼き込み後も cap=128 は維持する。**§5.1 の設計では UI 文字列が
> SD 経路を通らなくなるので F-6 の問題自体が UI からは消えるが、
> **ファイル名・書名は本文フォント (SD) 経由**のままなので、リング容量の問題は
> ファイルブラウザ等に残る。

### 6.5 【F-7】TXT の折り返しを O(n) にする

**何を**: `GfxRenderer::findWrapOffset()` を新設し (§4.4)、
`loadPageAtOffset()` の折り返しループを置き換えた。
加えて**段階A**として、索引構築中はファイルを開き直さないようにした。

**なぜ**: 折り返しループが候補位置ごとに `line.substr(0, breakPos)` を作って
**最初から測り直していた。**400文字の段落なら約370反復 × 平均215文字。
加えて `line = line.substr(skipChars)` が O(n²) の memcpy を生んでいた。

上流 Issue #2650 は空席 (修正 PR #2158 は著者が自己クローズ)。**フォークで修正した。**

段階A のスコープを `buildPageIndex()` に限定した理由:
**F-2 の書き戻しが同じファイルを `O_RDWR` で開く。**セッション全体で保持すると
衝突しうる。索引構築とトグルは同時に起きない。

#### 実機での等価性検証

**折り返しの結果が変わらないことを、旧実装と突き合わせて確認した。**
シリアルが使えないため結果は `/wrap-verify.txt` に書き出した (§3.7)。

| ファイル | 行数 | 不一致 | old | new | speedup |
|---|---|---|---|---|---|
| 英語 (組込フォント、切れ目なしトークン) | 304 | **19** | 10,792 ms | 59 ms | **180.3x** |
| 日本語 (SD フォント、チェックボックス含む) | 237 | **0** | 206 ms | 16 ms | 12.5x |

**19件の不一致はすべて同一原因**で、リガチャペア (ﬀ / ﬁ / ﬂ) の中間が
折り返し位置に来たケース。**差は常に1文字。**

**新実装を採用した。**リガチャの分断は組版として不正ではなく、発生条件
(組込フォント かつ 1行に収まらない語) も稀。日本語は SD フォント経路に
リガチャが無いため影響ゼロ。

**`CACHE_VERSION` を 4 → 5 に上げた。**折り返し結果が変わりうるため。

#### 実測 (112 KB / 217ページ)

| 段階 | 初回オープン |
|---|---|
| F-7 前 | **約 7分** |
| F-7 後 | 約 45秒 |
| **段階A 後** | **約 15〜20秒** |

**通算 約25倍。**そして計算量が O(n²) から O(n) になったことが本質で、
1MB 級のファイルでも数時間から約2分になった。

Flash +802 B (F-7) / +282 B (段階A)。RAM ±0。

#### 段階A の後に残っていたコスト

折り返しはもうボトルネックではない。15〜20秒の内訳は概算で:

| 処理 | 217ページ分 |
|---|---|
| `ensureSdCardFontReady()` (70 ms/回) | **約15秒** |
| seek + 8KB 読み | 約4秒 |
| 折り返し | ほぼゼロ |

**8KB 読んで1ページ分 (日本語で約900 B) しか使っていない**ため、約9倍の
重複がある。→ F-9 がこれを体感から消した。

- 凡例ブロックは「記号を使わないですむ場合は、入れる必要はありません」と
  定められている。**記法を使う本には必ず入り、使わない本には入らない。**
  適用判定の根拠として十分に堅い
- 外字注記は4形式ある。**U+ を持つのは1つだけ**
  (面区点 / Unicode / Unicode未掲載 / 特殊な仮名・記号)
- **"※《" のようなエスケープ規則は仕様に存在しない。**
  "※" は "※［＃" の形でのみ意味を持つ
- **"／＼" "／″＼" (二倍の踊り字) は注記ではなく本文の文字。**
  凡例に載っているため誤認しやすい

#### 実装の要点

| 要点 | 理由 |
|---|---|
| **凡例の範囲は `prepareEncoding()` で先に確定する** | 走査しながら罫線を見て決めると、**閉じ罫線を欠いたファイルで本文を丸ごと食う** |
| 罫線は ASCII ハイフン10個以上の連続で探す。**両方そろわなければ凡例除去を一切やらない** | 片方だけで判断すると範囲が暴走する |
| 判定は**変換後 (UTF-8) に対して**行う | 記法は全角文字で書かれており、Shift-JIS のまま照合すると表記が揺れる |
| **チャンク境界の持ち越しは「記法の開始位置」から** | `《` だけ読んで `》` が次チャンクにある場合、開始位置から持ち越さないと記法が本文として出る |
| 走査は独立したオブジェクト | **段階2 はルビを捨てずに保持する。**同じ走査を違う出口で再利用する |

**記法の実測** (石原莞爾『最終戦争論』/ 112,650 B / Shift-JIS):

### 6.7 【F-9】ページ索引の遅延構築と読書位置のオフセット化

> **詳細設計は `docs-jp/f9-lazy-page-index.md` v0.3。**
> **v0.7 にはこの節が存在しなかった。**

**何を**: 2段階で実装した。

| | 内容 | コミット |
|---|---|---|
| **フェーズ1** | 読書位置をページ番号から**バイトオフセット**に変える | `b6edc24f` |
| **フェーズ2** | 索引を一括構築せず、**助走16ページの後 `loop()` から1ページずつ**進める | `f561b5fd` |

**なぜ**: 112 KB の本で初回オープンに 15〜20 秒、1 MB なら約2分かかっていた。
**そしてページ番号は全ページを数え終わらないと意味を持たないため、
遅延構築そのものを阻んでいた。**

#### フェーズ1: 位置をオフセットで持つ

```cpp
size_t currentOffset = 0;        // 正本
int currentPage = 0;             // 導出 (表示用)
std::vector<size_t> offsetHistory;   // 最大16件 (§4.3)
```

**副産物: 既存の不正確さが直った。**フォントサイズを変えると全ページが
振り直されるため、保存済みのページ番号は別の場所を指していた。
オフセットなら指す場所が変わらない。

**キャッシュ無効化時に1ページ目から始めない。**`saveProgress()` は描画の
たびに走るため、1ページ目から始めるとその瞬間にしおりが消える。
**フォントサイズの変更でキャッシュは日常的に無効化される。**

#### フェーズ2: 1ページずつ進める

```cpp
bool advanceIndex(int maxPages);              // n ページ追加して返る
static constexpr int INDEX_WARMUP_PAGES = 16; // 助走。ページ数で縛る
bool indexComplete = false;
size_t indexBuildOffset = 0;      // どこまで作ったか
size_t currentPageNextOffset = 0; // 表示中のページがどこで終わるか
```

**4つの規則が位置と索引の関係を決める:**

1. **開くときは、索引が `currentOffset` を覆っている場合だけページ先頭に吸着する。**
   覆っていなければ (助走が届かない深い再開) オフセットをそのままにする
2. **索引が完成したとき吸着しない。**その時点で読者は読んでいる。
   吸着すると本文が動く (`d5e0ed91` で直した欠陥の再発)。`currentPage` だけ再計算する
3. **前進は常に `currentPageNextOffset` を使い、索引を見ない。**
   未索引の先へ歩けて、グリッドに引き戻されない
4. **後退は `offsetHistory` を優先する。**実際に歩いた経路なので、
   グリッド上かどうかに関わらず正確

**未構築範囲へのナビゲーションは拒否する** (「読込み中」を1回だけ出す)。
これは当初「総数が分からなければ位置ジャンプに意味がない」という理由で
決めたが、**実測により §8.4 の事故を構造的に防ぐ決定でもあったことが分かった。**

**助走の直後に1回だけ `reserve()` する。**助走後は `indexBuildOffset` と
`pageOffsets.size()` が揃うので1ページあたりの平均バイト数が求まる
(ステータスバーの推定と同じ式)。それ以前は平均が求まらない。
ガードは **0除算 / 平均が異常に小さい (`MIN_AVG_BYTES_PER_PAGE = 64`) /
異常に大きい (`INDEX_RESERVE_MAX_PAGES = 4096` = 16 KB) / 助走中に完成した場合**。

**`skipLoopDelay()` で省電力を抑止する** (§3.4)。これが無いと CPU が 10 MHz に
落ちて構築が約10分かかり、入力も壊れる。

**ティックは `RenderLock` の下で回し、`peek()` が真なら飛ばす** (§8.5)。

#### 実機での等価性検証

遅延構築した索引と一括構築した索引を全件比較し `/index-verify.txt` に出した。

```
lazy pages: 211   oneshot pages: 211   first mismatch: none   INDEX OK
lazy pages: 123   oneshot pages: 123   first mismatch: none   INDEX OK
```

**2種類のレイアウトで、ページ境界が全件一致。**検証後にコードを撤去した。

### 6.8 入力のラッチ (`010c4603`)

**何を**: `MappedInputManager` が物理ピン単位で押下・解放をラッチする (§3.2)。

**なぜ**: `InputManager` は差分方式でイベントを溜めない。**背景で何かを
進める以上、ループの1周は必ず伸びる。**EPUB の計測では盲目時間が
平均 477 ms / 最大 957 ms で、人の押下 (100〜200 ms) を丸ごと飲んでいた。

**ラッチが無ければ、TXT でも「索引構築中はボタンが効かない」が確実に起きた。**
F-9 フェーズ2 はこの上に立っている。

**実装の判断**:

- **物理ピン単位。**論理ボタンで持つと設定によって二重計上・取り落としが起きる
- **1500 ms で期限切れ。**最悪の盲目時間 (957 ms) を跨げる長さで、
  かつ押下が意図した画面より長生きしない長さ
- **アクティビティ遷移で全破棄。**前の画面に向けた押下が次の画面で発火しない
- `switch` は全 `Button` を明示的に列挙する (`default:` を書かない)。
  **`-Wswitch` を番人として残すため**
- **`getHeldTime()` はラッチしない。**「いま押されているか」は別の問いであり、
  古いエッジから答えるのは誤り

**撤去したもの**: 計測用の計装は commit 前に削除した。
ティックの粒度は 2 → **1ページ**に下げた (§8.4)。

### 6.9 ステータスバーと表示の修正

#### ページカウンタの桁揺れ (`fa623971`)

**何を**: パーセント表示の幅が変わってもページ番号が動かないよう、
「100%」分の枠を予約する。

**なぜ**: 1桁 → 2桁 → 3桁と進むにつれてページ番号が左右に揺れ、

#### 推定表示の翻訳キー化 (`4187ac93`)

**何を**: 索引が未完成のときの推定マーカーを `STR_ESTIMATE_PREFIX` にした
(英語 `~` / 日本語「推定」)。**独立した `drawText` として描く。**

**なぜ**: ハードコードした記号は翻訳できない。また、ページ番号の文字列に
連結すると桁揺れ対策 (上記) が壊れる。

> **この1件が UI フォントの焼き込み対象を1字増やした。**「推」は A-1 の
> 230字一覧に無かった (§8.6)。

#### レイアウト変更後の位置再整列 (`d5e0ed91`)

**何を**: 索引キャッシュが拒否されたとき (= 設定が変わったとき)、
復元した位置をページ先頭に吸着させる。**`STR_REINDEXING` で再索引を予告する。**
併せて `indexCacheRejected` が真のとき**履歴を最新1件に切り詰める。**

**なぜ**: 保存されたオフセットは、書かれた時点のレイアウトではページ境界
だった。索引が作り直されるとページの途中を指すことになり、そこから描いて
次のページへ進むと**既に読んだ行が再び現れる。**

履歴を切り詰めるのは同じ理由。**末尾以外の15件は旧レイアウトの境界を指す。**
フェーズ2 が履歴を「前へ」に使い始めた瞬間に同じ重複が再発する。

- **総ページ数は、数えたバイト数から外挿**し「推定」を付す
- **パーセントはオフセットから計算するので、最初から正確**
- **索引の進捗では画面を描き換えない** (§8.5)。数値はページを送った時点の
  値で描かれる

### 8.1 折り返しに触るとき

> 出典: **F-7** (`3694c2b8`) / **F-2** (`616739bd`)

1. **`findWrapOffset()` はリガチャペア (ﬀ / ﬁ / ﬂ) の中間では折らない。**
   旧実装は折れた。前進スキャンはペアを消費してから幅を知るため、手前で折る。
   **差は常に1文字。**日本語 (SD フォント経路) は影響ゼロ
2. **`[ ]` / `[x]` / `[X]` をすべて `x` の幅として測る。**
   3状態は別のグリフなので描画幅が違う (明朝体で顕著)。放置すると、
   **トグルした行がちょうど1行に収まる境目にあったとき視覚行が1本増え、
   `pageOffsets[currentPage+1]` は固定なので、その差分のテキストがどのページにも
   表示されなくなる**
3. **`[X]` の補正は負の値になる。クランプしてはならない。**
   `advance('x') - advance('X')` は負である。0 で止めると `[X]` 行だけ
   測定が狂う。**補正はマークを含む区間 (`lineBytePos == 0`) にだけ加算する**
4. **基準は小文字の `x`。**トグルが書き込むのは `' '` か `'x'` だけで、
   `[X]` は他のエディタが作った一時的な状態。`X` 基準にすると全行が実際より
   広く測られ続ける。**代償は未トグルの `[X]` 行が右に数px はみ出すこと。既知・許容**
5. **`buildPageIndex()` と `render()` は同じ折り返しをしなければならない。**
   違う折り返しをすると「索引が想定したページの中身」と「実際に表示される中身」が
   ずれ、ずれた分はどこにも表示されない。
   **幅の正規化を `outCheckboxes != nullptr` の内側に置くとこれを踏む** —
   判定は `isMarkdown` なら両経路で行い、`vector` への push だけを
   `render()` 経路に限定する
6. **固定小数点のまま積む。**SD 経路は最後に1回しか `fp4::toPixel()` を呼ばない。
   ピクセル単位で足し込むと丸め誤差で結果が変わる
7. **`resolveTextFontId()` は文字列全体に対して1回だけ呼ぶ。**
   この関数は文字列全体を走査して CJK の有無でフォントを切り替えるため、
   走査位置ごとに呼ぶと途中でフォントが変わる
8. **RTL は旧経路にフォールバックしている。**`resolveVisualText()` の bidi
   並べ替えにより、前進スキャンのオフセットが logical 位置に対応しない。
   RTL 行のみ O(n²) のまま。**この分岐を消さないこと**
9. **折り返しの結果が変わったら `CACHE_VERSION` を上げる** → §8.2

### 8.2 キャッシュに触るとき

> 出典: **F-2** (`616739bd`) / **F-3** (`3639c847`) / **F-7** (`3694c2b8`)

#### `index.bin` の検証は8項目。**mtime もハッシュも無い**

magic / version / fileSize / viewportWidth / linesPerPage / fontId /
screenMargin / paragraphAlignment (§4.3)。

**折り返しアルゴリズムを表すものが1つも無い。**

#### ⚠️ `CACHE_VERSION` を上げるべきとき

**「格納形式が変わったとき」ではなく「格納内容の意味が変わったとき」も含む。**

実際に踏みかけた経路 (F-2):

1. マーカー欄の導入で `.md` の `viewportWidth` が縮む → キャッシュはその値で再構築
2. その後に幅の正規化を入れる → **`viewportWidth` は同じ値のまま**
3. → キャッシュが「有効」と判定され、**古い折り返しで作った `pageOffsets` が
   黙って再利用される**

| いつ | 対象 |
|---|---|
| **折り返しの結果が変わりうる変更** | `CACHE_VERSION` |
| 変換後の本文のバイト列が変わる変更 | `ENCODING_VERSION` (記法除去の有無など) |
| 進捗の格納形式が変わる変更 | `PROGRESS_VERSION` (ただし新旧はサイズでも判別している) |

> **代償**: `.txt` を含む全索引が1回再構築される。キャッシュは拡張子で
> 分かれておらず `/.crosspoint/txt_<hash>/` を共有しているため。112 KB 程度なら
> F-9 後は1〜2秒。

#### ⚠️ F-3 の sidecar 不変条件

**「sidecar が無い = まだ一度も正常に判定できていない」**

| 判定に至った経路 | sidecar |
|---|---|
| 空ファイル / UTF-8 / ASCII / 判定不能 / Shift-JIS 変換成功 | **書く** (結論に達している) |
| 読み込み失敗 / OOM / 変換失敗 / sidecar 書き込み失敗 | **書かない** (結論ではなく失敗) |

`encoding.bin` は必ず最後に書き、変換後サイズを `content.u8` の実サイズと
照合する。途中で失敗した場合は `content.u8` を削除する。
**中途半端なキャッシュを「有効」と誤認させない。**

> **この不変条件を曖昧にして一度踏んだ。**当初 sidecar を Shift-JIS のときだけ
> 書いていたため、**UTF-8 ファイルでは常に「未判定」と見なされ、開くたびに
> ポップアップと E-Ink リフレッシュ (約550 ms) が走り、Quick Resume も
> 毎回無効化されていた。**
>
> **「結論に達した」と「成功した」は違う。**「変換しないと決めた」も結論である。

#### ⚠️ 索引は部分的に保存してはならない

**`savePageIndexCache()` は `indexComplete` になってから呼ぶ。**
途中の `pageOffsets` を書くと、次に開いたとき「完成した索引」として読まれる。

#### 既知の制約

**sidecar とファイルを結びつけているのはサイズだけ** (`index.bin` と同じ規則)。
同じバイト数の別の文字コードのファイルに差し替えると、記録された判定のまま
読まれる。**ファイルを移動・改名するとハッシュが変わり、位置と索引を失う** (§4.3)。

### 8.3 入力に触るとき

> 出典: **F-2** (`616739bd`) / **入力のラッチ** (`010c4603`) / **F-9** (`f561b5fd`)

1. **`InputManager` は差分方式。イベントは溜まらない** (§3.2)。
   `update()` の呼び出し間隔より短い押下は、原理的に存在しなかったことになる
2. **⚠️ ラッチはサンプルされなかったエッジを作り出せない。**
   長い1周をまたいで届けるだけである。1周が押下時間より長くなったら、
   直すのは**1周の長さ**であってラッチではない (§8.4)
3. **`ReaderUtils::detectPageTurn` は既定では「押し下げ」で発火する。**
   `longPressButtonBehavior` の既定値は `OFF` で、そのとき `wasPressed` を使う。
   **自分の処理で `wasReleased` を使うと、指を離す前にページが送られて
   処理に永遠に到達しない。**同じ規則に揃えること:

   ```cpp
   const bool usePress = SETTINGS.longPressButtonBehavior == SETTINGS.OFF;
   const bool sideNext = usePress ? mappedInput.wasPressed(Button::PageForward)
                                  : mappedInput.wasReleased(Button::PageForward);
   ```

4. **`Button::Up` / `Down` ではなく `PageBack` / `PageForward` を使う。**
   `Up`/`Down` は `sideButtonLayout` 設定を素通りする。`PageBack`/`PageForward` なら
   **`SIDE_BUTTONS_DISABLED` の尊重と `NEXT_PREV` の向き反転が自動で効く**
5. **ピーク用メソッドはガード専用。**`wasReleasedPeek()` はラッチを消さない。
   「別のボタンも離されたなら飛ばす」のように、エッジの所有権が次の処理にある
   場合だけ使う。通常の入力処理に使うと次の周でもう一度発火する。
   **`wasPressedPeek()` は作っていない** — 必要になっていないものを増やさない
6. **`isPressed()` / `getHeldTime()` はラッチしない。**
   「いま押されているか」「どれだけ押されているか」は別の問いであり、
   古いエッジから答えるのは誤り
7. **画面が変わったらラッチを捨てる。**`clearLatches()` を
   Replace / Push / Pop復帰 / 即時開始の4経路すべてで呼ぶ
8. **`switch` に `default:` を書かない。**全 `Button` を明示的に列挙して
   `-Wswitch` を番人として残す。ボタンが増えたときにコンパイラが教えてくれる
9. **SDK の `beginAsync()` は使えない。**理由3点は §3.2。
   **毎回調べ直さないこと**

### 8.4 `loop()` に重い処理を入れるとき

> 出典: **F-9** (`f561b5fd`) / **EPUB の計測** (`dba979f6`)

#### ⚠️ 1周を長くすると入力が壊れる

**入力は1周に1回しかサンプルされない** (§3.2)。1周が押下時間 (100〜200 ms) を
超えると、押下が消え始める。**ラッチでは救えない** (§8.3-2)。

**実測の目安**:

| 1周の長さ | 結果 |
|---|---|
| 〜100 ms | 問題なし |
| 477 ms (EPUB 2ページ/ティック) | **押下が飲まれる** |
| 1.3〜2.8 秒 (省電力に落ちた TXT) | **完全に効かない** |

**対処**: ティックの粒度を1単位に下げる。EPUB は 2 → 1ページで
**477 ms → 176 ms** になった。TXT は 1ページ 70〜90 ms なので
**1ページ/ティックなら 100 ms 未満**に収まる。**最初から1単位で進めること。**

#### ⚠️ 省電力に落ちると CPU が 10 MHz になる

3秒間操作が無いと `LOW_POWER_FREQ = 10 MHz` に落ち、`delay(50)` も加わる
(§3.4)。**1ページ 80 ms が約 1.3 秒になる。**

```cpp
bool skipLoopDelay() override { return !indexComplete; }
```

**背景で何かを進めている間だけ抑止する。**終わったら戻す。
**これを忘れると「索引が完成しない」「ボタンが効かない」が同時に起きる** —
症状が2つに見えるが原因は1つである。

#### ⚠️⚠️ `loop()` に戻らない同期ループを作らない — **最重要**

EPUB の計測2行目 (`ticks=0 / syncCalls=25`) は、**背景ティックが一度も走らず、
207ページ全部を `render()` 内の `while` が作った**という意味である。

```cpp
while (!section->isBuildComplete() &&
       (... : static_cast<int>(section->pageCount) <= target)) {
  section->buildSomeMore(BUILD_PAGES_PER_CHUNK);
}
```

**この 48 秒間、`loop()` に戻らないため `gpio.update()` が一度も呼ばれない。**
**ラッチがあっても救えない。**入力が到達する経路そのものが動いていない。

該当は「保存位置まで一気に組版する」経路。章の終盤で閉じた本を開き直すと発動する。

> **TXT では「未構築範囲へのナビゲーションを拒否する」という決定が、
> この事故を構造的に防いでいる。**当初は別の理由 (総数が分からなければ
> 位置ジャンプに意味がない) で決めたが、**実測により二重の意味があったことが
> 分かった。**この決定を緩めるときは §8.4 を読み直すこと。
>
> **EPUB 側の同期ループは未対処。**F-9 の範囲外として明示的に延期した。

#### ティックの位置はボタン検出の**後**

EPUB の `loop()` では組版ティックがボタン検出の約200行**手前**にあり、
毎周ボタンを読む前に待たされる。

**TXT では最初からボタン検出の後ろに置いた。**ゼロコストで、盲目時間が
「次の周まで」から「同じ周のうち」に変わる。

#### ヒープ

**1ページごとの `malloc(8193)` / `free` は CLAUDE.md の
「ループ内での反復確保を避ける」に該当する。**F-9 以前からある挙動だが、
構築が `loop()` に分散したことで**他の確保と交互**になり、断片化の条件は
悪化している。アクティビティ寿命で1本持つのが素直 (§7.5)。

**TXT に EPUB のようなヒープゲートは入れていない。**理由:

- **定常増加は1ページ4バイト** (211ページで 844 B)。DRAM 残 203 KB に対して
  問題にならない
- 一時使用量のピーク (8 KB + 行の `vector` 2〜3 KB) は**通常のページ描画と同額。**
  これが確保できない状況なら索引を止めても本文が描けない。
  **見張りを入れても何も救えない**
- フェーズ2 はピーク使用量を変えていない。1ページずつに分割しただけ

**EPUB は性質が違う。**章ごとにレイアウト構造を**長期保持**で積み上げるため
ゲートが必要である。

### 8.5 描画に触るとき

> 出典: **F-9** (`f561b5fd`) / **F-2** (`616739bd`)

1. **`render()` は別タスクで走り、`RenderLock` 保持下にある** (§3.3)。
   `loop()` は保持していない
2. **⚠️ 索引の進捗で再描画しない。**E-Ink の全画面書き換えは約 1.7 秒。
   1ページごとに呼ぶと構築が数分に伸び、**描画タスクが `RenderLock` を占有して
   入力が届かなくなる。**索引が進むだけでは何も描かない。
   数値はページを送った時点の値で描けばよい。
   **完成時の1回だけは `requestUpdate()` してよい** (「推定」が消えるため)
3. **共有する配列とファイルハンドルを `RenderLock` で守る。**
   `render()` が `pageOffsets` を読む箇所は5つある:
   `empty()` 判定 / `currentPage >= totalPages` のクランプ /
   `currentOffset = pageOffsets[currentPage]` の種まき /
   **`pageForOffset()` の `std::upper_bound` (配列全体を走査)** /
   `renderStatusBar()` 経由の `size()` / `back()`。
   **`push_back` の再確保は配列を動かす。**同時に読まれると壊れる。
   **逐次読み込みハンドルも共有している** — 片方が seek すると他方が別の場所を読む
4. **ロックは待たずに飛ばす。**`RenderLock::peek()` が真ならティックを飛ばし、
   次の周に回す。**待つと入力が止まる。**
   `peek()` と取得は原子的でないので、**取得後にもう一度条件を確認する**
5. **`requestUpdate()` を `RenderLock` の中で呼ばない。**
   `requestUpdateAndWait()` なら確実に詰む
6. **`render()` 内で状態を無条件に初期化しない。**
   `render()` は毎回走る。カーソル移動は `requestUpdate()` → `render()` を呼ぶので、
   無条件初期化は**インクリメントした直後に自分で打ち消す。**
   どのページのものかを覚える (`checkboxPageStamp`)
7. **`render()` は毎回 `loadPageAtOffset()` を呼ぶ。**
   「`currentPageLines` が残っている」前提は成り立たない。省略するにはフラグが要る
8. **`txt_prewarm` を飛ばさない。**描画スコープの destructor がフォント
   キャッシュを破棄するため、飛ばすと全グリフがミスして F-6 のスラッシングが再発する
9. **⚠️ 診断コード自身の副作用を疑う。**F-9 の検証コードは `RenderLock` を
   15〜20秒保持し、「索引構築中に開閉を繰り返すと固まる」という
   **検証コード由来の症状**を生んだ。本番版では再現しなかった。
   **検証結果を信じるための検証なので、ここを潰しておく必要がある**

#### ⚠️ 行を手で積むとき

> 出典: **ボタンヒントの2行化** (`wrappedText` の修正で露出)

10. **⚠️ ボタンヒントの枠の下端 (y = 800) は画面の下端である。余白がゼロ。**
    `boxTop = pageHeight - buttonHintsHeight` で `boxHeight = buttonHintsHeight`
    なので、枠の下端がちょうど画面の下端になる。
    **1 px でも溢れると、枠線で切れるのではなく画面の外に出る。**
    枠内に収める処理は描画側で閉じること

11. **⚠️ UI_10 の 2 行は 40 px の枠に物理的に入らない。**
    `2 × ascender = 2 × 20 = 40` が `boxHeight` と**同値**で、`lineGap` と
    上余白の分がない。`lineY = max(1, (boxHeight − block) / 2)` の下限 1 px も
    乗るので、**行間をどう詰めても入らない** (負の行間 = 行の重なりが必要)。
    2 行が必要な場面では **SMALL へ降格する** (`2 × 18 + 2 = 38 ≤ 40`)

12. **⚠️ 測るフォントと描くフォントが違う。**
    行送りを `getTextHeight(fontId)` で決め、`drawText` が
    `resolveTextFontId()` の返す SD フォントの ascender でベースラインを置くと、
    **CJK でだけ両者がずれる。**行を手で積むなら
    **`getTextAscender(fontId, text, style)`** を使う (§3.6)。

    判定式は **`2 × ascender + lineGap ≤ boxHeight`** (ベースライン形)。
    **`UDEVGothic` の実測では UI_10 面 `2×20+2 = 42 > 40` で不成立、
    SMALL 面 `2×16+2 = 34 ≤ 40` で成立** (§3.6)。
    **descender を足した厳密形は過剰である** — フォントの `descender` は
    全グリフの最大値でラテンの `g` `p` `y` が作る値であり、
    仮名・漢字はベースラインより下に墨を置かない。
    厳密形では SMALL も不成立になり、**実機で Lyra が 2 行を描けている事実と
    矛盾する。**ただしラテンを含む 2 行ラベルが現れたら最大 4 px はみ出す

#### ⚠️ 上余白の下限は 0 でなければならない (`ed50e4c0`)

`lineY = boxTop + max(0, (boxHeight − block) / 2)`。**`max(1, …)` ではない。**

降格先フォントの ascender を `a` とすると:

| `a` | `2a+2` | `twoLinesFit` | `block` | `(40−block)/2` | `max(1,…)` のBL | `max(0,…)` のBL |
|---|---|---|---|---|---|---|
| ≤ 18 | ≤ 38 | 成立 | ≤ 38 | ≥ 1 | 枠内 | **同じ値。差なし** |
| **19** | **40** | **成立** | **40** | **0** | **801 → ★画面外** | **800 → 枠内** |
| ≥ 20 | > 40 | **不成立** | — | — | **1 行 + 切り詰めに落ちる (安全)** | 同左 |

**`a = 19` のときだけ、黙って画面外に描かれる。**枠の下端 (800) が画面の下端なので、
**はみ出したことが画面に現れない。**

**現在の `UDEVGothic_8` は ascender 16 なので発生しない** (`block = 34`、
`(40−34)/2 = 3` で両式が一致)。**別の日本語フォントを入れたユーザーでは起こりうる。**

> `a ≥ 20` では `twoLinesFit` が false になり 2 行の経路に入らないため、
> **両式の差が実際に効くのは `a = 19` の1点だけである。**
> この変更は現在の構成で 1 px も描画を変えない。

#### 検討して採らなかった案 (ボタンヒントの幅と高さ)

> **同じ調査を繰り返さないための記録。**どれも「枠に入らない」問題への案。

| 案 | 判断 | 理由 |
|---|---|---|
| **左右マージンを詰めて枠を広げる** | **❌ 採らない** | `x4ButtonPositions = {25, 130, 245, 350}` は**物理ボタンの位置に対応している。**等間隔に配置し直すと枠とボタンの対応が壊れる。**機能の劣化である。**なお 14 px の差 (480/4 − 106) の行き先は枠の間ではなく**画面の左右端** (左 25 / 右 24)。枠1↔2 と 3↔4 は既に 1 px 重なっている |
| **行間 (`lineGap`) を 0 にする** | △ 使っていない | 2 px 回収できるが、`2×20 = 40` が既に `boxHeight` と同値なので **UI_10 の 2 行は救えない。**SMALL では降格で足りており、詰める必要がない |
| **`lineY` の下限を 0 にする** | △ 使っていない | `max(1, …)` は我々のコードで変更可能。ただし `block ≤ boxHeight` のときは `max` が効かないため、**差が出るのは UI_10 の 2 行だけ**で、`gap=0` と併せても**余裕 0 px** |
| **2 行目を枠の下端から逆算して配置** | ❌ 配置では解けない | 下寄せは配置の問題を解くが、**高さが足りないことは解かない。**UI_10 面では `bottomPadding` をどう取っても 1 行目が枠の上に出る。1 行ラベルとベースラインを揃えるには `bottomPadding = 13` が必要で、**1 行目が枠外 13 px** |
| **枠を上に伸ばして下端に揃える** | **❌ 採らない (確定)** | **必要になるのは UI_10 のまま 2 行を描く場合だけで、降格でその状況が消えた。**なお寸法としても成立しない: 段を揃える案は **15 px** 必要だが実質の空きは **12 px** (リストの選択ハイライトが y=748 まで来る)。`buttonHintsHeight` を増やすと**約20画面でリストが 1 行減る。**枠の塗りは 4 つの箱だけで**横に 56 px の隙間**があり、伸ばすと上の描画が隙間に残る |
| **字間 (トラッキング) を縮める** | ❌ 採らない | **幅を積む場所が 4 箇所ある** — `getTextAdvanceX()` / `findWrapOffset()` / `drawText()` / `drawTextRotated90CW()`。一部にだけ入れると**折り返し位置と描画がずれる。**全部に入れるには `GfxRenderer` の API を変える必要があり、**`GfxRenderer.cpp` は上流が 25 件触っていて最も衝突する 1 ファイル** (§9.3)。しかも**上流が #3528 で字間・語間の設定を入れている** — 同じ機能を別実装で持つことになる |
| **`textPadding` を 4 → 2 にする** | **⬜ 保留 (有効)** | `drawHintLabel()` 専用の定数で他に使用箇所なし。枠線は 1 px なので **2 px なら接触しない** (線 1 px + 空き 1 px)。**実効幅 98 → 102 px** で、SMALL の「ダウンロード」100.12 px が 1 行に収まる。**ただし Lyra は角丸 `cornerRadius = 6` のため 3 px が安全** |
| **スロット2 の枠だけを広げる** | **⬜ 保留** | 2 行になるラベルは常に**スロット2 (確定ボタン)** に出て、両隣は短い語。**物理ボタンの中心を保ったまま**左右に広げれば対応は壊れない。**隣が 2 字なら枠幅 168 px (実効 160 px / 現状 +62)、3 字なら 147 px (実効 139 px / +41) まで広げられる** — どちらも 6 字 (124.88 px) が 1 行に収まる。隣の枠を内容に合わせて縮める必要がある |

### 8.7 計測するとき

> 出典: **上流との差分計測** (2026-10-22) / **F-9** (`f561b5fd`)

**この軸は「コードを触るとき」ではなく「自分の計測を信じるとき」の前提である。**
計測が嘘をつくと、間違った判断がそのまま記録に残る。

1. **⚠️ この環境では `| wc -l` が信頼できない。**

   `git log --oneline 81028d58..upstream/develop | wc -l` が **50** を返したが、
   実際は **351** だった。7倍の誤りである。同じ計測で
   `upstream/develop..81028d58` が **1** を返したが、正解は **0** だった
   (ベースは上流の祖先なので 0 以外ありえない)。

   **件数は git 自身に数えさせること。**

   ```bash
   git rev-list --count 81028d58..upstream/develop          # 正しい
   git rev-list --count 81028d58..upstream/develop -- <path>
   git log --oneline ... | wc -l                             # 信用しない
   ```

   **症状としては「パイプの途中で出力が切られている」**ように見える。
   行数を数える目的でパイプを使うなら、**まず既知の値で検算する。**

2. **検算できる値を1つ用意しておく。**上の誤りに気付けたのは、
   「ベースが 8月、上流 HEAD が 10月なのに、範囲内の最古が 10-16」という
   **日付の矛盾**が出たからである。**`git rev-list --count A..B` と
   `git log --reverse | head -1` の日付が噛み合うかを見る。**

3. **⚠️ 診断コード自身の副作用を疑う** (§8.5-9 と同じ教訓)。
   F-9 の検証コードは `RenderLock` を15〜20秒保持し、
   **検証コード由来の症状**を生んだ。本番版では再現しなかった。

4. **シリアルが無いので、計測結果は SD のファイルか画面に出す** (§3.7)。
   使った出力先は `/wrap-verify.txt` / `/aozora-strip.txt` / `/index-verify.txt` /
   `/build-timing.txt`。

5. **`-S` と `-G` を使い分ける。**上流で `wrappedText` の実装が変わった
   コミットを探したとき、**`-S'wrappedText'` は空振りした** —
   `-S` は出現回数の変化を見るので、本文だけ書き換わった変更は捕まらない。
   **`-G'<本文の一部>'` で特定できた** (§9.3 の #2949)。

6. **⚠️⚠️ 設定値が読める場所にあるなら、見た目から推定しないこと。**

   `settings.json` に **`uiTheme = 1` (LYRA)** と明記されていたにもかかわらず、
   実機写真の枠の隙間からの目視推定で**「BaseTheme である」と2度断定し、
   調査を2往復空転させた。**

   **一次情報 (設定ファイルの直接読み取り) を、二次推定 (写真からの目測) で
   上書きしたことが誤りだった。**枠の並びは実際には区別可能で
   (Classic は左右余白 25/24・枠間 `[-1, 9, -1]`、Lyra は 58/58・`[8, 28, 8]`
   → §8.5)、**読めば分かったものを見て決めた。**

   同じ往復で、**テーマ別の枠幅もスクリプトにハードコードした推定値だった**
   (`'LyraTheme': (80, 'SMALL')`)。値は偶然ソースと一致していたが、
   **確認せずに使った手続きが誤りである。**

7. **⚠️⚠️ 実機の見た目の検証は、写真ではなくスクリーンショットで行う。**

   **POWER + DOWN で全画面から撮れる** — `main.cpp` の `loop()` 冒頭にあり、
   `activityManager.loop()` より前で `return` するので**アクティビティに
   依存しない。設定画面でも撮れる。**

   | 項目 | 値 |
   |---|---|
   | 保存先 | `/screenshots/<題名>/…bmp`、本を開いていなければ `/screenshots/screenshot-<起動からのms>.bmp` |
   | 形式 | **480×800 / 1 bpp / 無圧縮 / ボトムアップ / 48,062 B** |
   | 合図 | 太さ 2 px の枠を 1 秒表示してから `HALF_REFRESH` で復帰 |
   | 設定 | **なし。常時有効** |

   **PNG に変換すれば 1 px 単位で検証できる:**

   ```bash
   python scripts/bmp_to_png.py G:/screenshots <出力先>
   ```

   **写真からの目測で判断してはならない。**項目 6 のテーマ誤判定は
   これで再発しない。**約物の位置合わせ (`f5-vertical-writing.md` §7) も
   この方法で行う。**

   **制約**: 1 枚あたり**約 3 秒** (合図 1 秒 + `HALF_REFRESH` 1.72 秒 +
   書き出し)。**本を開いていない画面では題名が付かない**ので、
   連続で撮るときは順番を控えること。

8. **⚠️ 関数名から構造を推測しない。**

   `markPad` を「折り返し幅を予約する仕組み」と解釈し、
   **そこにチェックボックスを載せる案を出した。**実際には:

   | | 正体 |
   |---|---|
   | **`markerWidth`** | **欄の予約。**`viewportWidth` から引く (16.56 px) |
   | **`markPad`** | **`findWrapOffset` の `extraWidth`。**「`[ ]` を `x` の幅で測る」ための**測定の補正** |

   **コードを読まずに設計を組み立てたことが誤り。**
   名前が似ていても役割が違う。

9. **バージョン文字列は未コミットの変更を示さない。**
   `scripts/git_branch.py` は `rev-parse --short HEAD` だけを使い、
   **`-dirty` のような印を付けない。**作業ツリーに変更があるビルドも、
   画面には HEAD の SHA が出る。

   **「画面のバージョンが古いから修正が入っていない」とは言えない。**
   実際にこれで「修正が走っていない」と誤判断した。
   焼いたものに修正が入っているかは、**`.pio/build/default/firmware.elf` の
   シンボル** (`nm -C | grep <関数名>`) か、**bin の md5 照合**で確かめる。

## 附録C: フォントのライセンス

| フォント | ライセンス | 注意点 |
|---|---|---|
| UDEV Gothic | SIL OFL 1.1 | **Reserved Font Name "UDEV Gothic"** |
| Noto Serif JP | SIL OFL 1.1 | Google Fonts は RFN 非設定が原則。ただし Adobe 由来 (Source Han) は要確認 |

**OFL の定義では、Modified Version に「フォーマットの変更、あるいは新しい環境への
移植」が含まれる。**TTF → `.cpfont` への変換はこれに該当するため、
**生成した `.cpfont` は Modified Version。**

したがって:

- **個人利用は制限なし**
- **再配布時は RFN のあるフォントを改名する必要がある**
- 各コピーに著作権表示とライセンス全文を同梱する必要がある
  (UDEVGothic の場合、派生元の BIZ UDゴシック / JetBrains Mono 分も)

**RFN が制限するのは名前のみで、再配布そのものは自由。**

> ### ⚠️ UI サブセットを焼き込む場合
>
> **それも「再配布」に該当する。**ファームウェアバイナリにフォントデータが
> 含まれるため、**ライセンス表示の同梱と、RFN 対象フォントの改名が必要。**
> **Phase B で焼き込むフォントを選ぶ時点で確認すること** (§7.4 の課題2)。
