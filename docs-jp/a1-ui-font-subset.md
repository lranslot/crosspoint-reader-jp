## 3. フォント生成の仕組み (調査項目 5)

`lib/EpdFont/scripts/fontconvert.py` の実測。

| 項目 | 実測値 |
|---|---|
| サイズ指定 | `face.set_char_size(size << 6, size << 6, 150, 150)` (:268) → **pt 指定・150 DPI** |
| ビット深度 | 既定 **1-bit**。`--2bit` で2ビットグレースケール |
| ビットマップの詰め方 | **連続ビットストリーム**。`dataLength = ceil(width × height / 8)`。**行のバイト境界揃えは無い** (出荷済みヘッダ5本で検証) |
| 圧縮 | `--compress` で DEFLATE。グループ単位 |
| 収録範囲の指定 | `--additional-intervals min,max` の**繰り返し**。単独文字は `X,X` |
| 1グリフの構造体 | `EpdGlyph` = 14 B (`width`1 + `height`1 + `advanceX`2 + `left`2 + `top`2 + `dataLength`2 + `dataOffset`4) |
| 区間の構造体 | `EpdUnicodeInterval` = 12 B |
| フォントスタック | 複数 TTF を優先順に指定可。**先勝ち** |

### 現在の UI 5面の生成設定

**いずれも 1-bit・無圧縮。** 本文フォント (notosans_12 以降) は `--2bit --compress --pnum` を使っている。
**UI 面で `--compress` はまだ使われていない。**

### 実測: 日本語グリフのコスト

`fontconvert.py` と同一の設定 (FreeType / `set_char_size(size<<6, size<<6, 150, 150)` / 1-bit /

| 面 | em | ビットマップ | グリフ表 | 計 (無圧縮) | DEFLATE 後 |
|---|---|---|---|---|---|
| `ubuntu_10_regular` | 20.8 px | 15,644 B | 4,886 B | 20,530 B | 15,690 B |
| `ubuntu_10_bold` | 20.8 px | 16,431 B | 4,886 B | 21,317 B | 16,107 B |
| `ubuntu_12_regular` | 25.0 px | 22,967 B | 4,886 B | 27,853 B | 18,831 B |
| `ubuntu_12_bold` | 25.0 px | 23,939 B | 4,886 B | 28,825 B | 19,523 B |
| `notosans_8_regular` | 16.7 px | 10,960 B | 4,886 B | 15,846 B | 12,766 B |
| **合計** | | | | **114,371 B (112 KB)** | **82,917 B (81 KB)** |

> 仕様書 §4.1 の見積もり「1字あたり 150〜200 B」は**過小だった。**

参考: 漢字だけを 1,200字サンプルして測ると **1字あたり 356 B / 250 B**。
かな・記号を含む 349字の平均より高いのは、漢字が最も墨の多い字種であるため。

## 6. 判断: **UI サブセットのみを採る**

常用漢字・第1水準まで焼けば、書名や著者名も SD フォント無しで表示できるようになる。
容量も足りている。**それでも採らない理由は3つある。**

**1. 常用漢字では書名・人名を救えない。**
実例として『最終戦争論』の著者「石原莞爾」の **莞・爾はいずれも常用漢字ではない。**
中途半端に増やしても「たまに読める」が「たまに豆腐」は残る。**問題の性質が変わらない。**

**2. §4.1 の設計が既にこの問題を解いている。**
書名・著者・ファイル名は本文フォント経由にする。本文フォントはユーザーが選ぶ以上、
必ず SD に存在する。**フル字形が使えるので、第1水準ですら足りない字も表示できる。**

**3. 焼き込みの目的は「日本語 UI がフォント無しで成立すること」であり、それは 349字で達成される。**
UI が読めれば、フォントを SD に置く操作まで自力でたどり着ける。
**「読めない UI から抜け出せない」事故が原理的に起きない**という §4.1 の狙いは、112 KB で満たされる。

余った 1,121 KB は、将来の機能 (F-8 ルビ描画、F-5 縦書き) と OTA の安全余裕に残す。

## 7. 文字集合の再生成スクリプト

`japanese.yaml` を編集するたびに文字集合は変わる。**Phase B ではこれをビルド時に走らせる**のが確実。

```python
#!/usr/bin/env python3
"""UI フォントに焼き込むべき非 ASCII 文字を japanese.yaml / english.yaml から抽出する。"""
import re, sys, pathlib

TRANSLATIONS = pathlib.Path("lib/I18n/translations")
# 翻訳ファイルに現れないが UI フォントで描かれる文字
EXTRA = "…"          # GfxRenderer::truncatedText() の省略記号 (U+2026)

def values(path):
    out = []
    for ln in path.read_text(encoding="utf-8").splitlines():
        m = re.match(r'^([A-Za-z_][A-Za-z0-9_]*):\s*"(.*)"\s*$', ln.rstrip())
        if m:
            out.append(m.group(2).replace('\\n', '\n').replace('\\"', '"'))
    return "".join(out)

blob = values(TRANSLATIONS / "japanese.yaml") + values(TRANSLATIONS / "english.yaml") + EXTRA
chars = sorted({c for c in blob if ord(c) > 0x7F})

# fontconvert.py 用の引数 (1文字ずつの区間) を出力
for c in chars:
    print(f"--additional-intervals 0x{ord(c):04X},0x{ord(c):04X}")
print(f"# {len(chars)} characters", file=sys.stderr)
```

## 8. ⚠️ Phase B に持ち越す課題

数値は解決したが、**手順の面で未解決の点が4つある。**

### 8.1 コマンドライン長の上限

`--additional-intervals` は区間の繰り返しでしか指定できない。349字が CJK 領域に散らばっているため、
**約349個の区間指定**が必要になる。1個あたり約35文字で **12 KB 超**。

**Windows の `cmd.exe` はコマンドライン 8,191 文字が上限。**そのままでは通らない。

対策の候補:

| 案 | 内容 |
|---|---|
| **A** | `fontconvert.py` に `--charset-file` を足す (フォーク独自の変更。**推奨**) |
| B | PowerShell から配列で渡す (cmd の制限は回避できるが、可読性が落ちる) |
| C | 連続する符号位置をまとめて区間に畳む (かな・約物には効くが、漢字230字はほぼ畳めない) |

**A が素直。** `gen_i18n.py` と同じく `platformio.ini` の `extra_scripts` に載せれば、
翻訳を書き換えるたびに自動で追随する。

### 8.2 日本語のソースフォントが無い

`lib/EpdFont/builtinFonts/source/` にあるのは NotoSans / NotoSerif / NotoSansArabic /
NotoSansHebrew / OpenDyslexic / Ubuntu の6種で、**CJK は1つも無い。**

追加が必要。**ライセンスは再配布可能なものに限ること。**

| 候補 | ライセンス | 備考 |
|---|---|---|
| Noto Sans JP | OFL 1.1 | 上流と同じ系統。字面の統一が取りやすい |
| BIZ UDPGothic | OFL 1.1 | UD 系。小サイズの可読性が高い |
| UDEVGothic | OFL 1.1 | 羅闇さんが SD で使っているもの。見た目の一貫性は最も高い |

> **Ubuntu (ラテン) + 日本語フォント (CJK) の混植**になる。`fontconvert.py` は
> フォントスタックを優先順で受け取れるので、機構としては既に用意されている。
> 字面が揃うかは**実機で見て判断すること。**

### 8.3 `--compress` を UI 面に使うかは要検討

DEFLATE で 112 KB → 81 KB になるが、**容量は足りているので圧縮する動機が弱い。**

一方で、圧縮はグループ単位の展開が要る。**UI は常時描画されるため、展開コストが
描画速度に直接効く。**F-6 (日本語 UI の描画性能) で一度苦労した領域である。

**まず無圧縮で焼くこと。**容量が逼迫していない以上、リスクを取る理由がない。

### 8.4 `notosans_8_regular` は bold を持たない

`SMALL_FONT_ID` は regular 1面のみ。`drawText(SMALL_FONT_ID, ..., EpdFontFamily::BOLD)` を
呼んでいる箇所があるかを確認し、**あるなら 8pt bold を新設するか、regular へのフォールバックで
問題ないかを決めること。**現状の豆腐問題 (ステータスバーの `最終◆◆◆`) はこの面で起きている。
