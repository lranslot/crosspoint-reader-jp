焼き5 では `abort()` が **2 回**起きた。同じ版・同じ本で起きたので当初は
1 件に見えたが、**原因は無関係の 2 件**だった。片方は頁組み、もう片方は変換で、
直し方も違う。混ぜて追うと両方を外すので、分けて記録する。

| **①** | 本を開いた直後に落ちる | 頁組みの上限が消え、1 チャンクが数千行になった | [`5f5e2d8d`](#) 順序のガード + [`ec06f278`](#) `PageBudget` |

## 1. 追い方 ── アドレスと数値の突き合わせ

### 1.1 `.elf` は焼いたものと同一でなければならない

`crash_report.txt` のアドレスは**その版の配置**でしか意味を持たない。
②の解析時には焼き5 の `.elf` を別のビルドで上書きしてしまっていたので、
**別 worktree に `e14f93e4` を出し、submodule から作り直した**。

```bash
git worktree add /d/dev/cp-e14f93e4 e14f93e4
cd /d/dev/cp-e14f93e4 && git submodule update --init --recursive
pio run -e default
```

配置が一致していることは、解決結果の**行番号が現物のソースと合う**ことで確かめる
（下の `AozoraStrip.cpp:347` は `buffer_.append(in, len);` そのものだった）。
この worktree は次のクラッシュのために残してある。

### 1.2 解決は `-pfiaC`、埋まらないものは「不明」と書く

```bash
riscv32-esp-elf-addr2line -pfiaC -e firmware.elf <addr>...
```

★ **PC（例外を起こした番地）は当てにならない。**
②の PC `0x421b0e4d` は `__cxxabiv1::__class_type_info::__do_dyncast` に、
別の番地は `std::from_chars<float>` に解決されたが、
**どちらもこの経路にあり得ない**（`-fno-rtti` で `dynamic_cast` は存在せず、
`from_chars<float>` は呼ばれない）。`-Os` の畳み込みで libsupc++ の行表が
信用できなくなっている。**「不明」と書いて、スタックのフレームで押す。**

### 1.3 スタック上の数値が答えを決める

②のスタックには解決可能なアドレスのほかに、生の数値が並んでいた。

| 値 | 10 進 | 正体 |
|---|---|---|
| `0x00009B8D` | 39,821 | **`/book/f8-aozora-test-utf8.txt` のサイズ** → 落ちた本が確定 |
| `0x0000000D` | 13 | `carry_`（前チャンクから持ち越した未完の記法） |
| `0x0000200D` | 8,205 | **要求サイズ** = 13 + 8,192 |
| `0x00004001` | **16,385** | **実際に確保しようとした量** |
| `0x00002000` | 8,192 | `CONVERT_CHUNK` |

**8,205 を必要として 16,385 を要求している**という 1 行が、
原因（`std::string` の倍々成長）をそのまま指している。
アドレスだけでは「`append` で落ちた」までしか分からず、
数値だけでは「どこで」が分からない。**両方で初めて確定する。**

### 1.4 SD の現物を読む

`crash_report.txt` の「Last logs」は末尾しか残らないので、
**SD の診断ファイルと突き合わせる**のが要る。②では

- `/aozora-strip.txt` の最終エントリ（変換成功時にしか書かれない）
- `/.crosspoint/txt_*/encoding.bin` 15 バイトの中身
- `/reader-open.txt` の最終行の `millis`

の 3 つが、後述する私の誤った推論を否定した。

## 2. クラッシュ① ── 頁組みの上限が消えた

### 2.1 起きたこと

本を開いた直後、`loadPageAtOffset()` が 8 KB のチャンクから**数千の視覚行**を
作り、`std::vector<std::string>` の再確保が **98,304 バイト**（4,096 要素 ×
`sizeof(std::string)` 24）を要求して落ちた。

### 2.2 ★ 真因 ── 同じ「上限」でも 0 のときの向きが逆だった

これは**私が 2026-11-07 に入れた変更**（`cab90d874`、段階2c）が作った。
ルビで行の高さが可変になったので、**1 ページの容量を「行数」から
「画素の予算」に書き換えた**。

```cpp
// 変更前 — 行数の上限
while (pos < chunkSize && static_cast<int>(outLines.size()) < linesPerPage)

// 変更後 — 予算の上限
if (!outLines.empty() && usedExtent + pitch > pageExtent) break;
```

> **行数の上限は 0 のとき安全側に倒れる。**`linesPerPage == 0` なら
> ループは**一度も回らない** ── 1 ページも組めないが、暴走もしない。
>
> **予算の上限は 0 のとき無制限になる。**`pageExtent == 0`、`pitch == 0` だと
> 条件は `0 > 0` で、**永遠に偽**である。止めるものが何も無くなる。
>
> **同じ「上限」という言葉でありながら、0 のときの向きが逆だった。**
> 置き換えたとき、元の形が **`linesPerPage == 0` を偶然守っていた**ことに
> 気づいていなかった。守っていたのは意図ではなく、不等式の形である。

### 2.3 なぜ 0 で呼ばれたか ── 順序の穴

`pageExtent` と `normalPitch` を設定するのは `initializeReader()` で、
これを呼ぶのは **`render()` だけ**（描画タスク）。一方で `loop()`（主タスク）は
索引の延長のために `loadPageAtOffset()` を呼ぶ。

`Activity::onEnter()` の `requestUpdate()` は**非即時**で、
描画タスクへの通知は `ActivityManager::loop()` の**末尾**（`ActivityManager.cpp:162`）、
つまり **`currentActivity->loop()` が走ったあと**である。
よって「初期化前の `loop()`」が成立する。

### 2.4 修正 ── A（順序）と B（不変条件）を分けた

- **A** (`5f5e2d8d`): `loop()` の条件と RenderLock 取得後の再確認に
  `initialized` を足した。判断はロック内で、`initializeReader()` が
  **同じロックの下で走る**ので順序が保証される
- **B** (`ec06f278`): 打ち切りを**クラス単独の性質**にした。
  `PageBudget`（69 行、依存なし、host 試験可能）が
  ① 使えない予算は**何も通さない** ② 使える予算は**1 行 1 画素以上を課す**
  の 2 つを持つので、通る行数は最大 `extent` 本に**構造的に**収まる

★ **B が発動したときの挙動を明示した。**`loadPageAtOffset()` は
確保の前に `LOG_ERR` して `false`、`advanceIndex()` は
**「索引終了」にせず見送る**（索引を完了扱いにすると本が 1 ページで固まる ──
大声のクラッシュを静かな誤答に替えるのは改善ではない）。
件数は `geometryNotReady` に数え、SD の診断行に `notready=N` として出る。

試験は `test/page_budget/`、10 件。**判定門と送りの下限を抜いた変異体**に対して
**クラッシュ側 5 件だけが落ち、等価性 5 件は通る**ことまで確かめてある。

## 3. クラッシュ② ── 変換が 16 KB の連続ブロックを要求した

### 3.1 経路

```
ReaderActivity::onEnter():169
  → loadTxt():111
    → Txt::prepareEncoding():242
      → Txt::stripUtf8ToCache():467      strip.process(…)
        → AozoraStrip::process():347     buffer_.append(in, len);
          → std::string::_M_append → _M_mutate → operator new(16385)  ✗
            → abort()
```

`-fno-exceptions` なので `operator new` は `nullptr` を返さず
`abort()` に落ちる。

### 3.2 真因 ── 8,205 の必要が 16,385 の要求になる

```cpp
if (carry_.empty()) { buffer_.assign(in, len); }    // 1 枚目: capacity 8,192
else { buffer_ = carry_; buffer_.append(in, len); } // 8,205 > 8,192 → 倍に
```

libstdc++ は `max(2×旧, 必要)` で伸ばすので 16,384、終端分 +1 で **16,385**。
**必要なのは 8,205 だけ**で、16 KB は成長方針の産物である。

### 3.3 なぜ 1 回目だけ落ちるか ── 空きではなく最大連続ブロック

落ちたのは起動から **537 秒後**。直前のログは

```
[536977] [GFX] Time = 4645 ms from clearScreen to displayBuffer
[537548] [TXT] Encoding detected: UTF-8
```

**4.6 秒の全画面描画の 571 ms 後**である。その描画中に
`SdCardFont::onGlyphMiss()` が**27 字ぶんのグリフを 1 字 1 ブロックで**
オンデマンド確保していた（`slot 20/128` … `slot 27/128`）。

> **問題は量ではなく散り方である。**小さなブロックが 27 個散った領域では、
> 空きが 40 KB あっても **16 KB の連続ブロックが取れない**。
> 再起動直後なら同じ要求が通る。

### 3.4 修正 ── 定数で 1 回だけ予約する

```cpp
AozoraStrip::reserveForChunk(n)   // n + MAX_CARRY、各経路がループ前に 1 回
stripped (UTF-8 経路)             // 1 チャンク + 1/4
stripped (Shift-JIS 経路)         // 符号化出力 + 1/4
```

★ **チャンクごとに `reserve` するのでは足りない。**
MSVC の `reserve()` は**同じ幾何成長則を適用する**ので、
データで揺れる値を渡すと 12,533 の要求が 18,686 に膨らんだ（実測）。
**定数 1 回だけが、両方の標準ライブラリで要求サイズの一致する形である。**

1/4 の余裕は実測である。strip は**バイトを増やすこともある**
（正規化した字下げ記法、見出し前後の空行）ので、
コーパスでの最悪は **12,277 バイトのチャンクから 13,275 バイト**（8%）。
**きつい予約は超えた瞬間に倍々に戻る**ので、それは外す失敗そのものである。

### 3.5 残っている数字 ── Shift-JIS 経路は 15,431 B

`tools/layout_harness alloc` による単発最大要求:

| 経路 | 修正前 | 修正後 |
|---|---|---|
| UTF-8 | 8,503〜13,681（本によって変動） | **10,295**（決定的） |
| Shift-JIS | 18,062〜18,734 | **15,431**（決定的） |

同時常駐の山は全ファイルで 2〜4 割減り、確保回数はほぼ半減した。
出力は 8 ファイル（4 冊 × 2 経路）すべて**バイト一致**。

★ **Shift-JIS 経路は 8,192 を超えたままである。**
その経路の鎖は **8,192 の SJIS → 符号化 12,277 → strip 出力 13,275** で、
**13 KB 未満にはできない**。8,192 を下回らせるには
チャンクを小さくする（案3）か行単位で書き出す（案2）が要る。
**案1 でできるのは「非決定的な 18.7 KB」を「決定的な 15.4 KB」にすることまで。**

### 3.6 失敗時のヒープを知る手立て

`/heap.txt` に 1 行追記する（`lib/Memory/HeapDiag.h`）。
シリアルはこの端末の利用者に届かないので、**ファイルでなければ意味がない。**

```
<millis> <tag> free=<B> max=<B> min=<B> [詳細]
```

| tag | 置き場所 | 分かること |
|---|---|---|
| `boot` | `main.cpp` の機種判定直後 | 何も読んでいない基準値 |
| `reader-exit` | `TxtReaderActivity::onExit()` | **本 1 冊が残す状態** |
| `pre-convert` | 変換の**直前**。本のサイズと path 付き | ★ abort の前に card へ書き終わる |
| `post-convert` / `convert-failed` | 変換の直後 | 変換の費用 |

`getMaxAllocHeap()` が肝である。`getFreeHeap()` だけでは
16 KB が入るかどうか分からない。

## 4. 字下げの持ち越しを索引に置かなかった理由

段落の途中でページが変わると、`［＃N字下げ］` は**前のページに残る**。
断片は記法を見ないので `prefixLen == 0` となり、
**その段落の残り全部が字下げ 0 で描かれていた**（実機で p36 の先頭列、
p37 の先頭 4 列）。

### 4.1 何を保存すれば足りるかは分かっていた

- **必要なのは「ぶら下げ量」1 つだけ。**断片は全行が継続なので
  「最初の行の字下げ」は使われない
- **「折り返し中か」は保存不要。**`offset-1` のバイトが `'\n'` かを見れば分かる

つまり `index.bin` に **1 ページ 2 バイト**足せば表現できた。

### 4.2 ★ それでも索引に置かなかった

> **索引は遅延構築（F-9）である。**再起動後の復帰位置は
> `progress.bin` の `currentOffset` から来るのに、
> **索引はまだそのページに届いていない。**
>
> つまり**最も起きやすい経路（冷間復帰）でちょうど欠落する。**
> 索引に置くと、「普段は効くが、電源を入れ直した直後だけ効かない」という
> 最悪の形の不具合になる。

`progress.bin` にも持たせれば埋まるが、それは**形式変更が 2 つ**になり、
2 つのファイルの同期という新しい不変条件を作る。

### 4.3 採った形 ── ファイルから復元する

ページ先頭から**原稿行の頭まで遡って記法を読み直す**。
段階2g の原則（「行が自分で自分を名乗らなければならない」）と同じ考えである。

| 性質 | 索引に置く案 | 遡って読む案（採用） |
|---|---|---|
| 冷間復帰（索引未構築） | ✗ 欠落 | ✓ 動く |
| 索引パスと描画パスの一致 | 同期が必要 | **構造的に一致**（同じ関数） |
| 形式変更 | `index.bin` + `progress.bin` の 2 つ | **なし** |
| 費用 | 2 B×頁 | 1 ページあたり 4 KB の追加読み 1 回 |

純粋な部分は `src/activities/reader/AozoraIndent.h` に出した
（記法の解析、行頭の後方走査、「継続はぶら下げ量を負う」規則）。
`CACHE_VERSION` は 11 → **12** ── 索引の**形式**は変えていないが、
継続行が升目を食うので**ページの切れ目が動く**。

### 4.4 対照実験

| ファイル | 設定 | 持ち越し無 | 持ち越し有 | 最初に動く頁 |
|---|---|---|---|---|
| **新日本の進路**（字下げ無） | 3 設定すべて | 28 / 33 / 36 | **同一** | — |
| f8 試験ファイル | 3 設定すべて | 42 / 48 / 52 | **同一** | — |
| 最終戦争論 | narrow | 166 | 166 | — |
| | normal | 193 | 193 | **p3** |
| | wide | 210 | **211** | **p3** |
| 戦争史大観 | narrow | 324 | 324 | p219 |
| | normal | 378 | 378 | p255 |
| | wide | 412 | 412 | p57 |

**字下げの無い本は 1 箇所も動かない。**総ページ数の変化は最大 +1（0.5%）。
動いた境界の個数が多く見えるのは**連鎖**で、意味のある数字は
「最初に動く頁」である。

## 5. `tools/layout_harness` を常設にした理由

### 5.1 同じものを 3 回捨てていた

段階2g・2h・そして今回の対照実験で、**同じ頁組みモデルを
scratchpad に 3 回書き直した**。毎回「出荷コードを写した」モデルなので、
**書き直すたびにファームから離れる機会があった。**

常設にして、**出荷コードを include する**形にした
（`AozoraStrip.cpp`、`Utf8.cpp`、`AozoraIndent.h`、`PageBudget.h`、
`VerticalWrap.h`）。縦書きの折り返し規則そのものは
この harness のために `VerticalWrap.h` に出した。

### 5.2 ★ 初回の実行で、実装の欠陥を 1 つ捕まえた

字下げ持ち越しの遡り幅を **8 KB / 512 B 刻み**にしていた。
**どちらも測らずに決めた数字**である。harness で測ると:

| ファイル | 最長行 |
|---|---|
| 最終戦争論 | **2,845 B** |
| 戦争史大観 | 2,080 B |
| 新日本の進路 | 1,540 B |
| f8 試験ファイル | **23,838 B**（意図的な長行） |

512 B 刻みでは**最長段落 1 つに 6 回の SD 読み**が要り、
f8 試験ファイルでは `carrylost` が設定ごとに **15〜20 頁**出ていた。
→ **4 KB 刻み × 32 KB** に変更（`2c635e7b`）。
実書籍はどれも **1 回の読みで解決**し、`carrylost` は全ファイル 0 になった。

**この端末では費用はバイトではなく SD 読みの回数である。**
大きく少なく読むほうが速い ── それは測らなければ出てこなかった。

なお `carrylost` は「**行頭に到達できなかった**」の数で、
「字下げを落とした」ではない。件の 23,838 バイト行は記法を持っていないので、
実際には何も失われていなかった。**過大に出る向きは、
信頼できなくなった時を知らせる計器としては正しい向き。**

### 5.3 ★ 宿題 ── 頁組みループ本体がまだ host に無い

`TxtReaderActivity::loadPageAtOffset()` は renderer とフォントの奥にあり、
host ビルドできない。`pages` モードは**出荷プリミティブを
harness 自身のループで駆動**しており、ルビと傍点は外して全行同一ピッチにしている。

> **したがって `pages` の頁数は「版間の比較」のためのもので、
> 実機の頁番号の予測ではない。**
>
> ループ本体を出荷ヘッダに切り出せば本物になるが、
> それは最も繊細な関数の構造変更なので、焼く直前にはやらない。
> → STATUS の「次にやること」に起こした。

### 5.4 absolute な数字は移植できない

MSVC は `std::string` を 1.5 倍、libstdc++ は 2 倍で伸ばす。
**比較は移植できるが絶対値は移植できない。**
ただし「定数 1 回」の予約だけは**両者で一致する** ── それが §3.4 の実質である。

> **変換中に空きヒープの底が 19,132 バイトまで落ちる。**
> `min=` は `getMinFreeHeap()`、つまり**起動以来の最小値**である。
> `pre-convert` で 36,720、`post-convert` で **19,132** ──
> **この変換 1 回が、空きの底をさらに 17,588 バイト押し下げた。**
>
> `free` が前後で 96,516 のまま動いていないのは、
> 変換が確保したものを全部返しているからである。
> **残るのは「一瞬どこまで細くなったか」だけで、それが 19 KB である。**
>
> **今後ヒープを使う機能を足すときの基準はこの 19,132 である。**
> 96,516 の空きを見て設計してはいけない。
> 変換と同時に走るものを足せば、その分だけ底が下がる。

### 6.4 計数の健全性

| 項目 | 実機 | PC の模型 | 判定 |
|---|---|---|---|
| 『戦争史大観』の `《` / `》` | **95 / 95** | 95 / 95 | ✅ 均衡。二重計数の修正（`aa266721`）が効いた |
| `bouten` | 2 | 2 | ✅ |
| `indent lines` / `ranges` / `hanging` | 47 / 26 / 17 | 47 / 26 / 17 | ✅ |

焼き5 で `》` が 1 つ多く出ていた件は、**ファイルではなく計数の誤り**だった
（§7 の教訓と、仕様書 §8.8 項目 28 (a)）。

## 7. ★ `bt=` の 4 つの数字が何を数えているか

焼き6 の実機で `bt=40/8/1/7`（描いた/変種/衝突/親なし）。
対象は `/book/f8-aozora-test-utf8.txt`、開いたのは 1 回（`145788 open=library`）。

**ファイル上の実数**（羅闇さんの手数え、`tools/layout_harness bouten` が
**出荷の `bouten::parseNote()` で再現**）:

| | 手数え | harness（出荷コード） | 一致 |
|---|---|---|---|
| 傍点注記 総数 | 136 | **136** | ✅ |
| 未知の変種 | 4 | **4** | ✅ |
| 親が一致しない | 1 | （1。§7.3 で位置を特定） | ✅ |
| 衝突 | 1 | 1 | ✅ |

端末は **変種 8（2 倍）/ 親なし 7（7 倍）**。**衝突 1 だけが一致していた。**

### 7.1 各カウンタが何を 1 と数えているか（コードで確認）

`loadPageAtOffset()` の呼び手は**ちょうど 2 箇所**しかない
（`advanceIndex()` の索引構築と `render()` の描画）。
それがこの表の根拠である。

| カウンタ | 1 = | 増える場所 | 多重度 |
|---|---|---|---|
| **drawn** | **（視覚行 × 範囲）の対**を 1 回描いた | `collectBoutenForLine()` | **描画 1 回ごと。**1 つの範囲が 2 列に分かれれば **2**。同じ頁を 2 回描けばさらに 2 倍 |
| **variant** | **注記 1 件**（丸・ゴマ以外の種類） | `stripRubyNotation()` | ★ **その注記を含む行を走査するたび。**索引構築も含む |
| **collide** | **（視覚行 × 範囲）の対**をルビに譲って描かなかった | `collectBoutenForLine()` | drawn と同じ |
| **noparent** | **注記 1 件**（引用語が直前に一致しない） | `stripRubyNotation()` | variant と同じ |

★ **どれも「ファイルに何件あるか」ではない。**
**開いてから閉じるまでにリーダーが何回その仕事をしたか**である。
リセットは掛かっておらず、`onExit()` で診断行を書き換えるときの値が記録される。

### 7.2 再描画で二重に数えるか ── 数える

- **drawn / collide**: `collectBoutenForLine()` は `wantBouten` のとき
  （= 描画パス）だけ走る。**頁を描き直せばもう 1 回数える**
- **variant / noparent**: `stripRubyNotation()` は
  **`loadPageAtOffset()` のすべての原稿行**に対して走る ──
  **索引構築のパスも含む。**よって最低 1 回は索引で数えられ、
  その頁を表示するたびに 1 回増える

★ **さらに、長い行では位置によって多重度が変わる。**
`loadPageAtOffset(offset)` が見る `line` は
**頁の先頭から行末まで**なので、1 行が K 頁にまたがるとき、
**行の後ろにある注記は「その手前で始まる頁の数」だけ数えられる。**
試験ファイルの 23,838 バイト行では、索引 1 周だけで **最大 5 回**になる
（`layout_harness bouten` の `scans=` 列）。

### 7.3 ★ 食い違いは説明が付いた

`tools/layout_harness bouten` で、注記の位置と頁境界を突き合わせた
（縦書き「普通」= 端末と同じ `vp=464x764 n=12`）。

| | 位置 | その行の長さ | 索引 1 周の計数 | 乗っている頁 |
|---|---|---|---|---|
| **変種 4 件** | `line@31390` の +12 / +66 / +120 / +171 | 210 B | **1 回ずつ = 4** | **p46**（31,066〜31,603） |
| **親なし 1 件**「存在しない語」 | `line@31603` の +39 | 84 B | **1 回 = 1** | **p47**（31,603〜31,883） |

どちらも**短い行**なので、索引 1 周での計数は**実数そのまま（4 と 1）**である。
したがって:

> **変種 8 = 4 件 × p46 の読み込み 2 回**（索引 1 + 描画 1）
> **親なし 7 = 1 件 × p47 の読み込み 7 回**（索引 1 + 描画 6）

★ **2 倍と 7 倍が違う理由は「別の頁に乗っているから」である。**
変種 4 件は p46、親なし 1 件は p47 ── **213 バイトしか離れていないが、
ちょうど頁の境界をまたいでいる**（`line@31603` は **p47 の先頭バイトそのもの**）。
頁が違えば読み込まれた回数も違うので、**独立に積算される。**

衝突 1 が実数と一致したのは、**その頁が 1 回しか描かれなかった**ためである。

**drawn 40** は（視覚行 × 範囲）× 描画回数なので、
**136 とも 40 とも比較できる file 側の数字が存在しない。**

### 7.4 ★ 確認できていないこと

**p47 が本当に 7 回読み込まれたかは、私には確かめられない。**
言えるのは「カウンタがそう言っている」ことと、
**`loadPageAtOffset()` の呼び手が 2 箇所しかないので、
他の経路では増えようがない**ことである。
頁を行き来した回数、またはステータスバーの更新による再描画が
6 回あれば一致する。

### 7.5 数え方を変える案（実装は待ち）

いまの数字は「リーダーが何回やったか」として**正しい**。
問題は**「ファイルに何件あるか」を知りたいときに使えない**ことである。

| 案 | 内容 | 費用 | 評価 |
|---|---|---|---|
| **1** | **名前で区別する。**`bt=` を「この回の作業量」と明記し、ファイル側の実数は `/aozora-strip.txt` から読む（変換器は各注記を**ちょうど 1 回**見る） | **0。**文書とコメントだけ。**済（この節と header のコメント）** | ★ **推す。**両方の数字に意味があり、混ぜないだけで足りる |
| **2** | **変種を変換器に移す。**`AozoraStrip` が種類を分類し、`/aozora-strip.txt` に `variant=N` を出す | 小。`bouten::kindIsExact()` は共有ヘッダに出した | ★ **推す。**「このファイルに未知の種類が 4 件」が**1 回だけ**正しく出る |
| 3 | 索引パスだけで数える（`outAttrs == nullptr` で門） | 小 | **不十分。**長い行では索引 1 周でも多重に数える（§7.2） |
| 4 | 注記ごとに「もう数えた」を持つ | 中。ファイルオフセットを鍵にした集合が要る | **割に合わない。**RAM を払って、変換器が無料で持っている情報を再現することになる |
| 5 | そのまま | 0 | **不可。**焼き5 の `》=45` と同じ形で、次も読み違える |

**案1 + 案2** を推します。`noparent` は引用語と**刷り上がった本文**の照合なので
変換器には移せない（変換器は元の記法を持っているだけ）── 案1 の扱いで残す。

> **なぜ名前だけで足りるのか。**
> 焼き5 では `》=45` という**計数の誤り**を「ファイルの異常」と読んだ
> （仕様書 §8.8 項目 28 (a)）。今回の 8 と 7 は**計数が正しくて読み方が誤っていた**。
> **数字の定義が書いていないと、どちらの形でも間違える。**
