## 1. 背景と目的

### 1.1 経緯

AliExpress 等の国際流通品として販売される Xteink X4 の一部は、工場出荷時に
**USBフラッシュ書き込みが無効化 (ロック)** されている。日本語圏には、このロック品に
カスタムファームウェアを導入し、さらに日本語UI化まで到達した記録が存在しない。

2026-08-09、上流への日本語翻訳 PR (#2940) が**方針上の理由でクローズ**された。
翻訳の品質ではなく、CJK 字形が同梱フォントに含まれないことが理由である (§8.2)。
これを受け、**独立したフォークとして日本語版を公開する**方針に転換した。

### 1.2 目的

1. スマートフォンで作成したメモ / TODO (Markdown) を X4 上で快適に閲覧する
2. Markdown のチェックボックスを端末上でトグルできるようにする
3. **UI を日本語化する** ← v0.2 時点で達成
4. **フォントを別途用意しなくても日本語で使える状態で配布する** ← v0.5 で追加
5. 上記を **SDカード経由で導入可能なファームウェア** として公開する

### 1.3 非目的 (スコープ外)

- USBフラッシュロックそのものの解除 (技術的に不可能、かつ不要)
- PDF のネイティブレンダリング
- Bluetooth 機能の復活
- **上流へのマージを前提とした設計上の妥協** ← v0.5 で追加

## 3. 上流フォントの字形収録範囲 — **v0.5 の中核的発見**

**PR #2940 がクローズされた技術的根拠であり、フォーク設計の出発点。**

### 3.1 組み込みフォントの intervals

`scripts/fontconvert.py:43-89` で定義される範囲:

ASCII / Latin-1 / Latin Extended-A / Latin Extended-B (ベトナム語・欧州サブセット) /
ベトナム語拡張 / 一般句読点 / 結合分音記号 / **キリル 0x0400-0x04FF** / 数学記号

ギリシャ (0x0370-0x03FF) は L80 で**コメントアウト**されている。

### 3.2 フォント別の収録状況 (実測)

ヘブライ・アラビアは intervals ではなく `--additional-intervals` により
フォントスタックに合成されている (`convert-builtin-fonts.sh:42-83`)。

| フォント | 用途 | キリル | ヘブライ | アラビア | CJK |
|---|---|---|---|---|---|
| `ubuntu_10` / `ubuntu_12` (regular+bold) | **UI** | ✅ | ✅ | ✅ | ❌ |
| `notosans_8_regular` | **UI** | ✅ | ✅ | ✅ | ❌ |
| `notoserif` / `notosans` 12-18 | **本文** | ✅ | ❌ | ❌ | ❌ |

### 3.3 この事実が意味すること

**上流の言語受け入れ基準は「非ラテンか否か」ではなく「UIフォントに字形があるか」。**

ヘブライ語 (#2068) とアラビア語 (#2599) の UI 翻訳が受け入れられたのは、
UI フォントに字形が同梱されているため。キリル4言語 (RU/UK/BE/KK) も同様。
**CJK だけが一切含まれない。**

`cjk` / `hangul` は SD カードフォントのプリセット (`fontconvert_sdcard.py:54-56`)
にのみ存在する。

**メンテナの判断は一貫しており、恣意的な扱いではない。**この線引きを技術的に
覆すことはできない。したがって**フォーク側で UI 用字形を自前で用意する**のが
唯一の解となる (§4.1)。

### 3.4 CJK フォント配布が行われない理由 (メンテナ発言)

| 日付 | 発言者 | 場所 | 要旨 |
|---|---|---|---|
| 2026-04-24 | mcrosson | Discussion #1757 | スコープをリーダー(text/epub)に限定したい。**UI は後回し**で、リーダー経由の多言語サポートの力学を理解してから |
| 2026-05-30 | Uri-Tauber | PR #2208 (韓国語) | 組み込み UI フォントは韓国語範囲を非対応。**304グリフでは足りず Hangul Syllables は 11,172 グリフ必要** |
| 2026-06-29 | Uri-Tauber | Discussion #1757 | SD フォント一覧には**ユニバーサルフォントのみ**を載せている。他ユーザへの churn を避けるため。**フォント管理に言語別サブカテゴリを追加する必要がある。将来検討する** |
| 2026-07-04 | Uri-Tauber | Discussion #1757 | デーヴァナーガリー等の複雑シェーピングは個別 PR では受けない。HarfBuzz を ESP32-C3 向けに削る方向が現実的 |
| 2026-07-12 | itsthisjustin | PR #2208 | **「CJK へのより良い道筋に取り組む間、いったんクローズする」**(恒久拒否ではなく保留の含み) |
| 2026-08-09 | Uri-Tauber | PR #2940 | CJK UI 翻訳はフォント非同梱ゆえスコープ外。??? 表示は「壊れた UI の出荷」 |

**ボトルネックは翻訳ではなくフォント配布であり、それは上流も認識している。**

### 3.5 上流における CJK 対応の非対称

| 領域 | 状況 |
|---|---|
| **本文レンダリング** | 活発に受理。#2288 / #2652 / #2665 / #2710 / #2768 / #2781 がマージ済み |
| **UI 翻訳** | 全滅。韓国語 (#1609 / #2208)、中国語 (#2273)、日本語 (#2940) がいずれもクローズ |
| CJK UI フォント | #505 / #1059 クローズ、#2521 (フォールバック) のみマージ |

CJK 言語ファイルは**一度もマージされていない** (2026-08-10 時点)。
中国語 #2221 は DRAFT で、`_order: "0"` の重複と `_language_code: "ZH-HANS"` の
ハイフン (C++ 識別子として不正) により現状マージ不能。

## 4. フォーク設計

### 4.1 フォントアーキテクチャ — **UI固定 / 本文可変**

**設計の中核。上流がクローズした理由をそのまま解決する構造。**

| 用途 | フォント | 配置 | 理由 |
|---|---|---|---|
| **UI 文字列** | 日本語サブセットを**焼き込み** | Flash | フォント未設定でも日本語UIが成立する。「読めないUIから抜け出せない」事故が原理的に起きない |
| **本文** | ユーザーが選ぶ SD フォント | SDカード | 好みの書体で読めるべき。明朝/ゴシックの選択は読書体験の核心 |
| **ファイル名・書名** | **本文フォント**を使用 | SDカード | 何の文字が入るか事前に определ できないため、サブセットでは足りない |

#### 解決される問題

| v0.4 までの制約 | v0.5 での解決 |
|---|---|
| 12pt が UI と本文Small で共有され、片方だけ最適化できない | **UI と本文が完全に分離**。相互干渉が消える |
| SDフォントに 8/10/12pt が無いと UI が □ になる | **UI は Flash 上のフォントで描画**。SD の状態に依存しない |
| UI用に軽量化すると書名・ファイル名が表示できない | **ファイル名は本文フォント経由**。フル字形が使える |
| 日本語UIにフォント準備が必須 | **不要**。焼き込み済み |

#### 容量計画

必要文字数 = japanese.yaml に出現する文字 + 動的生成される文字。

**動的生成される文字を忘れないこと。**翻訳ファイルに現れないが UI フォントで
描画される:

- `%s` `%d` `%zu` `%u` `%.2f%%` に埋まる値 (数字、記号)
- 日付・時刻表示
- バッテリー残量、ページ番号
- 単位記号 (%, MB, KB)
- エラーコード

**ASCII 95文字は全て含める。**3サイズ2種でも数十KB程度であり、削る意味がない。

概算: 1文字あたり 150〜200 B (8/10/12pt × regular/bold 合計) と仮定すると、
1,000字で 150〜200 KB、3,000字で 450〜600 KB。**残 Flash 963 KB に対し、
1,000字前後なら余裕、3,000字でも収まる見込み。**(要実測)

#### 容量の捻出

**31言語分の翻訳文字列を削除する** (§4.2)。加えて `--strip-unused` が
未使用キーを除去するため、実際の削減量は yaml のサイズより大きい可能性がある。

### 4.2 対応言語の削減

**英語 + 日本語のみを残す。**

| 言語 | 扱い | 理由 |
|---|---|---|
| 英語 | **必ず残す** | フォント破損時・想定外事態の避難先。消すと復旧手段を失う |
| 日本語 | 主対象 | — |
| その他30言語 | 削除 | 日本語版フォークに不要。Flash を UI フォントに回す |

**副次的効果**: `STR_SMALL` 系4キーの二重管理 (PR版は削除 / 運用版は残す) が
develop ベース化により**不要になる**。japanese.yaml は1本で済む。

### 4.3 上流バグの自前修正

フォークでは上流の判断を待たずに修正する。修正は Issue の実証にもなる。

| 対象 | 上流 Issue | 内容 |
|---|---|---|
| `GfxRenderer::wrappedText` | **#2949** | 文字単位のハードブレークを実装。**訳文への半角スペース埋め込みが不要になり、日本語が自然になる** |
| `WifiSelectionActivity` の SSID 切り詰め | **#2950** | バイト数ではなくコードポイント数で数える |
| `TxtReaderActivity` の O(n²) 折り返し | #2650 (空席) | 二分探索等による最適化 (§4.7) |

### 4.4 配布形式

**`.bin` のみ。**

USBロック品でもロック無しでも、SD 経由なら**同じ手順が使える**。
分岐が無いことが利点。逆 (USB 前提) はロック品を排除してしまう。

## 5. 書き込み・復旧手順 (確立済み)

### 5.1 ⚠️ ロック品における書き込み経路の要点

**本プロジェクト最大の知見。**

| 経路 | 1.4系→1.4系 | 1.4系→1.5系 | 備考 |
|---|---|---|---|
| ファイルブラウザから `.bin` 直接実行 | ○ | — | 1.4.1 で成功実績あり |
| Settings > SD Card Firmware Update | ○ | **× Invalid firmware file** | 公式RC3でも同様に失敗 |
| **Escape Hatch > Flash Firmware** | ○ | **○** | **唯一の突破口** |
| 電源+上ボタン (OEMブートローダー) | × | × | ストック時のみ有効 |
| USB Web Flasher | × | × | ロックのため不可 |

> **1.4.1 の SD更新機能は 1.5系イメージを受け付けない。**
> 自作ビルド・公式RC3 の双方で「Invalid firmware file」を再現。
> ファイルサイズは PC 上の原本と 1 バイト単位で一致 (5,495,888 B)。
>
> **解決策**: Debug ページから **Escape Hatch (recovery, 0.4 MB)** を取得し、
> 通常の SD 更新でこれを書き込む。起動後のメニューから `Flash Firmware` を選び、
> SD 上の `.bin` を指定すれば 1.5系が書き込める。
> 一度 1.5 系に上がれば、以降は通常の SD Card Firmware Update が使える。

### 5.2 標準的な書き込み手順 (1.5系運用時)

1. `.pio\build\default\firmware.bin` を **`update.bin`** にリネーム
2. SDカードの**ルート**に配置
3. 端末で 設定 > システム > SDカードファームウェア更新 を実行

### 5.3 復旧経路の確保 (必須)

| ファイル | 用途 |
|---|---|
| `escape-hatch.bin` | **緊急脱出・世代跨ぎの書き込み** |
| `crosspoint_1.4.1_update.bin` | 安定版への復帰 |
| `crosspoint_1.5rc3_update.bin` | 公式1.5系への復帰 |
| `stock_english_update.bin` | 純正 (英語) への復帰 |
| `stock_chinese_v6.2.4_update.bin` | 純正 (中国語 / 出荷時) への復帰 |

> **運用ルール**: SDカードのルートに `update.bin` を**常設しない**。
> 書き込み時のみリネームして配置する。誤爆防止のため。

### 5.4 既知の障害と対処

| 現象 | 原因 | 対処 |
|---|---|---|
| Invalid firmware file | 1.4系が1.5系イメージを拒否 | **Escape Hatch を使用** |
| Escape Hatch で "No .bin files" | SDカード未挿入 / 認識前 | 挿入して**再起動** |
| SD更新で "Error 9" | 既知の未解決バグ | **文鎮化ではない**。再起動して再試行 |
| 1.2.0 系で OTA が常に失敗 | RAM不足による TLS+書き込みの競合 | **1.2.0ベースを導入しない** |
| SDカードのフォーマット不能 | 書き込み過多による物理故障 | カード交換。**MLC 推奨** |
| **develop 移行後に初回起動が遅い** | **キャッシュ形式の更新 (book.bin 8→10 / section.bin 32→37) による全再生成** | **正常。データ損失ではない** |

## 6. 機能要件

### 6.1 【F-1】UI日本語化 — ✅ 完了 (428キー)

`lib/I18n/translations/japanese.yaml` に 428 キー全訳。
ビルド時に `scripts/gen_i18n.py` が自動で取り込む。

#### gen_i18n.py の仕様 (実測)

| 項目 | 内容 |
|---|---|
| キーの正本 | `english.yaml` (`_language_code: EN` で自動検出、L140-147)。順序は英語ファイル準拠 (L202) |

| ビルドフック | `--strip-unused` が有効 (L1001) |

#### 翻訳作業上の知見

**① バイト数と文字数の混同**

`WifiSelectionActivity.cpp` の SSID 表示は `std::string::length()` (バイト数) で
上限判定。日本語プレフィクスは1文字3バイトを消費する。

| キー | 当初訳 | バイト | SSID表示可能長 | 採用 |
|---|---|---|---|---|
| STR_NETWORK_PREFIX | 「ネットワーク: 」 | 20 | 5〜8文字 | **"SSID: "** (6B) → 22文字 |
| STR_TO_PREFIX | 「接続先: 」 | 11 | 11〜14文字 | **"SSID: "** (6B) → 19文字 |

→ **上流 Issue #2950 として報告済み。フォークでは修正する。**

**② `wrappedText` は半角スペースにしか対応しない**

日本語文は1単語扱いになり、`maxWidth` を超えると**丸ごと「…」に切り詰められる**。
`STR_CRASH_DESCRIPTION` / `STR_RESTARTING_HINT` の2件で半角スペースを挿入して回避。

→ **上流 Issue #2949 として報告済み。フォークで修正すれば回避策が不要になる。**

**③ 設定画面のラベルは自動省略される**

`BaseTheme.cpp` の `truncatedText` は UTF-8 対応 (`utf8RemoveLastChar`)。
UI_10 で CJK 1文字 ≈ 13〜16px、ラベル予算は約 22〜25 文字。

**④ 描画APIごとの折り返し挙動 (実測)**

| API | 折り返し | 切り詰め | クランプ |
|---|---|---|---|
| `drawCenteredText` (GfxRenderer.cpp:549-553) | なし | なし | **なし** (画面外にはみ出す) |
| `BaseTheme::drawPopup` (BaseTheme.cpp:726-755) | なし | なし | **なし** (`w` が画面幅を超えると `x` が負になる) |
| `wrappedText` | スペースのみ | あり (`…`) | — |
| `truncatedText` | — | あり (UTF-8対応) | — |

**⑤ 書式指定子は個数・種類を保持する**

`%zu` `%d` `%.2f%%` `%u` `%s` は削除・翻訳・順序変更しない。位置移動のみ可。

**⑥ 訳さない方が良いもの**

### 6.3 【F-3】TXT の文字コード自動判別 (優先度: 高)

**現象**: Shift-JIS の `.txt` が `◆?` と半角英字の交互で文字化けする。

**重要性**: **青空文庫のテキストは Shift-JIS。**日本語ユーザーは全員当たる。

**実装方針**: 先頭数KBのバイトパターン検査。BOM の有無、UTF-8 として不正な
シーケンスの検出で大半は判別可能。ストリーム処理で RAM 制約下でも実装可能。

**暫定回避策**:

```powershell
$sjis = [System.Text.Encoding]::GetEncoding("shift_jis")
$utf8 = New-Object System.Text.UTF8Encoding $false
$t = [System.IO.File]::ReadAllText("in.txt", $sjis)
[System.IO.File]::WriteAllText("out.txt", $t, $utf8)
```

**上流での扱い**: スコープ内の可能性が高い (読書体験を直接改善)。
中国語 (GB18030)、韓国語 (EUC-KR) でも同じ需要。

### 6.6 【F-6】日本語UIの描画性能 — ✅ 原因特定・対策済み

#### 原因 (計装による実測で確定)

```
CJK文字を含む文字列 → SDフォントへ経路変更 (resolveTextFontId)
  → UI経路には prewarm が存在しないため interval 表が空
    → 全グリフが必ずミス
      → 1グリフごとに openFileForRead + 2 seek + 2 read
        → キャッシュは overflow リング 8スロットのみ
```

**システムタブだけが収束しない理由**: 異なり字数 91 > リング容量。
古典的なスラッシング。

#### 誤っていた仮説 (記録として残す)

| 仮説 | 結果 |
|---|---|
| フォントファイルが大きいから遅い | **誤り**。8/10pt を 97.5% 削減しても改善せず |
| `truncatedText` の O(n²) が効いている | **誤り**。全41フレームで `truncate_loop entered=0` |
| 行数が多いから遅い | **誤り**。異なり字数がリング容量を超えているため |

#### 対策と効果

`SdCardFont.h` の `OVERFLOW_CAPACITY` を 8 → 128。

| | cap=64 | cap=128 |
|---|---|---|
| グリフミス | 82 | **0** |
| ヒット率 | 80% | **100%** |
| SD I/O | 949 ms | **0 ms** |
| **フレーム総時間** | **1546 ms** | **577 ms** |

577ms = E-Ink 転送 548ms + 計算 29ms。**物理限界に到達。**

#### ⚠️ UI サブセット焼き込みによる影響

**§4.1 の設計では、UI 文字列が SD 経路を通らなくなる。**
したがって **F-6 の問題自体が UI からは消える。**

ただし**ファイル名・書名は本文フォント (SD) 経由**のままなので、
リング容量の問題はファイルブラウザ等に残る。cap=128 は維持する。

### 6.7 【F-7】TXT の折り返しが O(n²)

#### 原因 (特定済み)

`TxtReaderActivity.cpp:252-268`:

```cpp
size_t breakPos = line.length();
while (breakPos > 0 && renderer.getTextAdvanceX(
         cachedFontId, line.substr(0, breakPos).c_str(), REGULAR) > viewportWidth) {
  size_t spacePos = line.rfind(' ', breakPos - 1);
  if (spacePos != npos && spacePos > 0) breakPos = spacePos;  // 英語: 単語単位で飛ぶ
  else { breakPos--; ... }                                     // 日本語: 1文字ずつ後退
}
```

400文字の段落を30文字幅で折り返す場合、最初の1行を決めるのに
**約370反復 × 平均215文字 ≈ 8万回のコードポイント走査と370回のヒープ確保**。

さらに `:282` の `line = line.substr(skipChars)` で O(n²) の memcpy が乗る。

#### ⚠️ 「開く時」と「ページ送り」は別問題

| | コスト | 原因 |
|---|---|---|
| ページ送り | **144ms** (compute の 11%) | 当該ページ分の折り返し |
| **開く時** | **10分〜40分の報告あり** | `buildPageIndex()` が全ファイルを走査。**総ページ数分累積** |

**上流 Issue #2650 が空席** (修正 PR #2158 は著者が自己クローズ、以降誰も引き継がず)。

**フォークで修正する。**上流の Phase 1 (パフォーマンス・クリーンアップ) にも
合致するため、修正後に PR として出す価値がある。

## 附録C: フォントのライセンス

| フォント | ライセンス | 注意点 |
|---|---|---|
| UDEV Gothic | SIL OFL 1.1 | **Reserved Font Name "UDEV Gothic"** |
| Noto Serif JP | SIL OFL 1.1 | Google Fonts は RFN 非設定が原則。ただし Adobe 由来 (Source Han) は要確認 |

**OFL の定義では、Modified Version に「フォーマットの変更、あるいは新しい環境への
移植」が含まれる。**TTF → `.cpfont` への変換はこれに該当するため、
**生成した `.cpfont` は Modified Version。**

したがって:

- **個人利用は制限なし**
- **再配布時は RFN のあるフォントを改名する必要がある**
- 各コピーに著作権表示とライセンス全文を同梱する必要がある
  (UDEVGothic の場合、派生元の BIZ UDゴシック / JetBrains Mono 分も)

**RFN が制限するのは名前のみで、再配布そのものは自由。**

> ### ⚠️ v0.5 での新たな論点
>
> **UI サブセットを Flash に焼き込む場合、それも「再配布」に該当する。**
> ファームウェアバイナリにフォントデータが含まれるため、
> **ライセンス表示の同梱と、RFN 対象フォントの改名が必要。**
> 焼き込むフォントの選定時に、この点を確認すること。

## 附録D: 既存フォント構成 (v0.4 時点。参考記録)

```
/fonts/NotoSerifJP/
  NotoSerifJP_8.cpfont      51 KB  UDEVGothic 軽量(338文字)  ← UI 小文字・著者行
  NotoSerifJP_10.cpfont     68 KB  UDEVGothic 軽量           ← UI リスト行
  NotoSerifJP_12.cpfont  3,754 KB  UDEVGothicHS フル         ← UI 見出し + 本文Small
  NotoSerifJP_14.cpfont  4,934 KB  Noto Serif JP Medium      ← 本文 Medium
  NotoSerifJP_16.cpfont  6,119 KB  Noto Serif JP Medium      ← 本文 Large
  NotoSerifJP_18.cpfont  7,620 KB  Noto Serif JP Medium      ← 本文 Extra Large
```

**同一ファミリー内でサイズごとに書体を混在させる手法**が実機で動作確認済み。
公式ドキュメントに記載のない使い方。

**成立する理由**: インターバルテーブルはサイズ(ファイル)単位でファミリー単位ではなく、
フォントIDが内容ハッシュを含むため、サイズごとに中身が違ってもIDが衝突しない。

> **v0.5 での位置づけ**: §4.1 の UI/本文分離により、この構成は**本文専用**になる。
> 8/10/12pt を UI 用に確保する必要がなくなるため、
> **本文フォントは 12〜18pt のみで足りる。**
