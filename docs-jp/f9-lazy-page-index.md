# F-9: ページ索引の遅延構築と、読書位置のオフセット化 — 設計メモ

**作成日**: 2026-08-13
**位置づけ**: `docs-jp/xteink-x4-jp-firmware-spec-v0_6.md` §6.7 (F-7) の続き
**状態**: **設計確定。実装未着手。**

---

## 0. なぜやるのか

F-7 と段階A で、112KB の青空文庫ファイルの初回オープンは **約7分 → 15〜20秒**になった。
実用にはなったが、**まだ待ち時間として認識される。**

| ファイルサイズ | 現状の初回オープン |
|---|---|
| 112KB (『最終戦争論』217ページ) | **15〜20秒** |
| 1MB 級の長編 | **約2分** (推定) |

青空文庫には長編がいくらでもある。**2分は「待てる/待てない」の境界を跨ぐ。**

**目標: 索引の完成を待たずに本を開けるようにする。**

---

## 1. 中核の発想: 位置を「ページ番号」ではなく「バイトオフセット」で持つ

### 行き詰まりの原因

現在、読書位置は `progress.bin` に**ページ番号**で保存されている。

```cpp
// saveProgress()
data[0] = currentPage & 0xFF;
data[1] = (currentPage >> 8) & 0xFF;
data[2] = 0;   // 未使用
data[3] = 0;   // 未使用
```

**ページ番号は全ページを数え終わらないと意味を持たない。**
だから「180ページ目から再開」には180ページ分の索引が要る。ここが遅延構築を阻んでいた。

### 解決

**バイトオフセットは索引がゼロでも意味を持つ。**
しかも `render()` は元々オフセットから描いている。

```cpp
size_t offset = pageOffsets[currentPage];      // ← この変換をやめる
loadPageAtOffset(offset, currentPageLines, nextOffset);
```

**保存したオフセットをそのまま渡せば、索引が1件もなくても続きから表示できる。**

### 副産物: 既存の不正確さが直る

いまは**フォントサイズを変えると読書位置がずれる。**
文字を大きくすればページ数が増えるので、旧ページ180と新ページ180は別の場所を指す。

**オフセットで持てば、レイアウトが変わっても同じ文章から再開できる。**
これは今ある不正確さの根本的な解消でもある。

---

## 2. 索引が無くてもできること / できないこと

| 操作 | 索引なし | 根拠 |
|---|---|---|
| 開いた位置を表示 | ✅ | 保存オフセットから直接描く |
| **次のページへ** | ✅ | `loadPageAtOffset()` が `nextOffset` を返す |
| **前のページへ (再開直後、16ページまで)** | ✅ | **直近16ページのオフセットを保存する** (§3) |
| 前のページへ (通ってきた道) | ✅ | **セッション中の配列**から (§4) |
| 前のページへ (通っていない道) | ❌ | 「読込み中」で拒否 |
| 総ページ数の表示 | ❌ | **完成まで隠す** |
| 位置ジャンプ (n%へ) | ❌ | 完成まで拒否 |
| 末尾判定 | ✅ | `nextOffset >= fileSize` で分かる |

> **総ページ数を隠すのと、位置ジャンプを拒否するのは同じ理由である。**
> 総数が分からないのに「50%へ飛ぶ」を許しても、ユーザーにとって意味がない。

## 3. `progress.bin` の形式

### 現状と余地

- 4バイト書いているが、**うち2バイトは未使用**
- `ProgressFile::writeAtomic(cachePath, data, len)` は **`len` が任意**。8バイトでも12バイトでも書ける
- 書き込みは一時ファイル + rename で壊れない (issue #2275 の対策済み)

### バイト数は制約にならない

オフセット1件は **4バイト** (uint32。4GB まで表せる)。

そして **SD は512バイトのセクタ単位で書く。** 4バイト書いても500バイト書いても、書き込みにかかる時間は同じである。

| 保存件数 | バイト数 | 書き込みコスト |
|---|---|---|
| 1件 | 4 B | 同じ |
| **16件** | **64 B** | **同じ** |
| 128件 | 512 B | 同じ (上限) |
| 129件 | 516 B | セクタ2つ分になる |

**128件まで無料。**

### 新形式 — 履歴を16件持つ

**直近16ページ分のオフセットをリングで保持する (64バイト)。**

再開直後から**16ページ戻れる。**「どこまで読んだっけ」と数ページ遡る行動は、本を再開したときの典型なので、ここが効く。

128件にしても使われないまま終わる。履歴が必要なのは**索引が追いつくまでの間だけ**で、217ページの本なら15〜20秒、1MB級でも2分。その間に人が読めるのは数ページである。

**新旧の判別はファイルサイズで行う。** 4バイトなら旧形式 (ページ番号)、それより大きければ新形式。
旧形式を読んだときは従来どおりページ番号として扱い、**索引が完成した時点で新形式へ書き換える。**

> ⚠️ **フォントサイズを変えると、保存した履歴は旧レイアウトのページ境界になる。**
> 表示の開始位置としては有効で、往復 (§5) も成立するが、新しいページ区切りとは少しずれる。
> **壊れはせず、現在すでにある位置ずれと同程度の不正確さ**なので許容する。

---

## 4. セッション中の履歴は無料

**すでに表示したページのオフセットは、こちらが知っている。**
ページを送るたびに配列へ積むだけでよい。

```
開いた位置 → [X]
1回送る    → [X, Y]
2回送る    → [X, Y, Z]     ← 戻るときは後ろから取り出す
```

64ページ分持っても **256 バイト**。索引が届いていない領域でも、**通ってきた道は全部戻れる。**

---

## 5. 往復が正確であることの保証

**「戻る → 進む」で必ず元の位置に返る。**

`loadPageAtOffset(prevOffset, ...)` が返す `nextOffset` は、**定義上いま居た位置そのもの**である。
同じ関数に同じ入力を与えるので、ずれようがない。

**追加の索引を1件も作らずに往復できる。**

---

## 6. 決定事項 (2026-08-13)

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 索引構築中の総ページ数 | **完成まで隠す** | 育っていく数字 (`5/12` → `5/217`) は混乱を招く |
| 2 | 未構築範囲へのナビゲーション | **拒否し「読込み中」を出す** | 総数が分からなければ位置ジャンプに意味がない |
| 3 | 途中で本を閉じたときの部分索引 | **捨てる** | 「未完了」の印を持つ複雑さに見合わない |
| 4 | キャッシュ無効化からの再開 | **オフセットで再開。特別扱いなし** | §1 の方式なら場合分けが不要になる |

### 決定4 の経緯 (記録)

当初「キャッシュ無効化時は1ページ目から」という案があったが、**採らなかった。**

`saveProgress()` は描画のたびに走るため、1ページ目から始めると**その瞬間に `progress.bin` が 0 で上書きされ、読書位置が消える。**

そして**キャッシュの無効化は珍しくない。**

| 検証項目 | 何をすると変わるか |
|---|---|
| `CACHE_VERSION` | ファームウェアの更新 |
| `viewportWidth` | 画面余白、画面の向き |
| **`linesPerPage`** | **フォントサイズ**、余白、向き |
| **`fontId`** | **書体・サイズの変更** |
| `screenMargin` | 画面余白 |
| 段落揃え | 両端揃え ↔ 左揃え |

**フォントサイズを変えると必ず消える。**電子書籍端末では日常操作である。

> **重要**: 読書位置 (`progress.bin`) はキャッシュの検証対象ではないため、
> **現在の実装では、フォントを変えても位置は失われない** (近くのページに戻る)。
> 「1ページ目から」はこの性質を壊すことになる。**新しい事故を作り込むので却下した。**

## 7. 実装の骨格

| 層 | 変更 |
|---|---|
| `progress.bin` | 形式をオフセット2件に。旧形式からの移行あり |
| `saveProgress()` / `loadProgress()` | ページ番号ではなくオフセットを読み書き |
| `TxtReaderActivity` の状態 | `currentOffset` を真とする。`currentPage` は索引完成後の表示用 |
| `loop()` | ページ移動をオフセットで行う。未構築範囲への移動を拒否 |
| `buildPageIndex()` | 一括構築をやめ、**`loop()` から少しずつ進める** |
| ステータスバー | 索引未完成時は総ページ数を出さない |

### スレッドは要らない

`Activity` に受け皿がある。

```cpp
virtual void loop() {}                          // 毎周回呼ばれる
virtual bool skipLoopDelay() { return false; }  // 待ちを飛ばせる
```

`buildPageIndex()` には既に `vTaskDelay(1)` で他タスクに譲る処理があるので、
**`loop()` が回るたびに数ページずつ進める協調方式**が既存の構造に合う。
プリエンプティブなスレッドを持ち込む必要がなく、データ競合も起きない。

E-Ink の書き換えに 550ms〜1.7s、人が1ページ読むのに数十秒かかるので、
**15〜20秒は最初の1〜2ページを読んでいる間に隠れきる。**

## 8. ⚠️ 注意点

### 8.1 段階A のファイルハンドルとの衝突

段階A (`c2683e5c`) で `buildPageIndex()` の間だけファイルを開いたままにした。
**スコープを限定した理由は、F-2 のチェックボックス書き戻しが同じファイルを `O_RDWR` で開くためである。**

索引構築が `loop()` にまたがると、**ハンドルを長時間保持することになり、この前提が崩れる。**

**対策の候補**: `loop()` の1回ぶんの構築のたびに開いて閉じる (段階A の効果が薄れる)、
あるいはトグル時に一時的にハンドルを手放す。**実装前に決めること。**

### 8.2 索引完成時のスナップ

索引ができた時点で、保存オフセットがどのページに属するかを二分探索で求めて番号を確定する。
**そのとき現在位置が最大1ページ弱ずれる可能性がある。**

### 8.3 等価性の検証

**リーダーの中核に手を入れるため、F-7 と同じ検証を組むこと。**

比べるものは単純で、**「一括構築した `pageOffsets`」と「遅延構築した `pageOffsets`」が完全一致するか**でよい。
1件でも違えばページ境界がずれている。

**シリアルが使えない端末なので、結果は SD のファイルに書き出すこと** (F-7 と同じ方式)。

## 10. 関連する保留項目

F-9 とは独立に、索引構築そのものを速くする手が2つ残っている。

| # | 内容 | 見込み |
|---|---|---|
| 1 | **チャンクの使い回し** — 8KB 読んで1ページ分 (約900B) しか使っていない。約9倍の重複 | 17秒 → 3〜5秒 |
| 2 | **等幅フォントの表引き省略** — `ensureSdCardFontReady()` が残りコストの大半 (217 × 70ms ≈ 15秒)。フォントが均一幅と分かれば省ける | 未知。`.cpfont` に均一幅の情報があるかの調査から |

**F-9 が入れば体感はゼロになるので、これらの優先度は下がる。**
ただし裏で走る時間が短いほどバッテリーには優しい。
