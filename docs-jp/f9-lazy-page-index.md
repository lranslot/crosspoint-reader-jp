# F-9: ページ索引の遅延構築と、読書位置のオフセット化 — 設計メモ

**作成日**: 2026-08-13
**改訂**: 2026-08-22 (v0.3)
**位置づけ**: `docs-jp/xteink-x4-jp-firmware-spec-v0_7.md` §6.7 (F-7) の続き
**状態**: **フェーズ1 完了 (`b6edc24f`)。フェーズ2 は設計確定・未着手。**

---

## 0. なぜやるのか

F-7 と段階A で、112KB の青空文庫ファイルの初回オープンは **約7分 → 15〜20秒**になった。
実用にはなったが、**まだ待ち時間として認識される。**

| ファイルサイズ | 現状の初回オープン |
|---|---|
| 112KB (『最終戦争論』217ページ) | **15〜20秒** |
| 1MB 級の長編 | **約2分** (推定) |

青空文庫には長編がいくらでもある。**2分は「待てる/待てない」の境界を跨ぐ。**

**目標: 索引の完成を待たずに本を開けるようにする。**

---

## 1. 中核の発想: 位置を「ページ番号」ではなく「バイトオフセット」で持つ

> **フェーズ1 として実装済み (`b6edc24f`)。**以下は記録として残す。

### 行き詰まりの原因

読書位置は `progress.bin` に**ページ番号**で保存されていた。

```cpp
// 旧 saveProgress()
data[0] = currentPage & 0xFF;
data[1] = (currentPage >> 8) & 0xFF;
data[2] = 0;   // 未使用
data[3] = 0;   // 未使用
```

**ページ番号は全ページを数え終わらないと意味を持たない。**
だから「180ページ目から再開」には180ページ分の索引が要る。ここが遅延構築を阻んでいた。

### 解決

**バイトオフセットは索引がゼロでも意味を持つ。**
しかも `render()` は元々オフセットから描いている。

```cpp
size_t offset = pageOffsets[currentPage];      // ← この変換をやめた
loadPageAtOffset(offset, currentPageLines, nextOffset);
```

**保存したオフセットをそのまま渡せば、索引が1件もなくても続きから表示できる。**

### 副産物: 既存の不正確さが直った

フォントサイズを変えるとページ数が変わるため、旧ページ180と新ページ180は別の場所を指していた。
**オフセットで持てば、レイアウトが変わっても同じ文章から再開できる。**

ただしオフセットは新しいレイアウトのページ**途中**を指すため、そのままでは
最初のページ送りで文章が重複する。**索引が使える状態になった直後に、
そのオフセットが属するページの先頭へ吸着させる**ことで解決した (`d5e0ed91`)。

## 2. 索引が無くてもできること / できないこと

| 操作 | 索引なし | 根拠 |
|---|---|---|
| 開いた位置を表示 | ✅ | 保存オフセットから直接描く |
| **次のページへ** | ✅ | `loadPageAtOffset()` が `nextOffset` を返す |
| **前のページへ (再開直後、16ページまで)** | ✅ | **直近16ページのオフセットを保存する** (§3) |
| 前のページへ (通ってきた道) | ✅ | **セッション中の配列**から (§4) |
| 前のページへ (通っていない道) | ❌ | 「読込み中」で拒否 |
| **総ページ数の表示** | ✅ | **「推定」を付けて出す** (§6 決定1、v0.3 で変更) |
| 位置ジャンプ (n%へ) | ❌ | 完成まで拒否 (§6 決定2) |
| 末尾判定 | ✅ | `nextOffset >= fileSize` で分かる |

## 3. `progress.bin` の形式

> **フェーズ1 として実装済み。**

### バイト数は制約にならない

オフセット1件は **4バイト** (uint32。4GB まで表せる)。
そして **SD は512バイトのセクタ単位で書く。** 4バイト書いても500バイト書いても、
書き込みにかかる時間は同じである。

| 保存件数 | バイト数 | 書き込みコスト |
|---|---|---|
| 1件 | 4 B | 同じ |
| **16件** | **64 B** | **同じ** |
| 128件 | 512 B | 同じ (上限) |
| 129件 | 516 B | セクタ2つ分になる |

**128件まで無料。**

### 実装された形式

**8バイトのヘッダ + 直近16ページ分のオフセット (4バイト × 最大16件)。**
最大 72 バイト。再開直後から**16ページ戻れる。**

**新旧の判別はファイルサイズで行う。** 4バイトなら旧形式 (ページ番号)、
それより大きければ新形式。旧形式は次回オープン時に移行する。

### レイアウト変更時の履歴の扱い (フェーズ2 への前提)

**フォントサイズを変えると、保存済みの履歴は旧レイアウトのページ境界を指す。**
末尾以外の15件は新しいページの途中を指すことになる。

フェーズ1 では履歴を「前へ」に使っていないため無害だが、**フェーズ2 で使い始めた
瞬間に、§1 で直したのと同じ重複が「前へ」で再発する。**

そのため `indexCacheRejected` が真のとき、**履歴を最新1件に切り詰めている** (`d5e0ed91`)。
**フェーズ2 はこの前提の上に立てる。**

---

## 4. セッション中の履歴は無料

**すでに表示したページのオフセットは、こちらが知っている。**
ページを送るたびに配列へ積むだけでよい。

```
開いた位置 → [X]
1回送る    → [X, Y]
2回送る    → [X, Y, Z]     ← 戻るときは後ろから取り出す
```

64ページ分持っても **256 バイト**。索引が届いていない領域でも、**通ってきた道は全部戻れる。**

---

## 5. 往復が正確であることの保証

**「戻る → 進む」で必ず元の位置に返る。**

`loadPageAtOffset(prevOffset, ...)` が返す `nextOffset` は、**定義上いま居た位置そのもの**である。
同じ関数に同じ入力を与えるので、ずれようがない。

**追加の索引を1件も作らずに往復できる。**

## 6. 決定事項

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 索引構築中の総ページ数 | **「推定」を付けて出す** (v0.3 で変更) | 下記 |
| 2 | 未構築範囲へのナビゲーション | **拒否し「読込み中」を出す** | 位置ジャンプに意味がない。**加えて §7.3 の事故を構造的に防ぐ** |
| 3 | 途中で本を閉じたときの部分索引 | **捨てる** | 「未完了」の印を持つ複雑さに見合わない |
| 4 | キャッシュ無効化からの再開 | **オフセットで再開。特別扱いなし** | §1 の方式なら場合分けが不要になる |

### 決定1 の変更 (2026-08-22)

**v0.2 では「完成まで隠す」だった。**理由は「育っていく数字 (`5/12` → `5/217`) は混乱を招く」。

**当時は存在しなかった仕組みが、いまはある。**

`BaseTheme::drawStatusBar()` は `pageCountEstimated` を受け取り、真なら
`STR_ESTIMATE_PREFIX` をページ数の左に描く。EPUB がスパイン構築中に使っている経路で、
**日本語では「推定」と出る** (`4187ac93`)。

| | 隠す (旧決定) | 推定を付けて出す (新決定) |
|---|---|---|
| 見え方 | `12` だけ | `推定 12/45` → `推定 12/180` → `12/217` |
| 正直さ | 情報が無い | **暫定であることが画面に書いてある** |
| 実装 | **隠すための分岐が要る** | **`pageCountEstimated` に `true` を渡すだけ** |
| EPUB との一貫性 | 割れる | **揃う** |

**分岐を増やさずに済むことが決め手。**隠す実装は「いつ隠すか」「いつ出すか」の
条件を持つことになり、索引完成の判定と二重管理になる。

### 決定4 の経緯 (記録)

当初「キャッシュ無効化時は1ページ目から」という案があったが、**採らなかった。**

`saveProgress()` は描画のたびに走るため、1ページ目から始めると**その瞬間に
`progress.bin` が 0 で上書きされ、読書位置が消える。**

そして**キャッシュの無効化は珍しくない。**

| 検証項目 | 何をすると変わるか |
|---|---|
| `CACHE_VERSION` | ファームウェアの更新 |
| `viewportWidth` | 画面余白、画面の向き |
| **`linesPerPage`** | **フォントサイズ**、余白、向き |
| **`fontId`** | **書体・サイズの変更** |
| `screenMargin` | 画面余白 |
| 段落揃え | 両端揃え ↔ 左揃え |

**フォントサイズを変えると必ず消える。**電子書籍端末では日常操作である。

## 7. EPUB から学んだこと — **フェーズ2 の設計制約**

> **2026-08-22 追加。**EPUB リーダーは既に遅延組版を実装している。
> **フェーズ2 が作ろうとしている構造と同型**であり、実機で計測した結果、
> **踏んではいけない罠が3つ**見つかった。

### 7.1 実測値

`/build-timing.txt` に出力して回収した (計装は計測後に撤去済み)。

```
spine=0 pages=128 ticks=62 totalMs=29623 maxTickMs=957  avgTickMs=477  syncCalls=0
spine=0 pages=207 ticks=0  totalMs=48101 maxTickMs=2613 avgTickMs=1924 syncCalls=25
```

| 導出 | 値 |
|---|---|
| **EPUB 1ページの組版** | **約 232 ms** (29623/128 = 231.4、48101/207 = 232.4。**別の本で一致**) |
| 背景ティック (2ページ) | 平均 477 ms / 最大 957 ms |
| 同期チャンク (8ページ) | 平均 1,924 ms / 最大 2,613 ms |

TXT の索引構築は F-7 + 段階A 後で **217ページ 15〜20秒 ≒ 1ページ 70〜90 ms**。
EPUB より速いが、**桁は同じ**である。

### 7.2 罠1: 入力が消える (対処済み・フェーズ2 の前提条件)

`InputManager::update()` は `pressedEvents` を**前回との差分**として毎回作り直す。
**イベントとして溜まらない。**

```cpp
void InputManager::update() {
  pressedEvents = 0;              // 毎回クリア
  ...
}
void InputManager::applyStateChange(const uint8_t state, ...) {
  pressedEvents = state & ~currentState;   // 代入。前回のイベントは消える
```

**`update()` の呼び出し間隔より短い押下は、原理的に存在しなかったことになる。**
人がボタンを押して離すのは 100〜200 ms なので、**477 ms の盲目時間は押下を丸ごと飲む。**

> **索引を裏で進める以上、ループの1周は必ず伸びる。**
> ラッチが無ければ、TXT でも「索引構築中はボタンが効かない」が確実に起きた。

**対処済み** (`010c4603`): `MappedInputManager` が物理ピン単位で押下・解放をラッチし、
最初の読み取りで消費する。1500 ms で期限切れ、アクティビティ遷移で全破棄。

**フェーズ2 はこの上に立つ。**

### 7.3 罠2: `loop()` に戻らない同期ループを作らないこと ★最重要

2行目の `ticks=0 / syncCalls=25` は、**背景ティックが一度も走らず、
207ページ全部を `render()` 内の `while` が作った**という意味である。

該当は「保存位置まで一気に組版する」経路。章の終盤で閉じた本を開き直すと発動する。

```cpp
while (!section->isBuildComplete() &&
       (... : static_cast<int>(section->pageCount) <= target)) {
  section->buildSomeMore(BUILD_PAGES_PER_CHUNK);
}
```

**この 48 秒間、`loop()` に戻らないため `gpio.update()` が一度も呼ばれない。**
**ラッチがあっても救えない。**入力が到達する経路そのものが動いていない。

> **フェーズ2 では、索引構築を `loop()` に戻らないループで回してはならない。**
> 決定2 (未構築範囲へのナビゲーションを拒否する) は、当初「総数が分からなければ
> 位置ジャンプに意味がない」という理由で決めたが、**実測により、
> この事故を構造的に防ぐ決定でもあったことが分かった。**

### 7.4 罠3: ティックの位置

EPUB の `loop()` では、組版ティックが**ボタン検出の約200行手前**にある。
毎周、ボタンを読む前に組版を待たされる。

**TXT では最初からボタン検出の後ろに置く。**ゼロコストで、盲目時間が
「次の周まで」から「同じ周のうち」に変わる。

### 7.5 ティックの粒度

EPUB は `BACKGROUND_BUILD_PAGES_PER_TICK` を 2 → 1 に下げ、
背景ティックの盲目時間が **477 ms → 176 ms** になった (実測)。

TXT は 1ページ 70〜90 ms なので、**1ページ/ティックなら盲目時間は 100 ms 未満**に収まる。
**最初から1ページ単位で進めること。**

## 8. 実装の骨格

| 層 | 変更 | 状態 |
|---|---|---|
| `progress.bin` | 形式をオフセットに。旧形式からの移行 | ✅ フェーズ1 |
| `saveProgress()` / `loadProgress()` | オフセットを読み書き | ✅ フェーズ1 |
| `TxtReaderActivity` の状態 | `currentOffset` を真とする | ✅ フェーズ1 |
| `loop()` | ページ移動をオフセットで行う | ✅ フェーズ1 |
| **`buildPageIndex()`** | **一括構築をやめ、`loop()` から1ページずつ進める** | **フェーズ2** |
| **ティックの位置** | **ボタン検出より後ろ** (§7.4) | **フェーズ2** |
| **ステータスバー** | **索引未完成時は `pageCountEstimated = true`** (§6 決定1) | **フェーズ2** |
| **未構築範囲への移動** | **拒否して「読込み中」** (§6 決定2 / §7.3) | **フェーズ2** |

### スレッドは要らない

`Activity` に受け皿がある。

```cpp
virtual void loop() {}                          // 毎周回呼ばれる
virtual bool skipLoopDelay() { return false; }  // 待ちを飛ばせる
```

`buildPageIndex()` には既に `vTaskDelay(1)` で他タスクに譲る処理があるので、
**`loop()` が回るたびに1ページずつ進める協調方式**が既存の構造に合う。
プリエンプティブなスレッドを持ち込む必要がなく、データ競合も起きない。

E-Ink の書き換えに 550ms〜1.7s、人が1ページ読むのに数十秒かかるので、
**15〜20秒は最初の1〜2ページを読んでいる間に隠れきる。**

## 9. ⚠️ 注意点

### 9.1 段階A のファイルハンドル — **解決済み**

段階A (`c2683e5c`) で `buildPageIndex()` の間だけファイルを開いたままにした。
**スコープを限定した理由は、F-2 のチェックボックス書き戻しが同じファイルを
`O_RDWR` で開くためである。**

索引構築が `loop()` にまたがると、ハンドルを長時間保持することになり、
この前提が崩れる — はずだった。

**フェーズ1 で `Txt::writeByteAt()` を新設し、書き込みの前に
`endSequentialRead()` を呼ぶようにした。**同じパスを二重に開くことがなくなったので、
**フェーズ2 はハンドルを保持したままでよい。**

### 9.2 索引完成時のスナップ — **解決済み**

索引ができた時点で、保存オフセットがどのページに属するかを二分探索で求めて番号を確定する。
そのとき現在位置が最大1ページ弱ずれる。

**フェーズ1 でこの吸着を実装した** (`d5e0ed91`)。`indexCacheRejected` のときは
履歴も最新1件に切り詰める (§3)。**フェーズ2 では同じ処理が
「索引が完成した時点」に移るだけである。**

### 9.3 等価性の検証

**リーダーの中核に手を入れるため、F-7 と同じ検証を組むこと。**

比べるものは単純で、**「一括構築した `pageOffsets`」と「遅延構築した `pageOffsets`」が
完全一致するか**でよい。1件でも違えばページ境界がずれている。

**シリアルが使えない端末なので、結果は SD のファイルに書き出すこと** (F-7 / F-8 と同じ方式)。

### 9.4 折り返しに触れるときの前提

`loadPageAtOffset()` と `findWrapOffset()` には過去に踏んだ罠の対策が積み重なっている。
**フェーズ2 で折り返しそのものを書き換える必要は無いはずだが、触る場合は
仕様書 §6.7 と `f2-markdown-checkbox.md` §2.4 / §3.3 / §3.4 を先に読むこと。**

## 11. 関連する保留項目

F-9 とは独立に、索引構築そのものを速くする手が2つ残っている。

| # | 内容 | 見込み |
|---|---|---|
| 1 | **チャンクの使い回し** — 8KB 読んで1ページ分 (約900B) しか使っていない。約9倍の重複 | 17秒 → 3〜5秒 |
| 2 | **等幅フォントの表引き省略** — `ensureSdCardFontReady()` が残りコストの大半 (217 × 70ms ≈ 15秒)。フォントが均一幅と分かれば省ける | 未知。`.cpfont` に均一幅の情報があるかの調査から |

**F-9 が入れば体感はゼロになるので、これらの優先度は下がる。**
ただし裏で走る時間が短いほどバッテリーには優しい。

### EPUB 側に残った課題 (F-9 の範囲外)

§7.3 の同期ループ (48秒間、入力が到達しない) は **EPUB 側に残っている。**
`render()` の `while` を `loop()` に返す構造改修が必要で、
**フェーズ2 とまったく同じ形の課題**である。フェーズ2 の実装で得た形を
EPUB に持ち込むのが順当。上流への還元価値もある。
