## 0. 何を作るのか

**TXT リーダーで日本語を縦書きに組む。**右から左へ列が進み、各列は上から下へ。

段階1 の範囲は §6 で定義する。**ルビ (F-8 段階2) は含まない。**

### なぜ縦書きを先にやるのか

**縦書きは「1ページ = 固定数のマス」という前提を保ち、ルビはそれを壊す**
(仕様書 §4.2)。逆順にすると、ルビで可変行高を入れた上に縦書きを乗せることになり、
**ルビの作り直しが 2 回**になる。

## 1. 有利な既知の事実

### 1.1 グリフ描画はすでに任意座標を取る

```cpp
// lib/GfxRenderer/GfxRenderer.cpp:379
enum class TextRotation { None, Rotated90CW };

template <TextRotation rotation = TextRotation::None>
static void renderCharImpl(const GfxRenderer& renderer, GfxRenderer::RenderMode renderMode,
                           const EpdFontFamily& fontFamily, const uint32_t cp,
                           int cursorX, int cursorY, bool pixelState, EpdFontFamily::Style style);
```

座標計算は x と y が対称:

```cpp
outerBase = cursorY - top;    // screenY = outerBase + glyphY
innerBase = cursorX + left;   // screenX = innerBase + glyphX
```

**1 グリフを任意の `(x, y)` にステートレスに置ける。**
したがって「グリフを回さずに下へ積む」描画に**新しいビットマップ転送コードは要らない。**
`x` を固定して `y` を送り分だけ増やしながら `renderCharImpl<None>` を呼ぶだけ。

> **`drawTextRotated90CW()` と `anchorOverRotated90CW()` は画面回転 (側面ボタンの
> ラベル) 用であり、縦書き用ではない。**字形自体を 90° 回すので、
> そのまま使うと日本語が横倒しになる。使うのは**その下の `renderCharImpl`** の方。

**`renderCharImpl` は `.cpp` 内の `static`。**新しい公開メソッドは
`GfxRenderer.cpp` の中に置く必要がある (他ファイルからは呼べない)。

### 1.2 幅と高さはすでに独立したスカラ

```cpp
// TxtReaderActivity::initializeReader()
viewportWidth  = screenWidth - orientedMarginLeft - orientedMarginRight - markerWidth;
const int viewportHeight = screenHeight - orientedMarginTop - orientedMarginBottom;
linesPerPage = viewportHeight / renderer.getLineHeight(cachedFontId);
```

**互いを参照していない。**`findWrapOffset(fontId, text, maxWidth, ...)` の
`maxWidth` も**軸を知らない単なるスカラ**である。

### 1.3 SD フォント経路はカーニングもリガチャも引かない

`getTextAdvanceX()` / `findWrapOffset()` の SD 高速路は **advance table の
表引き 1 回の素の加算**で、`font.getKerning()` も `applyLigatures()` も呼ばない。

**F-7 で苦労した差分丸め・リガチャ不可分・RTL フォールバックは、
すべて組み込みフォント経路 (= ラテン文字) の話だった。**
日本語は SD フォント経路しか通らない。

### 1.4 ★ 全角は完全な等幅 — これが最も効く

**SD の `.cpfont` を直接読んだ実測値** (仕様書 §3.6):

| pt | `advanceY` | `ascender` | `descender` | **全角 em** |
|---|---|---|---|---|
| 8 | 19 | 16 | −4 | **16.6875 px** |
| 10 | 24 | 20 | −5 | **20.8125 px** |
| 12 | 29 | 24 | −6 | **25.0000 px** |
| 14 | 42 | 34 | −9 | **29.1875 px** |
| 16 | 48 | 39 | −10 | **33.3125 px** |
| 18 | 54 | 44 | −11 | **37.5000 px** |

**2026-10-27 に全 pt を実測** (`scripts/cpfont_metrics.py`)。
**全角 em は pt に完全比例する** (pt x 150/72)。
**`advanceY` は比例しない** — 8/10/12 pt で em の 1.14〜1.16 倍、
14/16/18 pt で **1.44 倍**。この 6 面は同一設計のフォントではない
(仕様書 §3.6)。

**かな・漢字 18 文字を測って advance が 1 種類しかなかった。**完全な等幅である。

#### 等幅性が縦書きに効く度合い — 横書きより*簡単*になる

| | 横書き | **縦書き (全角のみ)** |
|---|---|---|
| 1 行/列に入る数 | **文字ごとに幅を積む必要がある** (プロポーショナル) | **`viewportHeight / em` の割り算 1 回** |
| 折り返し位置 | `findWrapOffset()` で前から積む | **文字数で割るだけ。測定が不要** |
| 必要な API | `findWrapOffset` / `getTextAdvanceX` | **なし (純粋な整数演算)** |

**全角だけなら `findWrapOffset()` を呼ぶ必要すらない。**
`charsPerColumn = viewportHeight / em` を一度求めれば、
あとは「n 文字ごとに改列」で済む。

> **ただし素のままでは「全角だけなら」である。**実際の青空文庫テキストには
> ASCII (数字・英字・記号) と半角カナ (U+FF61-FF9F) が混ざる。
>
> **§3.5 で「すべての文字を 1 マスとして扱う」と決めたので、
> 混在しても割り算のモデルが保たれる。**これが段階1 を安くしている核心。

#### F-9 と F-7 の遺産

| 既存の資産 | 縦書きでの扱い |
|---|---|
| **読書位置がバイトオフセット** (F-9 フェーズ1) | **そのまま使える。**軸に依存しない |
| **索引の遅延構築** (F-9 フェーズ2) | **そのまま使える。**§2.4 参照 |
| `findWrapOffset()` (F-7) | 全角のみなら不要。混在時は縦書き版が要る (§2.3) |
| `pageOffsets` / `index.bin` | 検証項目の追加が必要 (§2.5) |

## 2. 行・ページのモデル

### 2.1 横書きの現状

```
linesPerPage = viewportHeight / lineHeight          // lineHeight = advanceY
loadPageAtOffset(offset, outLines, nextOffset)      // ちょうど linesPerPage 行を埋める
```

`outLines` は**視覚行**の配列。`renderPage()` が 1 行につき `drawText` 1 回で描く。

### 2.2 縦書きの対応物

**「視覚行」を「視覚列」に読み替える。**`outLines` の型も中身も変えない。

```
columnWidth    = em * COLUMN_RATIO    // 列の太さ。★ advanceY ではない (下記)
columnsPerPage = viewportWidth  / columnWidth
charsPerColumn = viewportHeight / em  // 全角等幅なので割り算 1 回 (§1.4)
```

#### ★ `columnWidth` を `advanceY` に紐づけてはならない (2026-10-27 変更)

**初版は `columnWidth = advanceY` だった。取り下げる。**

| # | 理由 |
|---|---|
| 1 | **`advanceY / em` がこの端末で 1.14〜1.16 と 1.44 に分かれている。**12 → 14 pt で列の間隔が飛ぶ |
| 2 | **しかもこれは利用者のフォント次第で任意の値を取る** (仕様書 §3.6)。フォントを替えただけで組版が崩れる |
| 3 | **`advanceY` は横組みの行送りであって、縦組みの列送りではない。**たまたま近い値なだけで、根拠が無い |

**12 → 14 pt で列数がどう動くか** (実測値から計算):

| モデル | 12 pt | 14 pt | 減少 |
|---|---|---|---|
| `advanceY` (初版) | 16 列 | **11 列** | **−31%** |
| `em x 1.3` | 14 列 | 12 列 | −14% |

**`em` 基準なら、列数は字の大きさだけで決まる。**
フォントの縦メトリクスという**利用者依存の量**が組版に混ざらない。

#### `COLUMN_RATIO` の候補

**12 pt (em 25 px) / viewport 464 x 754 px での実測ベースの計算。**
`charsPerColumn = 754 / 25 = 30 字`。

| 比 | `columnWidth` | 列数 | 1 ページの字数 | 横書き現状比 | 行間 |
|---|---|---|---|---|---|
| 1.0 | 25 | **18** | 540 | +15% | **0。列が密着する** |
| 1.15 | 29 | **16** | 480 | +3% | 0.15 em |
| **1.3** | **32** | **14** | **420** | **−10%** | **0.3 em** |
| 1.5 | 38 | **12** | 360 | −23% | 0.5 em |
| 1.75 | 44 | **10** | 300 | −36% | 0.75 em |

**横書きの現状**: 26 行 x 18 字 = **468 字/ページ** (12 pt)。

**日本語の縦組みの慣習**: 書籍の本文は**行間 0.5〜0.75 em
(= 比 1.5〜1.75)** が一般的。新聞や詰めた文庫で 1.2〜1.3。
**比 1.0 は列が密着するので読めない。**

> **⚠️ 慣習の値は紙の本のものである。**480 x 800 の電子ペーパーで
> 比 1.5 を採ると 1 ページ 360 字まで落ち、**ページ送りが 1.3 倍に増える。**
> 書き換えが 1〜2 秒かかる端末では、これは実際の不便になる。

### ★ 確定: `COLUMN_RATIO = 1.3` (2026-10-27)

0.3 em の間隔は列の区切りとして十分に見え、密度の損失は横書き比 −10% に収まる。
**12 pt で 14 列 x 30 字 = 420 字/ページ。**

#### 設定項目 — **`SETTINGS.lineSpacing` の enum を流用する**

**新しい設定は作らない。**`TIGHT` / `NORMAL` / `WIDE` の 3 段が既にあり、
UI も翻訳も揃っている。

**ただし既存の係数をそのまま掛けてはならない。**
`getReaderLineCompression()` が返すのは 0.95 / 1.0 / 1.1 で、
**幅が狭すぎて列数が動かない**:

| 案 | TIGHT | NORMAL | WIDE |
|---|---|---|---|
| 既存の係数を 1.3 に掛ける | 比 1.235 → **14 列** | 比 1.3 → **14 列** | 比 1.43 → 12 列 |
| **★ 縦書き専用の写像 (確定)** | **比 1.15 → 16 列** | **比 1.3 → 14 列** | **比 1.5 → 12 列** |

**既存係数だと TIGHT と NORMAL が同じ 14 列になり、設定が 2 段にしか
見えない。**縦書き専用の写像にすれば 3 段がそれぞれ別の結果になる。

```
縦書きの列幅:
  COLUMN_RATIO = { TIGHT: 1.15, NORMAL: 1.30, WIDE: 1.50 }[SETTINGS.lineSpacing]
  columnWidth  = round(em * COLUMN_RATIO)
```

#### ★ `lineSpacing` は索引キャッシュの検証項目に**入っていない** (2026-10-27 確認)

`TxtReaderActivity::loadPageIndexCache()` を読んで確認した。
**検証しているのは 8 項目で、`lineSpacing` は無い**:

```
magic / version / fileSize / viewportWidth / linesPerPage /
fontId / screenMargin / paragraphAlignment
```

**横書きの TXT が `lineSpacing` を見ていないので、入っている必要も無かった。**
`linesPerPage = viewportHeight / getLineHeight(fontId)` は圧縮を掛けていない。
`getReaderLineCompression()` の呼び出し元は `TextSettingsPreview.cpp` と
`CrossPointSettings.cpp` だけである。

**→ 縦書きで流用した瞬間、F-2 と同型の罠になる** (設定を変えても古い索引が
再利用される)。**手当てが要る。**

#### 手当て — **`lineSpacing` を足すのではなく、`columnsPerPage` と
`charsPerColumn` を検証する**

**ページの区切りを決めているのはこの 2 つの積だけである。**

```
1 ページの収容文字数 = columnsPerPage * charsPerColumn
columnsPerPage = viewportWidth  / columnWidth      // lineSpacing はここに効く
charsPerColumn = viewportHeight / em               // 向き・ステータスバーがここに効く
```

| 検証する値 | 捕まえられる変化 |
|---|---|
| **`columnsPerPage`** | **`lineSpacing` の変更**、`viewportWidth` の変更、フォントサイズ |
| **`charsPerColumn`** | **`viewportHeight` の変更** (向き・ステータスバーの構成)、フォントサイズ |

**`lineSpacing` そのものを検証項目にする必要は無い。**比が変わっても
`columnsPerPage` が変わらないなら、**ページの区切りは同じ位置に出る**
(x 座標だけが変わり、それは描画時に計算される)。**再利用して正しい。**

> **⚠️ 横書きでは `charsPerColumn` に相当する検証が `linesPerPage` で
> 済んでいた** (`viewportHeight` が `linesPerPage` に畳み込まれるため)。
> **縦書きでは `viewportWidth` が `columnsPerPage` に畳み込まれ、
> `viewportHeight` を畳み込む先が無い。**
> `viewportWidth` だけを検証していると、**向きを変えても索引が
> 再利用されうる。**ここは横書きと非対称である。

**これは形式変更なので `CACHE_VERSION` の繰り上げを伴う** (6 → 7)。
縦書き段階1 を入れるときに 1 回だけ上げる。

#### 段階2 以降に送る項目

| # | 内容 |
|---|---|
| 1 | **横書きの TXT も `lineSpacing` を見るようにするか。**現在は無視している。**縦書き段階1 のスコープ外**。やるなら `linesPerPage` が変わるので `CACHE_VERSION` をさらに 1 つ上げる |

**どちらを採るか**: **両方いる。**`columnsPerPage` が「1 ページに何列」、
`charsPerColumn` が「1 列に何文字」で、横書きの `linesPerPage` と
「1 行に何文字入るか (= 折り返し)」に 1 対 1 で対応する。

| 横書き | 縦書き |
|---|---|
| `linesPerPage` = 縦に何行 | **`columnsPerPage`** = 横に何列 |
| 折り返し幅 `viewportWidth` | **`viewportHeight`** |
| 行送り `advanceY` (縦方向) | **列送り `columnWidth`** (横方向) |
| 字送り = 文字ごとの `advanceX` | **字送り = `em` (固定)** |

### 2.3 座標の式

**列は右から左へ。文字は上から下へ。**

```
列 i (0 が最も右) の x:
  columnLeft(i) = marginLeft + viewportWidth - (i + 1) * columnWidth

列内の文字 j の y (drawText の y は文字の上端 → 仕様書 §3.6):
  charTop(j) = marginTop + j * em
```

**`renderCharImpl<None>(…, cursorX, cursorY, …)` の `cursorY` はベースライン**
なので、公開ラッパ側で `+ascender` する (`drawText` と同じ規約に揃える)。

```cpp
// 新設する公開メソッドの想定シグネチャ
void drawTextVertical(int fontId, int x, int yTop, const char* text,
                      bool black = true,
                      EpdFontFamily::Style style = EpdFontFamily::REGULAR) const;
```

**約 40 行の見込み。**`drawTextRotated90CW()` が 65 行で、そこから
カーニング・リガチャ・結合マークの処理を除いた規模。

### 2.4 ★ ページ境界のバイトオフセットは意味を保つか — **保つ**

**これが最重要の論点。結論: 保つ。**

`pageOffsets[n]` は「n ページ目が始まるソースのバイト位置」であり、
**レイアウトの向きに依存しない定義である。**縦書きでも:

- `loadPageAtOffset(offset, outColumns, nextOffset)` は
  `offset` から読んで `columnsPerPage` 列を埋め、`nextOffset` を返す
- `currentOffset` は依然「表示中のページの先頭バイト」
- `currentPageNextOffset` は依然「表示中のページが終わるバイト」
- `offsetHistory` は依然「歩いた経路」

**F-9 の 4 つの規則がそのまま成立する** (仕様書 §6.7):

| 規則 | 縦書きでの扱い |
|---|---|
| 1. 開くとき、索引が覆っていれば先頭に吸着 | **そのまま** |
| 2. 索引完成時は吸着しない | **そのまま** |
| 3. 前進は `currentPageNextOffset` を使う | **そのまま** |
| 4. 後退は `offsetHistory` を優先 | **そのまま** |

**遅延索引 (`advanceIndex`) も変更不要。**1 ページ分を組んで `nextOffset` を
得る処理の中身が変わるだけで、ティックの構造・`RenderLock`・`skipLoopDelay()`
はすべて同じ。

### 2.5 キャッシュの扱い — **`CACHE_VERSION` を上げ、検証項目を 1 つ足す**

`index.bin` の検証項目は 8 つで、**向きを表すものが 1 つもない**
(仕様書 §4.3)。

```
magic / version / fileSize / viewportWidth / linesPerPage / fontId
  / screenMargin / paragraphAlignment
```

**縦書きに切り替えると `pageOffsets` の中身が完全に変わる**が、
`viewportWidth` も `linesPerPage` も**同じ値のまま**になりうる
(`linesPerPage` は縦書きでは使わない)。
**→ 古い索引が「有効」と判定され、黙って再利用される。**
これは F-2 で一度踏んだ罠と同型 (仕様書 §8.2)。

**必要な対応 (2 つとも):**

1. **`CACHE_VERSION` を 5 → 6 に上げる。**切り替えた瞬間の 1 回を確実に潰す
2. **検証項目に向きのフラグを足す。**横書き ⇄ 縦書きを往復するたびに
   再構築させる。`linesPerPage` のフィールドを
   「縦書きなら `columnsPerPage` を書く」形にしても検証は通るが、
   **偶然一致する組み合わせがありうる**ので独立したフラグにする

`progress.bin` (`"PTXP"` v1) は**オフセットしか持たない**ので、
**形式の変更は不要。**ただし §2.4 の規則 1 (吸着) が働くため、
**向きを変えた直後は `indexCacheRejected` が真になり、履歴が最新 1 件に
切り詰められる** (`d5e0ed91` の挙動)。これは意図した動作。

## 3. 字形の扱い

> ⚠️ **`UDEVGothic_*.cpfont` に縦書き用字形 (U+FE10-FE19 / U+FE30-FE4F) が
> 入っているかは【未調査】。**SD を接続して `intervals` を読む必要がある
> (読み取りスクリプトは `scratchpad/read_cpfont.py` にある)。
>
> 生成プリセット `cjk` (`fontconvert_sdcard.py:54-55`) は
> `0x3000-303F / 0x3040-309F / 0x30A0-30FF / 0x4E00-9FFF / 0xF900-FAFF / 0xFF00-FFEF`
> で、**縦書き用の 2 ブロックを含まない。**`UDEVGothic` が同じプリセットで
> 生成されたなら未収録のはずだが、**確認していない。**

### 3.1 文字ごとの判定

| 対象 | 必要な処理 | `Rotated90CW` で足りるか |
|---|---|---|
| **かな・漢字** | **なし。**そのまま置く | 回さない (`None`) |
| **長音符 `ー`** (U+30FC) | **90° 回転** | **✓ 足りる** |
| **罫線類** (U+2500-257F) | 90° 回転 | ✓ 足りる (ただし収録【未調査】) |
| **括弧 `「」『』（）`** | 90° 回転**＋位置のオフセット** | **✗ 回転だけでは足りない** — 回すと字の重心が列の中心から外れる |
| **句読点 `、。`** | **回転しない。マスの右上へ移動** | **✗ オフセットのみ** |
| **小書き文字 `っゃゅょ` 等** | **回転しない。マスの右上へ移動** | **✗ オフセットのみ** |
| **ラテン・数字** | §3.5 の判断次第 | — |

### 3.2 ★ レンダラ側で回転＋オフセットに一本化する

`「` を 90° 回すと `﹁` 相当になるが、**回転は `renderCharImpl` の座標変換で
行われるため、回った字形が列の中心に来るとは限らない。**

```cpp
// renderCharImpl<Rotated90CW> の座標
outerBase = cursorX + fontData->ascender - top;   // screenX
innerBase = cursorY - left;                       // screenY
```

**`ascender` と `top` から x が決まる**ので、縦書きの列幅 (`columnWidth`) の
中心に合わせるには**補正値が要る。**補正は字形ごとに違う。

**→ コードポイント別の「回転の有無 + (dx, dy)」の表 1 つで閉じる。約 45 行。**

#### Unicode の縦書き用コードポイント (U+FE10-FE19 / U+FE30-FE4F) は採らない

**採っても §3.2 の表は消えない。**範囲の対応を調べると:

| 対象 | 縦書き用コードポイント | 範囲 |
|---|---|---|
| `「」『』` | U+FE41 / FE42 / FE43 / FE44 | FE30-FE4F |
| `（）〈〉` | U+FE35-FE38 | FE30-FE4F |
| **`、。`** | **U+FE11 / U+FE12** | **★ FE10-FE19。別範囲** |
| **長音符 `ー`** | **存在しない** | — |
| **小書きかな `っゃゅょぁぃぅぇぉ`** | **★ Unicode に縦書き形が存在しない** | — |

**小書きかなに縦書き形が無い。**したがって**オフセットの仕組みは
どちらの道を選んでも必須である。**

**それが存在すれば、`「」` や `、。` を同じ表に足すコストはほぼゼロ。**
FExx を使う利点が消える。

#### 逆に FExx には欠点が付く

| # | 欠点 |
|---|---|
| 1 | **フォント依存になる。**別のフォントを入れたユーザーで崩れる |
| 2 | **未収録フォント用のフォールバックが必要** → **経路が 2 本になりテストが倍** |
| 3 | **`vert` フィーチャで実装されたフォントでは FExx が水平形と同じグリフを指すことがある** → 「入っているのに回っていない」という**最も分かりにくい壊れ方**をする |

**→ レンダラ側で回転＋オフセットに一本化する。**
**SD を読んで収録を確認する必要もない。**

> **この判断の副産物**: フォントを作り直さないので、
> **Phase B (UI フォントの焼き込み) との順序を気にしなくてよくなった。**
> 配布物が二度変わる問題が消える。

### 3.3 句読点と小書き文字 — オフセットのみ

`、` `。` は縦書きでは**マスの右上**に置く。`っ` `ゃ` `ゅ` `ょ` `ぁぃぅぇぉ` も同様。

**回転も字形置換も不要。**`renderCharImpl` が任意座標を取るので、
**コードポイント別の `(dx, dy)` 表を引いて位置をずらすだけ。**

```
、。          → dx = +em/2 相当, dy = -em/2 相当 (右上へ)
っゃゅょぁぃぅぇぉ → dx = +em/4 程度 (右へ寄せる。上下は動かさない)
```

**具体的な値は実機で合わせる必要がある【未調査】。**フォントのデザインに依存する。

### 3.4 対象のコードポイント一覧

| 種別 | コードポイント |
|---|---|
| 右上へ移動 | `、`(3001) `。`(3002) `，`(FF0C) `．`(FF0E) |
| 右へ寄せ | `っ`(3063) `ゃゅょ`(3083/3085/3087) `ぁぃぅぇぉ`(3041/3043/3045/3047/3049) / カタカナの対応字 (30C3, 30E3/30E5/30E7, 30A1/30A3/30A5/30A7/30A9) |
| 90° 回転 | `ー`(30FC) `―`(2015) `…`(2026) `‥`(2025) `〜`(301C) |
| 回転＋オフセット | `「」`(300C/300D) `『』`(300E/300F) `（）`(FF08/FF09) `〈〉`(3008/3009) `《》`(300A/300B) `【】`(3010/3011) `〔〕`(3014/3015) `［］`(FF3B/FF3D) `｛｝`(FF5B/FF5D) |

**約 45 文字。**表 1 つで足りる。

### 3.5 ★ ASCII と半角カナ — 段階1 では **1 文字 = 1 マスで正立**

**ここが設計の穴だった。**

```
charsPerColumn = viewportHeight / em
```

**これは全文字が全角のときにだけ成立する。**青空文庫の本文には
ASCII (数字・注記のラテン) と半角カナが普通に出るため、
**等幅性という最大の武器がそこで失われる。**

#### 案 A を採る (段階1)

| 案 | 内容 | 割り算のモデル | 測定関数 | 段階 |
|---|---|---|---|---|
| **A** | **ASCII・半角カナも 1 文字 = 1 マス。正立のままマスの中央に置く** | **保たれる** | **一切呼ばない** | **✓ 段階1** |
| B | ラテンの連続を 90° 回転し、`getTextAdvanceX` で幅を測って `ceil(幅 / em)` マス消費 | 崩れる | 必要 | 段階2 |
| C | 2 文字以下は縦中横、3 文字以上は回転 | 崩れる | 必要 | 段階2 |

**A を採る理由: 段階1 を安くしている唯一の理由が「割り算だけで済む」こと
だから、そこを守る。**

```
全文字が 1 マスを消費する
  → charsPerColumn = viewportHeight / em  が常に正しい
  → findWrapOffset() も getTextAdvanceX() も呼ばない
  → 列の切れ目は「n 文字ごと」の整数演算だけで決まる
```

**見た目の代償**: **ラテン語の単語は読みにくい** (1 字ずつ縦に並ぶため)。
**数字や記号は自然に見える** — 日本語組版で数字を 1 桁ずつ縦に置くのは
正当な表記であり、青空文庫の本文に出る数字はたいてい 1〜2 桁。

**半角カナ (U+FF61-FF9F) も同じ扱い。**advance が em/2 であっても
**マスは 1 つ消費し、グリフをマスの中央に置く。**
`em/2` を実測する必要がなくなる (§7 の未調査から外れる)。

**判定は不要。**すべての文字が一律 1 マスなので、
`utf8IsCjkCodepoint()` による分岐すら要らない。
**マスの中央に置くための `dx` だけ、グリフの実幅から求める:**

```
dx = (em - advanceX(cp)) / 2      // 全角なら 0、半角なら em/4
```

`advanceX` は `renderCharImpl` が引く `glyph->advanceX` をそのまま使えるので、
**別途 `getTextAdvanceX()` を呼ぶ必要はない。**

#### 段階2 に回すもの

**B と C は独立した項目とする** (§6.3 の「段階1 に含めないもの」)。
どちらも「ラテンの連続を 1 つの単位として扱う」ことが必要で、
**割り算のモデルを崩す。**段階1 が動いてから、
**実際に読んでみて必要かを判断する** (STATUS.md の順序 5)。

## 4. 禁則処理

### 4.1 入れる。ただし縦書きのためではない

`lib/Epub/Epub/ParsedText.cpp:62-122` に実用水準の実装がある:

```cpp
bool isNoBreakBeforeCjkPunctuation(uint32_t cp);  // 行頭禁則: 、。」』】）！？ 全36文字
bool isNoBreakAfterCjkPunctuation(uint32_t cp);   // 行末禁則: 「『【（〈《 全18文字
bool hasCjkBreakOpportunityBetween(uint32_t leftCp, uint32_t rightCp);
std::vector<size_t> cjkCharacterBreakByteOffsets(const std::string& text);
```

全角・半角の両方を網羅し、述語は純粋な `switch` で状態を持たない。

**⚠️ TXT は横書きでも禁則を使っていない。**`findWrapOffset()` は
`lastFittingOffset` (直前のコードポイント境界) を返すだけなので、
**いまの横書き日本語でも `。` や `」` が行頭に来る** (仕様書 §4.4)。

**→ 禁則は縦書き固有のコストではなく、既存の横書きにある欠落である。**
**縦書きとは独立に、横書きにも効く改善として入れるべき。**

### 4.2 共有する形 (実装しない)

**問題: `namespace { }` の中にある** (同ファイル L18-263)。翻訳単位の外から呼べない。

**置き場所の前例がある**: `utf8IsCjkBreakable()` は既に
`lib/Utf8/Utf8.h:29` にある共有ヘッダ。

```
案: lib/Utf8/CjkBreak.h (新規) に 2 つの述語を移す

  bool utf8IsNoBreakBeforeCjk(uint32_t cp);
  bool utf8IsNoBreakAfterCjk(uint32_t cp);

  ParsedText.cpp は匿名名前空間の定義を消して #include に差し替える
  findWrapOffset() / 縦書きの折り返しが同じヘッダを引く
```

**機械的な移動で済む。約 60 行 + ParsedText.cpp の差し替え。**

> **⚠️ `ParsedText.cpp` は上流が触る** (`GfxRenderer.cpp` ほどではないが
> ruby と CJK 分割の中核で develop 移行時に +374/−26 の変更があった)。
> **移動は衝突しやすい。**段階1 に含めず、**独立したコミットにする。**

### 4.3 段階1 では入れない

**理由**: 縦書きの骨格を動かすことが先で、禁則を同時に入れると
「縦書きが壊れたのか禁則が壊れたのか」を切り分けられない
(仕様書 §8.7-3 と同じ構図)。

**縦書きが動いてから、横書き・縦書きの両方に効く改善として入れる。**

## 6.4 検討して採らなかった案

| 案 | 判断 | 理由 |
|---|---|---|
| **Unicode の縦書き用コードポイント (U+FE10-FE19 / U+FE30-FE4F) を使う** | **❌ 採らない** | **小書きかな `っゃゅょぁぃぅぇぉ` と長音符 `ー` に縦書き形が Unicode に存在しない**ため、**オフセットの仕組みはどちらの道でも必須。**それがあれば `「」` `、。` を同じ表に足すコストはほぼゼロで、**利点が消える。**逆に欠点が付く: ① フォント依存になる ② 未収録フォント用のフォールバックで**経路が 2 本になりテストが倍** ③ `vert` フィーチャ実装のフォントでは **FExx が水平形と同じグリフを指すことがあり「入っているのに回っていない」という最も分かりにくい壊れ方**をする。→ **レンダラ側で回転＋オフセットに一本化** (§3.2) |
| **ラテンの連続を 90° 回転して幅で送る (案 B)** | **⬜ 段階2** | `getTextAdvanceX` で測って `ceil(幅 / em)` マス消費する。**割り算のモデルが崩れる** — 段階1 を安くしている唯一の理由がそこなので、段階1 では採らない (§3.5) |
| **縦中横 (案 C)** | **⬜ 段階2** | 2 文字以下を 1 マスに横並び、3 文字以上は回転。**真に新規のレイアウト論理で約 80 行。**同じく割り算を崩す |
| **禁則処理を段階1 に入れる** | **⬜ 独立した改善** | TXT は**横書きでも禁則を使っていない** — 縦書き固有のコストではなく既存の欠落。同時に入れると「縦書きが壊れたのか禁則が壊れたのか」を切り分けられない (§4.3) |
| **EPUB も対象にする** | ❌ 段階1 では採らない | `ParsedText` / `TextBlock` の組版を通る別案件。**段階1 の 3〜5 倍の規模**【未見積もり】(§5.2) |
