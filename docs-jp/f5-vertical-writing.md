## 0. 何を作るのか

**TXT リーダーで日本語を縦書きに組む。**右から左へ列が進み、各列は上から下へ。

段階1 の範囲は §6 で定義する。**ルビ (F-8 段階2) は含まない。**

### なぜ縦書きを先にやるのか

**縦書きは「1ページ = 固定数のマス」という前提を保ち、ルビはそれを壊す**
(仕様書 §4.2)。逆順にすると、ルビで可変行高を入れた上に縦書きを乗せることになり、
**ルビの作り直しが 2 回**になる。

## 1. 有利な既知の事実

### 1.1 グリフ描画はすでに任意座標を取る

```cpp
// lib/GfxRenderer/GfxRenderer.cpp:379
enum class TextRotation { None, Rotated90CW };

template <TextRotation rotation = TextRotation::None>
static void renderCharImpl(const GfxRenderer& renderer, GfxRenderer::RenderMode renderMode,
                           const EpdFontFamily& fontFamily, const uint32_t cp,
                           int cursorX, int cursorY, bool pixelState, EpdFontFamily::Style style);
```

座標計算は x と y が対称:

```cpp
outerBase = cursorY - top;    // screenY = outerBase + glyphY
innerBase = cursorX + left;   // screenX = innerBase + glyphX
```

**1 グリフを任意の `(x, y)` にステートレスに置ける。**
したがって「グリフを回さずに下へ積む」描画に**新しいビットマップ転送コードは要らない。**
`x` を固定して `y` を送り分だけ増やしながら `renderCharImpl<None>` を呼ぶだけ。

> **`drawTextRotated90CW()` と `anchorOverRotated90CW()` は画面回転 (側面ボタンの
> ラベル) 用であり、縦書き用ではない。**字形自体を 90° 回すので、
> そのまま使うと日本語が横倒しになる。使うのは**その下の `renderCharImpl`** の方。

**`renderCharImpl` は `.cpp` 内の `static`。**新しい公開メソッドは
`GfxRenderer.cpp` の中に置く必要がある (他ファイルからは呼べない)。

### 1.2 幅と高さはすでに独立したスカラ

```cpp
// TxtReaderActivity::initializeReader()
viewportWidth  = screenWidth - orientedMarginLeft - orientedMarginRight - markerWidth;
const int viewportHeight = screenHeight - orientedMarginTop - orientedMarginBottom;
linesPerPage = viewportHeight / renderer.getLineHeight(cachedFontId);
```

**互いを参照していない。**`findWrapOffset(fontId, text, maxWidth, ...)` の
`maxWidth` も**軸を知らない単なるスカラ**である。

### 1.3 SD フォント経路はカーニングもリガチャも引かない

`getTextAdvanceX()` / `findWrapOffset()` の SD 高速路は **advance table の
表引き 1 回の素の加算**で、`font.getKerning()` も `applyLigatures()` も呼ばない。

**F-7 で苦労した差分丸め・リガチャ不可分・RTL フォールバックは、
すべて組み込みフォント経路 (= ラテン文字) の話だった。**
日本語は SD フォント経路しか通らない。

### 1.4 ★ 全角は完全な等幅 — これが最も効く

**SD の `.cpfont` を直接読んだ実測値** (仕様書 §3.6):

| pt | `advanceY` | `ascender` | `descender` | **全角 em** |
|---|---|---|---|---|
| 8 | 19 | 16 | −4 | **16.6875 px** |
| 10 | 24 | 20 | −5 | **20.8125 px** |
| 12 | 29 | 24 | −6 | **25.0000 px** |
| 14 | 42 | 34 | −9 | **29.1875 px** |
| 16 | 48 | 39 | −10 | **33.3125 px** |
| 18 | 54 | 44 | −11 | **37.5000 px** |

**2026-10-27 に全 pt を実測** (`scripts/cpfont_metrics.py`)。
**全角 em は pt に完全比例する** (pt x 150/72)。
**`advanceY` は比例しない** — 8/10/12 pt で em の 1.14〜1.16 倍、
14/16/18 pt で **1.44 倍**。この 6 面は同一設計のフォントではない
(仕様書 §3.6)。

**かな・漢字 18 文字を測って advance が 1 種類しかなかった。**完全な等幅である。

#### 等幅性が縦書きに効く度合い — 横書きより*簡単*になる

| | 横書き | **縦書き (全角のみ)** |
|---|---|---|
| 1 行/列に入る数 | **文字ごとに幅を積む必要がある** (プロポーショナル) | **`viewportHeight / em` の割り算 1 回** |
| 折り返し位置 | `findWrapOffset()` で前から積む | **文字数で割るだけ。測定が不要** |
| 必要な API | `findWrapOffset` / `getTextAdvanceX` | **なし (純粋な整数演算)** |

**全角だけなら `findWrapOffset()` を呼ぶ必要すらない。**
`charsPerColumn = viewportHeight / em` を一度求めれば、
あとは「n 文字ごとに改列」で済む。

> **ただし素のままでは「全角だけなら」である。**実際の青空文庫テキストには
> ASCII (数字・英字・記号) と半角カナ (U+FF61-FF9F) が混ざる。
>
> **§3.5 で「すべての文字を 1 マスとして扱う」と決めたので、
> 混在しても割り算のモデルが保たれる。**これが段階1 を安くしている核心。

#### F-9 と F-7 の遺産

| 既存の資産 | 縦書きでの扱い |
|---|---|
| **読書位置がバイトオフセット** (F-9 フェーズ1) | **そのまま使える。**軸に依存しない |
| **索引の遅延構築** (F-9 フェーズ2) | **そのまま使える。**§2.4 参照 |
| `findWrapOffset()` (F-7) | 全角のみなら不要。混在時は縦書き版が要る (§2.3) |
| `pageOffsets` / `index.bin` | 検証項目の追加が必要 (§2.5) |

## 2. 行・ページのモデル

### 2.1 横書きの現状

```
linesPerPage = viewportHeight / lineHeight          // lineHeight = advanceY
loadPageAtOffset(offset, outLines, nextOffset)      // ちょうど linesPerPage 行を埋める
```

`outLines` は**視覚行**の配列。`renderPage()` が 1 行につき `drawText` 1 回で描く。

### 2.2 縦書きの対応物

**「視覚行」を「視覚列」に読み替える。**`outLines` の型も中身も変えない。

```
columnWidth    = em * COLUMN_RATIO    // 列の太さ。★ advanceY ではない (下記)
columnsPerPage = viewportWidth  / columnWidth
charsPerColumn = viewportHeight / em  // 全角等幅なので割り算 1 回 (§1.4)
```

#### ★ `columnWidth` を `advanceY` に紐づけてはならない (2026-10-27 変更)

**初版は `columnWidth = advanceY` だった。取り下げる。**

| # | 理由 |
|---|---|
| 1 | **`advanceY / em` がこの端末で 1.14〜1.16 と 1.44 に分かれている。**12 → 14 pt で列の間隔が飛ぶ |
| 2 | **しかもこれは利用者のフォント次第で任意の値を取る** (仕様書 §3.6)。フォントを替えただけで組版が崩れる |
| 3 | **`advanceY` は横組みの行送りであって、縦組みの列送りではない。**たまたま近い値なだけで、根拠が無い |

**12 → 14 pt で列数がどう動くか** (実測値から計算):

| モデル | 12 pt | 14 pt | 減少 |
|---|---|---|---|
| `advanceY` (初版) | 16 列 | **11 列** | **−31%** |
| `em x 1.3` | 14 列 | 12 列 | −14% |

**`em` 基準なら、列数は字の大きさだけで決まる。**
フォントの縦メトリクスという**利用者依存の量**が組版に混ざらない。

#### `COLUMN_RATIO` の候補

**12 pt (em 25 px) / viewport 464 x 754 px での実測ベースの計算。**
`charsPerColumn = 754 / 25 = 30 字`。

| 比 | `columnWidth` | 列数 | 1 ページの字数 | 横書き現状比 | 行間 |
|---|---|---|---|---|---|
| 1.0 | 25 | **18** | 540 | +15% | **0。列が密着する** |
| 1.15 | 29 | **16** | 480 | +3% | 0.15 em |
| **1.3** | **32** | **14** | **420** | **−10%** | **0.3 em** |
| 1.5 | 38 | **12** | 360 | −23% | 0.5 em |
| 1.75 | 44 | **10** | 300 | −36% | 0.75 em |

**横書きの現状**: 26 行 x 18 字 = **468 字/ページ** (12 pt)。

**日本語の縦組みの慣習**: 書籍の本文は**行間 0.5〜0.75 em
(= 比 1.5〜1.75)** が一般的。新聞や詰めた文庫で 1.2〜1.3。
**比 1.0 は列が密着するので読めない。**

> **⚠️ 慣習の値は紙の本のものである。**480 x 800 の電子ペーパーで
> 比 1.5 を採ると 1 ページ 360 字まで落ち、**ページ送りが 1.3 倍に増える。**
> 書き換えが 1〜2 秒かかる端末では、これは実際の不便になる。

### ★ 確定: `COLUMN_RATIO = 1.3` (2026-10-27)

0.3 em の間隔は列の区切りとして十分に見え、密度の損失は横書き比 −10% に収まる。
**12 pt で 14 列 x 30 字 = 420 字/ページ。**

#### 設定項目 — **`SETTINGS.lineSpacing` の enum を流用する**

**新しい設定は作らない。**`TIGHT` / `NORMAL` / `WIDE` の 3 段が既にあり、
UI も翻訳も揃っている。

**ただし既存の係数をそのまま掛けてはならない。**
`getReaderLineCompression()` が返すのは 0.95 / 1.0 / 1.1 で、
**幅が狭すぎて列数が動かない**:

| 案 | TIGHT | NORMAL | WIDE |
|---|---|---|---|
| 既存の係数を 1.3 に掛ける | 比 1.235 → **14 列** | 比 1.3 → **14 列** | 比 1.43 → 12 列 |
| **★ 縦書き専用の写像 (確定)** | **比 1.15 → 16 列** | **比 1.3 → 14 列** | **比 1.5 → 12 列** |

**既存係数だと TIGHT と NORMAL が同じ 14 列になり、設定が 2 段にしか
見えない。**縦書き専用の写像にすれば 3 段がそれぞれ別の結果になる。

```
縦書きの列幅:
  COLUMN_RATIO = { TIGHT: 1.15, NORMAL: 1.30, WIDE: 1.50 }[SETTINGS.lineSpacing]
  columnWidth  = round(em * COLUMN_RATIO)
```

#### ★ `lineSpacing` は索引キャッシュの検証項目に**入っていない** (2026-10-27 確認)

`TxtReaderActivity::loadPageIndexCache()` を読んで確認した。
**検証しているのは 8 項目で、`lineSpacing` は無い**:

```
magic / version / fileSize / viewportWidth / linesPerPage /
fontId / screenMargin / paragraphAlignment
```

**横書きの TXT が `lineSpacing` を見ていないので、入っている必要も無かった。**
`linesPerPage = viewportHeight / getLineHeight(fontId)` は圧縮を掛けていない。
`getReaderLineCompression()` の呼び出し元は `TextSettingsPreview.cpp` と
`CrossPointSettings.cpp` だけである。

**→ 縦書きで流用した瞬間、F-2 と同型の罠になる** (設定を変えても古い索引が
再利用される)。**手当てが要る。**

#### 手当て — **`lineSpacing` を足すのではなく、`columnsPerPage` と
`charsPerColumn` を検証する**

**ページの区切りを決めているのはこの 2 つの積だけである。**

```
1 ページの収容文字数 = columnsPerPage * charsPerColumn
columnsPerPage = viewportWidth  / columnWidth      // lineSpacing はここに効く
charsPerColumn = viewportHeight / em               // 向き・ステータスバーがここに効く
```

| 検証する値 | 捕まえられる変化 |
|---|---|
| **`columnsPerPage`** | **`lineSpacing` の変更**、`viewportWidth` の変更、フォントサイズ |
| **`charsPerColumn`** | **`viewportHeight` の変更** (向き・ステータスバーの構成)、フォントサイズ |

**`lineSpacing` そのものを検証項目にする必要は無い。**比が変わっても
`columnsPerPage` が変わらないなら、**ページの区切りは同じ位置に出る**
(x 座標だけが変わり、それは描画時に計算される)。**再利用して正しい。**

> **⚠️ 横書きでは `charsPerColumn` に相当する検証が `linesPerPage` で
> 済んでいた** (`viewportHeight` が `linesPerPage` に畳み込まれるため)。
> **縦書きでは `viewportWidth` が `columnsPerPage` に畳み込まれ、
> `viewportHeight` を畳み込む先が無い。**
> `viewportWidth` だけを検証していると、**向きを変えても索引が
> 再利用されうる。**ここは横書きと非対称である。

**これは形式変更なので `CACHE_VERSION` の繰り上げを伴う** (6 → 7)。
縦書き段階1 を入れるときに 1 回だけ上げる。

#### 段階2 以降に送る項目

| # | 内容 |
|---|---|
| 1 | **横書きの TXT も `lineSpacing` を見るようにするか。**現在は無視している。**縦書き段階1 のスコープ外**。やるなら `linesPerPage` が変わるので `CACHE_VERSION` をさらに 1 つ上げる |

**どちらを採るか**: **両方いる。**`columnsPerPage` が「1 ページに何列」、
`charsPerColumn` が「1 列に何文字」で、横書きの `linesPerPage` と
「1 行に何文字入るか (= 折り返し)」に 1 対 1 で対応する。

| 横書き | 縦書き |
|---|---|
| `linesPerPage` = 縦に何行 | **`columnsPerPage`** = 横に何列 |
| 折り返し幅 `viewportWidth` | **`viewportHeight`** |
| 行送り `advanceY` (縦方向) | **列送り `columnWidth`** (横方向) |
| 字送り = 文字ごとの `advanceX` | **字送り = `em` (固定)** |

### 2.3 座標の式

**列は右から左へ。文字は上から下へ。**

```
列 i (0 が最も右) の x:
  columnLeft(i) = marginLeft + viewportWidth - (i + 1) * columnWidth

列内の文字 j の y (drawText の y は文字の上端 → 仕様書 §3.6):
  charTop(j) = marginTop + j * em
```

**`renderCharImpl<None>(…, cursorX, cursorY, …)` の `cursorY` はベースライン**
なので、公開ラッパ側で `+ascender` する (`drawText` と同じ規約に揃える)。

```cpp
// 新設する公開メソッドの想定シグネチャ
void drawTextVertical(int fontId, int x, int yTop, const char* text,
                      bool black = true,
                      EpdFontFamily::Style style = EpdFontFamily::REGULAR) const;
```

**約 40 行の見込み。**`drawTextRotated90CW()` が 65 行で、そこから
カーニング・リガチャ・結合マークの処理を除いた規模。

### 2.4 ★ ページ境界のバイトオフセットは意味を保つか — **保つ**

**これが最重要の論点。結論: 保つ。**

`pageOffsets[n]` は「n ページ目が始まるソースのバイト位置」であり、
**レイアウトの向きに依存しない定義である。**縦書きでも:

- `loadPageAtOffset(offset, outColumns, nextOffset)` は
  `offset` から読んで `columnsPerPage` 列を埋め、`nextOffset` を返す
- `currentOffset` は依然「表示中のページの先頭バイト」
- `currentPageNextOffset` は依然「表示中のページが終わるバイト」
- `offsetHistory` は依然「歩いた経路」

**F-9 の 4 つの規則がそのまま成立する** (仕様書 §6.7):

| 規則 | 縦書きでの扱い |
|---|---|
| 1. 開くとき、索引が覆っていれば先頭に吸着 | **そのまま** |
| 2. 索引完成時は吸着しない | **そのまま** |
| 3. 前進は `currentPageNextOffset` を使う | **そのまま** |
| 4. 後退は `offsetHistory` を優先 | **そのまま** |

**遅延索引 (`advanceIndex`) も変更不要。**1 ページ分を組んで `nextOffset` を
得る処理の中身が変わるだけで、ティックの構造・`RenderLock`・`skipLoopDelay()`
はすべて同じ。

### 2.5 キャッシュの扱い — **`CACHE_VERSION` を上げ、検証項目を 1 つ足す**

`index.bin` の検証項目は 8 つで、**向きを表すものが 1 つもない**
(仕様書 §4.3)。

```
magic / version / fileSize / viewportWidth / linesPerPage / fontId
  / screenMargin / paragraphAlignment
```

**縦書きに切り替えると `pageOffsets` の中身が完全に変わる**が、
`viewportWidth` も `linesPerPage` も**同じ値のまま**になりうる
(`linesPerPage` は縦書きでは使わない)。
**→ 古い索引が「有効」と判定され、黙って再利用される。**
これは F-2 で一度踏んだ罠と同型 (仕様書 §8.2)。

**必要な対応 (2 つとも):**

1. **`CACHE_VERSION` を 5 → 6 に上げる。**切り替えた瞬間の 1 回を確実に潰す
2. **検証項目に向きのフラグを足す。**横書き ⇄ 縦書きを往復するたびに
   再構築させる。`linesPerPage` のフィールドを
   「縦書きなら `columnsPerPage` を書く」形にしても検証は通るが、
   **偶然一致する組み合わせがありうる**ので独立したフラグにする

`progress.bin` (`"PTXP"` v1) は**オフセットしか持たない**ので、
**形式の変更は不要。**ただし §2.4 の規則 1 (吸着) が働くため、
**向きを変えた直後は `indexCacheRejected` が真になり、履歴が最新 1 件に
切り詰められる** (`d5e0ed91` の挙動)。これは意図した動作。

## 3. 字形の扱い

> ⚠️ **`UDEVGothic_*.cpfont` に縦書き用字形 (U+FE10-FE19 / U+FE30-FE4F) が
> 入っているかは【未調査】。**SD を接続して `intervals` を読む必要がある
> (読み取りスクリプトは `scratchpad/read_cpfont.py` にある)。
>
> 生成プリセット `cjk` (`fontconvert_sdcard.py:54-55`) は
> `0x3000-303F / 0x3040-309F / 0x30A0-30FF / 0x4E00-9FFF / 0xF900-FAFF / 0xFF00-FFEF`
> で、**縦書き用の 2 ブロックを含まない。**`UDEVGothic` が同じプリセットで
> 生成されたなら未収録のはずだが、**確認していない。**

### 3.1 文字ごとの判定

| 対象 | 必要な処理 | `Rotated90CW` で足りるか |
|---|---|---|
| **かな・漢字** | **なし。**そのまま置く | 回さない (`None`) |
| **長音符 `ー`** (U+30FC) | **90° 回転** | **✓ 足りる** |
| **罫線類** (U+2500-257F) | 90° 回転 | ✓ 足りる (ただし収録【未調査】) |
| **括弧 `「」『』（）`** | 90° 回転**＋位置のオフセット** | **✗ 回転だけでは足りない** — 回すと字の重心が列の中心から外れる |
| **句読点 `、。`** | **回転しない。マスの右上へ移動** | **✗ オフセットのみ** |
| **小書き文字 `っゃゅょ` 等** | **回転しない。マスの右上へ移動** | **✗ オフセットのみ** |
| **ラテン・数字** | §3.5 の判断次第 | — |

### 3.2 ★ レンダラ側で回転＋オフセットに一本化する

`「` を 90° 回すと `﹁` 相当になるが、**回転は `renderCharImpl` の座標変換で
行われるため、回った字形が列の中心に来るとは限らない。**

```cpp
// renderCharImpl<Rotated90CW> の座標
outerBase = cursorX + fontData->ascender - top;   // screenX
innerBase = cursorY - left;                       // screenY
```

**`ascender` と `top` から x が決まる**ので、縦書きの列幅 (`columnWidth`) の
中心に合わせるには**補正値が要る。**補正は字形ごとに違う。

**→ コードポイント別の「回転の有無 + (dx, dy)」の表 1 つで閉じる。約 45 行。**

#### Unicode の縦書き用コードポイント (U+FE10-FE19 / U+FE30-FE4F) は採らない

**採っても §3.2 の表は消えない。**範囲の対応を調べると:

| 対象 | 縦書き用コードポイント | 範囲 |
|---|---|---|
| `「」『』` | U+FE41 / FE42 / FE43 / FE44 | FE30-FE4F |
| `（）〈〉` | U+FE35-FE38 | FE30-FE4F |
| **`、。`** | **U+FE11 / U+FE12** | **★ FE10-FE19。別範囲** |
| **長音符 `ー`** | **存在しない** | — |
| **小書きかな `っゃゅょぁぃぅぇぉ`** | **★ Unicode に縦書き形が存在しない** | — |

**小書きかなに縦書き形が無い。**したがって**オフセットの仕組みは
どちらの道を選んでも必須である。**

**それが存在すれば、`「」` や `、。` を同じ表に足すコストはほぼゼロ。**
FExx を使う利点が消える。

#### 逆に FExx には欠点が付く

| # | 欠点 |
|---|---|
| 1 | **フォント依存になる。**別のフォントを入れたユーザーで崩れる |
| 2 | **未収録フォント用のフォールバックが必要** → **経路が 2 本になりテストが倍** |
| 3 | **`vert` フィーチャで実装されたフォントでは FExx が水平形と同じグリフを指すことがある** → 「入っているのに回っていない」という**最も分かりにくい壊れ方**をする |

**→ レンダラ側で回転＋オフセットに一本化する。**
**SD を読んで収録を確認する必要もない。**

> **この判断の副産物**: フォントを作り直さないので、
> **Phase B (UI フォントの焼き込み) との順序を気にしなくてよくなった。**
> 配布物が二度変わる問題が消える。

### 3.3 句読点と小書き文字 — オフセットのみ

`、` `。` は縦書きでは**マスの右上**に置く。`っ` `ゃ` `ゅ` `ょ` `ぁぃぅぇぉ` も同様。

**回転も字形置換も不要。**`renderCharImpl` が任意座標を取るので、
**コードポイント別の `(dx, dy)` 表を引いて位置をずらすだけ。**

```
、。          → dx = +em/2 相当, dy = -em/2 相当 (右上へ)
っゃゅょぁぃぅぇぉ → dx = +em/4 程度 (右へ寄せる。上下は動かさない)
```

**具体的な値は実機で合わせる必要がある【未調査】。**フォントのデザインに依存する。

| 種別 | コードポイント |
|---|---|
| 右上へ移動 | `、`(3001) `。`(3002) `，`(FF0C) `．`(FF0E) |
| 右へ寄せ | `っ`(3063) `ゃゅょ`(3083/3085/3087) `ぁぃぅぇぉ`(3041/3043/3045/3047/3049) / カタカナの対応字 (30C3, 30E3/30E5/30E7, 30A1/30A3/30A5/30A7/30A9) |

### 3.5 ★ ASCII と半角カナ — 段階1 では **1 文字 = 1 マスで正立**

**ここが設計の穴だった。**

```
charsPerColumn = viewportHeight / em
```

**これは全文字が全角のときにだけ成立する。**青空文庫の本文には
ASCII (数字・注記のラテン) と半角カナが普通に出るため、
**等幅性という最大の武器がそこで失われる。**

#### 案 A を採る (段階1)

| 案 | 内容 | 割り算のモデル | 測定関数 | 段階 |
|---|---|---|---|---|
| **A** | **ASCII・半角カナも 1 文字 = 1 マス。正立のままマスの中央に置く** | **保たれる** | **一切呼ばない** | **✓ 段階1** |
| B | ラテンの連続を 90° 回転し、`getTextAdvanceX` で幅を測って `ceil(幅 / em)` マス消費 | 崩れる | 必要 | 段階2 |
| C | 2 文字以下は縦中横、3 文字以上は回転 | 崩れる | 必要 | 段階2 |

**A を採る理由: 段階1 を安くしている唯一の理由が「割り算だけで済む」こと
だから、そこを守る。**

```
全文字が 1 マスを消費する
  → charsPerColumn = viewportHeight / em  が常に正しい
  → findWrapOffset() も getTextAdvanceX() も呼ばない
  → 列の切れ目は「n 文字ごと」の整数演算だけで決まる
```

**見た目の代償**: **ラテン語の単語は読みにくい** (1 字ずつ縦に並ぶため)。
**数字や記号は自然に見える** — 日本語組版で数字を 1 桁ずつ縦に置くのは
正当な表記であり、青空文庫の本文に出る数字はたいてい 1〜2 桁。

**半角カナ (U+FF61-FF9F) も同じ扱い。**advance が em/2 であっても
**マスは 1 つ消費し、グリフをマスの中央に置く。**
`em/2` を実測する必要がなくなる (§7 の未調査から外れる)。

**判定は不要。**すべての文字が一律 1 マスなので、
`utf8IsCjkCodepoint()` による分岐すら要らない。
**マスの中央に置くための `dx` だけ、グリフの実幅から求める:**

```
dx = (em - advanceX(cp)) / 2      // 全角なら 0、半角なら em/4
```

`advanceX` は `renderCharImpl` が引く `glyph->advanceX` をそのまま使えるので、
**別途 `getTextAdvanceX()` を呼ぶ必要はない。**

#### 段階2 に回すもの

**B と C は独立した項目とする** (§6.3 の「段階1 に含めないもの」)。
どちらも「ラテンの連続を 1 つの単位として扱う」ことが必要で、
**割り算のモデルを崩す。**段階1 が動いてから、
**実際に読んでみて必要かを判断する** (STATUS.md の順序 5)。

**→ 禁則は縦書き固有のコストではなく、既存の横書きにある欠落である。**

`lib/Utf8/Utf8.h:29` にある共有ヘッダ。

```
  bool utf8IsNoBreakAfterCjk(uint32_t cp);
```

**機械的な移動で済む。約 60 行 + ParsedText.cpp の差し替え。**

|---|---|
| 1 | **`resolveTextFontId()` は文字列全体に 1 回だけ呼ぶ規則** (仕様書 §8.1-7)。1 文字ずつの API にすると**呼び出し側が 1 文字ごとに解決することになり、この規則を破る** |
| 2 | **`drawText` と対称になる。**横書きが「1 行 = 1 呼び出し」なら、縦書きは「1 列 = 1 呼び出し」 |
| 3 | prewarm のスキャン走査が文字列単位で動く。1 文字ずつだと走査の粒度が合わない |

#### 約物の回転とオフセットは**関数の中**で決める — 決定

| # | 理由 |
|---|---|
| 1 | **表に必要な値 (`left` / `top` / `width`) はグリフのメタデータで、`GfxRenderer` しか持っていない** |
| 2 | 呼び出し側 (`TxtReaderActivity`) が縦組みの約物を知る必要が無い。**活動は「この列を描け」としか言わない** |
| 3 | 表が 1 箇所に収まる。将来 EPUB を縦書きにするとき、同じ表が効く |

#### 案

```cpp
/// 全角 1 文字ぶんの送り (em) を px で返す。縦書きの字送りであり、
/// charsPerColumn = viewportHeight / この値 で列の収容数が決まる。
int getFullWidthAdvance(int fontId, EpdFontFamily::Style style = EpdFontFamily::REGULAR) const;

/// text を 1 列として上から下へ描く。
///
/// (x, y) は列の最初のマスの左上。drawText の y が「字の上端」であるのと
/// 同じ規約に揃えてある (内部で ascender を足す)。
/// cellSize は getFullWidthAdvance() の戻り値をそのまま渡す。
/// 呼び出し側が収容数を計算するのに使った値と、描画が使う値を
/// 必ず同じにするため、再計算させずに受け取る (markPad の教訓: §8.7-8)。
///
/// 1 コードポイント = 1 マス。約物の回転とオフセットはこの中で決める。
void drawTextVertical(int fontId, int x, int y, int cellSize, const char* text,
                      bool black = true,
                      EpdFontFamily::Style style = EpdFontFamily::REGULAR) const;
```

**`cellSize` を引数にする理由**: 収容数を決めた値と描画が使う値が
別々に計算されると、**1 マスぶんずれても誰も気づかない。**
`markerWidth` と `markPad` を取り違えた件と同じ構図である (仕様書 §8.7-8)。

### 11.3 `TxtReaderActivity` の分岐 — **不変条件は成立する**

**コードで確認した。**`outLines` / `currentPageLines` を読む場所は
**2 箇所しか無い**:

| 場所 | 役割 |
|---|---|
| `loadPageAtOffset()` (503-658 行) | **作る** |
| `renderPage()` の 742 行のループ | **描く。1 要素 = `drawText` 1 回** |

ほかに `CheckboxRef::lineIndex` が添字として参照するだけである。
**「1 つの視覚的なまとまり、読み順」という意味を解釈している第三者はいない。**

→ **横書きでは 1 行、縦書きでは 1 列。概念を変えずに切り方の規則だけを
変えられる。不変条件は成立する。**

#### `loadPageAtOffset()` — どこで切るか

```
横書き: breakPos = findWrapOffset(fontId, segment, viewportWidth, ...)
縦書き: breakPos = charsPerColumn 個のコードポイントを進めた位置
```

**全角等幅なので幅を積む必要が無い** (§1.4)。UTF-8 のコードポイント境界を
数えるだけで、**フォントに一切触らない。**

変わるのはここと、`while (outLines.size() < linesPerPage)` の上限が
`columnsPerPage` になることだけ。**`pos` / `lineBytePos` の会計は不変。**

#### `renderPage()` — どこに置くか

```
横書き: x = textLeft (+ 揃えの補正)      y = marginTop + i * lineHeight
縦書き: x = marginLeft + viewportWidth - (i + 1) * columnWidth
        y = marginTop
```

**列は右から左、文字は上から下。**1 要素あたりの呼び出しが
`drawText` から `drawTextVertical` に替わる。

#### ⚠️ 成立するが、3 点ひっかかる

| # | 内容 | 扱い |
|---|---|---|
| 1 | **文字揃え (`cachedParagraphAlignment`)** は横方向の揃えで、縦書きでは意味が変わる (列の中で上下に寄せる) | **段階1 では上揃え固定。**設定は無視する |
| 2 | **空行が 1 列まるごとを占める。**14 列しかないので代償が大きい | **段階1 では占めさせる。**青空文庫では空行が節の区切りなので、縦組みでもそれが正しい。詰めるなら段階2 |
| 3 | **結合文字 (U+3099 / U+309A の濁点・半濁点)** が独立したコードポイントで来ると、1 マスを占めて崩れる | **段階1 では 1 マス扱い。**日本語テキストは合成済みが通常で、`.cpfont` にも字形はある。**既知の制約として記録する** |

## 14. 約物の確定 (v0.6 / 2026-10-28)

**試し刷りの画素から機械的に判定した。目視の印象では決めていない。**

### 14.1 ★ `Rotated90CW` は縦組みに使えない — **逆向きである**

**`TextRotation::Rotated90CW` は「左 → 下」に写す。**
縦組みの約物は「左 → 上」でなければならない。

| | 写像 |
|---|---|
| **ファーム** (`renderCharImpl<Rotated90CW>`) | `screenX = cx + ascender − top + glyphY` / `screenY = cy − left − glyphX` |
| | → `screenX` は `glyphY` に比例、`screenY` は `glyphX` に**反**比例 |
| **縦組みに要るもの** | **両軸とも符号が逆。**90 度の逆回転 (= 180 度ずれている) |

#### 判定: 回転後の墨の重心が、墨の箱の中心からどちらへずれるか

開き括弧は墨が**上**へ (負)、閉じ括弧は**下**へ (正) 寄っていなければならない。

| 字 | ファーム | 判定 | 補正版 | 判定 | 縦書きの正解 |
|---|---|---|---|---|---|
| `（` | **+0.91** | **★逆** | −0.64 | OK | 墨が上へ |
| `）` | **−0.91** | **★逆** | +0.65 | OK | 墨が下へ |
| `「` | **+1.95** | **★逆** | −1.95 | OK | 墨が上へ |
| `」` | **−2.07** | **★逆** | +1.95 | OK | 墨が下へ |
| `『` | **+1.35** | **★逆** | −1.35 | OK | 墨が上へ |
| `』` | **−1.67** | **★逆** | +1.35 | OK | 墨が下へ |

| 字 | 元の頂点 | ファーム回転 | 補正版 | 正解 |
|---|---|---|---|---|

| `〉` | 最も右の列 `gx=9` | 行 0/9 = **上** ★逆 | 行 9/9 = **下** OK | 下 |

>
> `（` の弧は **下に膨らんでいる** (開きが上を向く)。正しくは**上に膨らむ**。
> `）` の弧は **上に膨らんでいる**。正しくは**下に膨らむ**。
> **開き括弧と閉じ括弧が入れ替わって見える。**

#### 実装への影響

**`drawTextVertical()` は `Rotated90CW` を使えない。逆回転が要る。**

```
screenX = cellLeft + (cell − inkTop − h) + (h − 1 − glyphY)
screenY = cellTop  + (cell − left   − w) + glyphX
```

**上端の余白が左端の余白に、左端の余白が上端の余白になる** —
縦横の余白が入れ替わる。これにより `「` (`left=16`) は上へ、
`」` (`left=1`) は下へ行く。**メトリクスがそのまま縦の位置を決めてくれる。**

> **⚠️ `renderCharImpl` は `TextRotation` のテンプレートである。**
> 値を 1 つ増やすとインスタンス化が 1 つ増え、**バイナリが増える**
> (仕様書 §「テンプレートの肥大」)。それでも必要である。
> `Rotated90CW` を流用して座標をいじる逃げ道は無い —
> **180 度の回転が別に要るため、どちらにせよ新しい経路になる。**

**`ー` `―` `〜` `‥` は左右対称なので回転の向きに依存しない** (実測で重心のずれ 0.00)。
**`…` だけは依存する** (±0.33) が、下記のとおり字形を使わない。

### 14.2 ★ 三点リーダは**自前で点を 3 つ描く**

| 案 | 内容 | 判定 |

| b | 1 マスに中央寄せ・回転 | 不採用。1 マスに 3 点で間延びする |
| c | 字形を 2 つで 1 マス | **不採用 (下記)** |

### 14.3 ★ `、` `。` は **em 比ではなく「角に寄せる」**

**マスの大きさ: 25 x 25 px (12 pt)。**

| 字 | 方式 | dx, dy | 墨の箱 | 右の余白 | 上の余白 |
|---|---|---|---|---|---|
| `、` | em 比 0.5 | +12, −12 | (13, 7)-(20,13) | **4 px** | **7 px** |
| `。` | em 比 0.5 | +12, −12 | (13, 6)-(21,13) | **3 px** | **6 px** |
| **`、`** | **角寄せ** | **+14, −17** | **(15, 2)-(22, 8)** | **2 px** | **2 px** |
| **`。`** | **角寄せ** | **+13, −16** | **(14, 2)-(22, 9)** | **2 px** | **2 px** |

**em 比では上の余白が 6〜7 px 残り、マスの中ほどに見える。**

#### 角寄せを採る本当の理由 — **フォントが変わっても余白が変わらない**

```
dx = (cell − margin − glyph.width)  − glyph.left
dy =  margin                        − (ascender − glyph.top)
```

**グリフの墨の箱から直接求める。**em 比で持つと、
**利用者が別のフォントを入れたとき寄り方が変わる** (仕様書 §3.6)。
`、` と `。` は幅も高さも違うので、**同じ比を掛けても同じ余白にならない** —
実際、0.5 em では `、` が右 4 px、`。` が右 3 px とずれている。

**余白は 2 px で確定。**隣の列には食い込まない:
墨の右端は 22 px、マスは 25 px、列幅は 32 px でマスは中央に置くので、
**列の右端まで 7 px 余る。**

**小書きかなにも同じ規則を適用する。**`0.1 em` (3 px) では
**見分けが付かなかった** (§13)。角寄せなら字ごとに正しい位置になる。

```
  |###......|            |.......##|
  |.####....|            |.....####|
  |...####..|            |...####..|
  |.....####|            |.####....|
  |.....####|            |.###.....|
  |...#####.|            |..#####..|
  |.####....|            |....#####|
  |###......|            |.......##|
  |.........|            |.........|
   頂点 gx=8 (右)         頂点 gx=1 (左)
```

| ラベル | 置かれる位置 | ファームの回転 | 真の時計回り |
|---|---|---|---|
| `>` | **上の側面ボタン** | 頂点 → 行 0 = **上向き** ✅ | 行 8 = 下向き ❌ |
| `<` | **下の側面ボタン** | 頂点 → 行 7 = **下向き** ✅ | 行 1 = 上向き ❌ |

> ### 結論: **既存の回転は、その唯一の用途では正しい**
>
> 上のボタンに上向きの矢、下のボタンに下向きの矢が出ている。
> **真の時計回りに変えると、矢の向きが両方とも逆になる。**
>
> **既存の挙動には触らない。**

### 16.3 実装方針 — **新しい値を足す。既存は改名もしない**

**改名も見送る。**名前と実体が食い違っているのは事実だが:

| # | 理由 |
|---|---|
| 1 | **`GfxRenderer` は上流の更新が最も多いファイル** (`.cpp` 25 件 / `.h` 19 件。STATUS.md の「危険度の高いファイル」の筆頭) |
| 2 | **改名は 11 箇所に触る** — 同じファイルの中だけとはいえ、追随のたびに衝突する |
| 3 | **コメントで実体を書けば、踏む原因は消える。**名前だけが頼りの状態をやめるのが目的であって、名前を直すこと自体が目的ではない |

**→ §9.2 に divergence として記録し、コメントで実体を明示する。**

```cpp
enum class TextRotation {
  None,
  // 字の上 → 左、字の左 → 下。**名前に反して反時計回りである。**
  // 文字列は下から上へ読む向きに並ぶ。
  // 唯一の用途は画面キーボードの側面ボタンのラベル (">" "<" の 1 文字) で、
  // そこでは上向き・下向きの矢になり、これが正しい。変えないこと。
  Rotated90CW,
  // 字の上 → 右、字の左 → 上。**こちらが本当の時計回り。**
  // UTR #50 の R / Tr が言う向きで、縦書きの約物に使う。
  VerticalCW,
};
```

**`VerticalCW` の写像** (§15.7 で確定):

```
screenX = cellLeft + (cell − inkTop − h) + (h − 1 − glyphY)
screenY = cellTop  + (cell − left   − w) + glyphX
```

> **⚠️ テンプレートのインスタンス化が 1 つ増える。**
> `renderCharImpl` は `TextRotation` のテンプレートなので、
> 値を足すとコードが 1 本増える (仕様書 §「テンプレートの肥大」)。
> **縦書きには必要な出費である。**

### 16.4 全角数字の写し — **採用で確定**

**縦書きのときだけ `0-9` を `U+FF10-FF19` に写す。**

| 条件 | 動き |
|---|---|
| 全角数字がフォントにある | **全角に写して正立** (規格どおり。§15.5) |
| **無い** | **従来どおり半角をマス中央に寄せる** |

**条件は 1 つだけ。**`getGlyph()` が `nullptr` を返すかで決まる。

**英字は写さない** (§15.6)。`ｐａｒｅｎｔｈｅｓｉｓ` は日本語の組版に無い。

## 17. 実機で出た 3 点と、原因がひとつだったこと (v0.9 / 2026-10-30)

**縦書きは実機で動いた。**横書き 211 ページ → 縦書き 189 ページ (比 1.12)、
1 ページ 468 字 → 420 字 (比 1.11)。列幅 `em x 1.3` の計算どおりで、
§2.2 のモデルが正しいことの裏付けになった。

指摘は 3 点。**うち 2 点は同じ原因だった。**

### 17.1 ★ 原因: 昇り箱と em の箱を取り違えていた

| | 14 pt | 16 pt |
|---|---|---|
| フォントの昇り箱 (`ascender - descender`) | **43 px** | **49 px** |
| 組版の em (全角字の送り = 升目) | **29 px** | **33 px** |

**昇り箱は行送りの指標で、行間が入っている。**升目が表すのは em の箱のほうで、
**両者は 1.5 倍近く違う。**縦組みの配置をこの 2 つのどちらで測るかで、
結果が十数 px ずれる。

em の箱の上端は、昇り線から `ascender - em x 0.88` だけ下にある
(0.88 は表意文字の em 四角の通例の昇り)。**カードに入っているフォントの
6 サイズすべてで検算した:**

| 検算 | 結果 |
|---|---|
| `本` `戦` の墨 | `[emTop, emTop + cell]` を**ちょうど埋める** (14pt: 9..37、箱は 9..38) |
| `「` の墨 | 箱の**上端に接する** |
| `」` の墨 | 箱の**下端に接する** |
| `ー` の墨 | 箱の**中央** |
| `、` の墨 | 箱の**下端** (横書きで左下にあるのは正しい) |

`「` と `」` から独立に求めた上端が 6 サイズすべてで 1〜2 px 以内に一致し、
`asc - 0.88 x cell` とも一致した。**比ではなく実測で裏が取れている。**

> **§3.6 の「フォントは利用者依存」との関係**: 0.88 は比である。
> しかし `.cpfont` には em の箱を書く欄が無く、他に出どころが無い。
> **6 サイズで実測して合うことを確かめたうえで使う。**
> 外れても結果は列全体の一様な平行移動で、組みが崩れることはない。

### 17.2 「ローマの伸ばす棒が左に寄っている」

`ー` の墨は昇り箱の中央にある。これを**昇り線から数えて** 29 px の升目に
写すと、箱の差 (43 − 29 = 14) の半分だけ左へ寄る。

| | 左余白 | 右余白 |
|---|---|---|
| 直す前 | **3** | **21** |
| 直した後 | **12** | **12** |
| 参考画像 (em 20 → 29 換算) | 12.3 | 12.3 |

**`R` と `Tr` で後処理を分ける必要は無かった。**`ー` は規格上 `Tr` であって
`R` ではないので、分類で分ける案ではそもそも直らない。**em の箱で測れば
括弧も棒も同じ式で正しい位置に来る。**

### 17.3 ★ ついでに見つかった: 括弧が上下逆だった

同じ検算で、**`「` と `」` が升目の中で上下逆**に置かれていたことが分かった。

時計回りでは **グリフの上端が升目の右端へ、左端が升目の上端へ**行く。
だから縦の位置は**左のサイドベアリングそのもの**でなければならない。
実装は**右のサイドベアリング** (`cell - left - w`) を使っており、
これは反時計回りの式である。画素の回転 (`renderCharImpl`) は正しい
時計回りだったので、**配置だけが逆**という形で残っていた。

| | `「` の上余白 | `」` の上余白 |
|---|---|---|
| 直す前 | 0 (前の字に貼り付く) | 19 |
| 直した後 | **19** | **1** |
| 参考画像 (換算) | 19.6 | 2.2 |

**開き括弧は後ろの字に、閉じ括弧は前の字に寄る。**直す前は逆だった。

> **なぜ前回の照合で見つからなかったか**: 5 項目の照合は**字の形**
> (`「` の角がどちらを向くか、`（` の弧がどちらに膨らむか) を見ていた。
> 形は正しかった。**升目のどこに置かれているかは見ていなかった。**
> 形の一致は位置の一致を意味しない。

### 17.4 「上につく系が前の文字と近すぎる」 — 小書きかなを分けた

`、。` と小書きかなを同じ `Tu` の経路に入れ、**どちらも升目の右上に
貼り付けていた**のが原因。規格の分類は同じでも、組版上の意味が違う。

参考画像の実測 (縦書き文庫、em 20 px):

| 字 | 上余白 | 下余白 | 左余白 | 右余白 |
|---|---|---|---|---|
| `、` | 1.5 | 14.5 | 13.5 | 0.5 |
| `。` | 2.0 | 12.0 | 13.5 | 0.5 |
| `ャ` | **4.5** | **4.5** | 5.5 | 1.5 |
| `ぉ` | **4.5** | **4.5** | 5.5 | 1.5 |
| `ぇ` | **3.5** | **3.5** | 6.5 | 1.5 |
| `ィ` | 4.5 | 2.5 | 6.5 | 4.5 |

**小書きかなは 4 字とも上下が 1 px 以内で等しい —— 中央である。**
角に寄せる字ではない。横だけ、中央から右へ 1〜2.5 px (約 0.095 em) 寄る。

**→ `Tu` を 3 つに分けた。**

| 経路 | 対象 | 置き方 |
|---|---|---|
| 角寄せ | `、` `。` `，` `．` | 升目の右上、余白 2 px |
| 中央＋右寄せ | 小書きかな 24 字 | 上下中央、横は中央から em の 1/10 だけ右 |
| そのまま正立 | `！` `？` `゛` `゜` | 寄せない |

実装では**例外の 8 字だけを列挙し、残りの `Tu` を小書きかな扱い**にする。
24 字を書き並べるより短く、規格に字が増えても壊れない。

### 17.5 ★ `、。` の上の余白は 2 px のままでよい

実測 0.075 em。升目 29 px で 2.2 px、33 px で 2.5 px。**現状の 2 px が正しい。**
横の余白だけは実測 0.025 em (29 px で 0.7 px) で、現状の 2 px より 1 px ほど
詰めるのが実物に近い。**1 px のために定数をもう 1 つ増やす価値は無いと判断し、
`VERTICAL_CORNER_MARGIN` は 2 のまま据え置いた。**

### 17.6 列全体が 9 px 下がっていた

正立の経路はベースラインを `cellTop + ascender` に置いていた。これも昇り箱で
測っているので、**列全体が `emTop` (14 pt で 9 px) ぶん下へずれ、列の最後の
字が下の余白へはみ出す。**`cellTop + emAscent` に直した。

小書きかなを「升目の中央」と定義する以上、**周りの字が同じ箱に収まっていないと
揃わない。**この 2 つは一緒に直す必要があった。

### 17.7 試し刷りと実機の対応

**①②とも試し刷りで直してから焼く**方針で進めた。`scripts/vertical_proof.py` に
同じ式を入れ、組んだ結果を参考画像と数値で突き合わせてある
(比較画像 `docs-jp/mockups/vertical/ref_vs_proof.png`、再生成できるので追跡しない)。

| 字 | 試し刷り 上/下/左/右 | 参考画像 (換算) |
|---|---|---|
| `「` | 19/1/9/0 | 19.6/0.7/3.6/0.7 |
| `」` | 1/19/1/8 | 2.2/18.1/0.7/5.1 |
| `ー` | 3/4/12/14 | 4.1/4.1/12.3/12.3 |
| `。` | 2/-/-/2 | 2.9/-/-/0.7 |
| `ャ` | 6/6/7/4 | 6.5/6.5/8.0/2.2 |
| `ィ` | 5/6/9/7 | 6.5/3.6/9.4/6.5 |

左右の余白が参考画像とずれているのは**グリフの墨の幅が違うから**で
(我々の `「` は 20 px、参考は換算 24.6 px)、位置の問題ではない。
**接する辺の余白はすべて 1〜2 px 以内で一致している。**

## 18. ★ 「もっさり」の正体 — 先読みの配線漏れ (v1.0 / 2026-10-31)

縦書きは実機で正しく組めたが、**操作がもっさりする**と報告が来た。

### 18.1 切り分け

羅闇への 2 つの質問で確定した。

| 質問 | 回答 | 意味 |
|---|---|---|
| 横書きでも重いか | **横書きは快適** | 縦書き固有 |
| 開いた直後だけか | **いつでも重い** (「推定」が消えた後も) | 索引ではない |

索引が無罪であることはコードからも裏付けられた。
折り返しの判定がここで分かれる ([TxtReaderActivity.cpp:640-642](../src/activities/reader/TxtReaderActivity.cpp))。

    横: renderer.findWrapOffset(...)   — グリフの送り幅を測る。SD に触る
    縦: advanceCodepoints(...)         — 継続バイトを読み飛ばすだけ

**縦書きの索引構築はフォント I/O がゼロで、横書きより速い。**
`CACHE_VERSION` 6 → 7 による作り直しは 1 回きりの代償で、
`skipLoopDelay()` と 1 ティック 1 ページも向きに無関係に効いている。

### 18.2 ★ 原因 — `drawTextVertical()` が走査モードを知らなかった

横書きの `drawText()` の冒頭にはこれがある。

    if (fontCacheManager_ && fontCacheManager_->isScanning()) {
        fontCacheManager_->recordText(renderedText, resolvedFontId, style);
        return;
    }

**`drawTextVertical()` には無かった。**
`FontCacheManager.h` の注釈が「called by `GfxRenderer::drawText()`」と
書いているとおり、新しい経路は配線されていないままであった。

`renderPageVertical()` は横書きと同じ 2 パス構造を持っているので、
配線がないと次のことが起きる。

| 段 | 意図 | 縦書きの実際 |
|---|---|---|
| `createPrewarmScope()` | 走査 ON、**キャッシュを空に** | 同じ |
| 1 回目の描画 | 字を記録するだけ | **空のキャッシュで本当に描く** |
| `endScanAndPrewarm()` | 全グリフを **1 回の SD 走査**で読む | `scanText_` が空 → **即 return** |
| 2 回目の描画 | キャッシュ命中、SD 読みゼロ | — |

**先読みを使わないより悪い。**`PrewarmScope` のコンストラクタが
`clearCache()` を呼ぶため、**空にしてから本番を迎える**からである。

### 18.3 1 グリフあたりの代償

mini が積まれていないグリフは**オーバーフロー経路**に落ちる
([SdCardFont.cpp:1448-1485](../lib/EpdFont/SdCardFont.cpp))。

    .cpfont を open → seek → グリフ 16 B を read
                      → seek → ビットマップを read → new でヘープ確保

リングは **`OVERFLOW_CAPACITY` = 128**。日本語 1 ページ 420 字の
異なり字数は **150～250 程度で 128 を超える**ので、
超えた分は FIFO で追い出され、再び現れたときに再度 open される。
**「異なり字数ぶんの open」では済まない。**

### 18.4 配線だけでは足りなかった 3 点

記録するのは「実際に描く字」である。縦書きには
**自分のコードポイントと別のグリフで描く字が 2 種類ある。**

| 字 | 描くグリフ | 対応 |
|---|---|---|
| 半角数字 `0`～`9` | 全角 `U+FF10`～`U+FF19` | 全角を**追加で**記録する |
| `…` `‥` | どちらも `U+2026` のグリフ | `U+2026` を記録する |

全角は**追加**であって差し替えではない。フォントに全角形が無いときは
半角に落とすので、半角も先読みの対象のままである必要がある。

走査中に `getGlyph()` を呼んで全角の有無を調べるのは**本末転倒**である。
それ自身が SD の open になる。判定せず両方記録し、
無い字は `prewarm()` が `missed` として数えるだけにする。

3 点目は `drawLeaderDots()` 自身である。`getGlyphBitmap()` を直接呼んで
描くので、走査中に入ってはいけない。現在は冒頭の return で到達しないが、
**描画関数は自分で走査を知っているべき**なので、他の描画 API と
同じ `isScanning()` ガードを置いた。

### 18.5 走査パスで 1 画素も描かれないこと

走査中に `renderColumns()` から到達できる描画は次の 2 つだけである。

| 経路 | 状態 |
|---|---|
| `renderCharImpl<...>` | 冒頭の return で**到達不能** |
| `drawLeaderDots()` | 到達不能。加えて**自身でもガード** |

画素を置くのは `drawPixel()` だけで、それを呼ぶのはこの 2 つしかない。
`renderStatusBar()` と表示処理は `renderColumns()` の外にあるので走査に入らない。

### 18.6 無罪と判定した候補

疑って潰したものを残す。**あとから同じ場所を疑わないためである。**

| 疑い | 判定と根拠 |
|---|---|
| 転置でキャッシュの当たりが悪い | **無罪。**ESP32-C3 は内部 SRAM にデータキャッシュを持たず、アクセスは一定遅延。`drawPixel()` は縦横とも 1 画素 1 呼び出しで 1 バイトの read-modify-write。**行方向のまとめ書きがどちらにも無い**ので、歩幅が 60 B か 1 B かは費用に出ない |
| `getGlyph` が 1 文字 2 回 | **横書きも同じ。**縦書き固有の劣化ではない |
| `vo::lookup` の二分探索が毎文字 | 183 件で 8 回程度の整数比較。420 字で数十マイクロ秒。**列ごとに hoist する価値はない** (字ごとに答えが違うので hoist できる形でもない) |
| 約物のオフセット計算が毎回 | 整数の加減算が数本。グリフ 1 枚の SD 読みに対して**無視できる桁** |
| 縦書きで毎ループ増えた処理 | **ない。**`isVertical` の参照は 6 箇所、毎フレーム走るのは `renderPage()` の分岐 1 つ |

### 18.7 效果の見積もり (コードから)

1 ページあたりの `.cpfont` の open 回数。本文 420 字、異なり字数 U、
スタイル 1 種 (REGULAR) とする。

| | 走査パス | 本番パス | 合計 |
|---|---|---|---|
| **直す前** | U～420 (リング 128 を超えてスラッシング) | U～420 | **約 380～840** |
| **直した後** | **0** (字を記録するだけ) | **1** (`prewarmStyle` が 1 回 open し、グリフ番号順に読む) | **1** |

アンチエイリアス ON なら本番が 3 パスになるので、直す前はさらに増える。
直した後は mini が生きているので **1 回のまま**である。

`prewarmStyle()` がスタイルごとに 1 回 open し、`globalIndex` でソートして
**連続読みに近づけている**ことも效いている ([SdCardFont.cpp:955-975](../lib/EpdFont/SdCardFont.cpp))。

#### `MAX_PAGE_GLYPHS` = 512 は足りるか

本書と仕様書の日本語本文 (表とコードを除いた 41,936 字) を
420 字ずつ 99 窓に切って、異なりコードポイント数を数えた。

| | 値 |
|---|---|
| 最小 | 58 |
| 中央値 | **159** |
| p90 | 175 |
| 最大 | **190** |

技術文書は語彙が偏るので、文学作品はこれより多い (漢字の種類が多い)。
それでも **250 を越えるとは考えにくく、512 には十分な余裕がある。**
逆に **128 は全窓の半数超で超えている**ので、オーバーフロー経路での
スラッシングは推測でなく**必然**であった。

### 18.8 実機での結果 (2026-10-31)

**解消した。**羅闇の報告は「快適になった」。

**ただしこれは体感であって、ミリ秒の実測ではない。**
計測コードを入れずに直したので、数字は§18.7 の見積もりだけである。
次に計測コードを入れる焼き (② の等価性検証) のときに、
`logStats()` がすでに持っている SD 読みの統計を一緒に出せば
**open 回数を実数で裏付けできる** (`FontCacheManager::logStats()`)。

| | 状態 |
|---|---|
