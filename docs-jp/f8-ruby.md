## 0.5 ★ 着手前に必ず読む — ルビの領域は **em の箱**から測る

**各段階の実装の前にここを読むこと。**

縦書きで `ascender`（昇り箱）と em の箱を取り違え、
**括弧の上下逆・長音符の左寄り・列全体の 9 px 下がり**を同時に出した。
**ルビでも同じ罠がある。**

```cpp
// GfxRenderer.cpp:2405-2406 — 升目が立っている em の箱
const int emAscent = cellSize * VERTICAL_EM_ASCENT_PERCENT / 100;  // 88
const int emTop = ascender - emAscent;
```

| | |
|---|---|
| `ascender` | フォントの**昇り箱**。em の箱より**半分ほど高い** |
| `emAscent` | 升目 1 つぶんの高さ = `cellSize * 88 / 100` |
| `emTop` | 昇り箱の上端から em の箱の上端までの差 |

**親文字の上（縦書きでは右）に確保する量を `ascender` 基準で決めると
1.5 倍ずれる。**上流の `getRubyShift(ascender)` が `ascender / 2` を返すのは
**EPUB の行箱の中での話**であって、
**升目に組む我々の縦書きにそのまま持ち込めない。**

> **確保量の設計は、`cellSize` と `emAscent` で書く。**
> `ascender` が式に出てきたら、それが昇り箱で正しいのかを必ず確かめる。
> 14 pt で `emTop` は 9 px ある。**9 px は 1 行ぶんより大きい。**

## 1. ★ 最大の山 — ページモデル

### 1.1 いまのモデル

```cpp
// TxtReaderActivity.cpp:296-303 — 除算 1 回。ページは固定セル数
linesPerPage = viewportWidth / columnWidth;    // 縦書き
linesPerPage = viewportHeight / lineHeight;    // 横書き
charsPerUnit = viewportHeight / cellSize;      // 縦書きの 1 列の字数
```

| | |
|---|---|
| `pageOffsets` | `content.u8` への**バイト位置**の配列 |
| 進捗 | 同じく**バイト位置** (`currentOffset`) |
| ページの切り方 | **本数を数える。**`loadPageAtOffset()` が `linesPerPage` 本作ったら終わり |

**縦書き (F-5 段階1) はこのモデルを守れた。**
升目の大きさが変わっただけで、
**1 ページ = 固定数のセルという性質は壊れなかった。**
だからページ境界のバイト位置は無傷で、索引もキャッシュもそのまま動いた。

### 1.2 ルビは守れない

ルビは親文字の**外側**に領域を要求する（横書きは上、縦書きは右。F-5 §15.8）。
領域の大きさは**その行にルビがあるかどうか**で変わる。

```
lineHeight / columnWidth が行ごとに変わる
  → linesPerPage が「1 ページあたりの本数」でなくなる
  → ページは「高さを積んで溢れたら切る」ことになる
```

**上流の EPUB 側はこれをやっている。**

```cpp
// ChapterHtmlSlimParser.cpp:1663-1665 — 行ごとに高さを出して積む
const int lineHeight =
    renderer.getLineHeight(fontId, lineCompression) + line->getRubyShift(...);
...
if (currentPageNextY + lineHeight > viewportHeight) { /* 次ページへ */ }

// TextBlock.h:91 — 421 コミット経っても変わっていない
int getRubyShift(int ascender) const { return hasRuby() ? (ascender / 2) : 0; }
```

**ルビの領域は `ascender / 2`。**親文字を行箱の中で下にずらし、
ルビはその上 (`wordY - ascender`) に 50% 縮小で描かれる。

## 2. 案の比較

### 案A — 行ごと可変高（上流の EPUB と同じ）

ルビのある行だけ `ascender/2` 高くし、ページは**高さを積んで切る。**

| 観点 | |
|---|---|
| `pageOffsets` の意味 | **保たれる。**バイト位置のままで、意味は変わらない |
| F-9 の遅延索引 | **そのまま使える。**`advanceIndex()` は `loadPageAtOffset()` を繰り返すだけで、1 ページの切り方が本数から高さに変わっても構造は同じ |
| F-9 の等価性検証（条件②） | **成立する。**ページの切れ目はそのページの先頭からの内容だけで決まり、前のページの履歴に依存しない。**この性質が崩れていたら案A は不成立だった** |
| `CACHE_VERSION` | **繰り上げ必須** (7 → 8)。ページの切れ目が動く |
| 進捗 | バイト位置なので**壊れない。**ページ番号は作り直される |
| 代償 | **ページあたりの行数が一定でなくなる。**ルビの多い章は 1 ページが短くなる |
| 傍点 (A7) | **そのまま載る。**領域が行ごとにあるので、そこに点を置く |

**ページ数が揺れることは問題にならない。**進捗の表示は
`currentOffset / fileSize` のバイト比で出しており、ページ番号ではない。

### 案B — 全行に領域を確保（固定セル維持）

本にルビが 1 つでもあれば、**全行**を `ascender/2` 高くする。

| 観点 | |
|---|---|
| ページモデル | **無傷。**`linesPerPage` はスカラーのまま |
| `CACHE_VERSION` | 繰り上げ必要（行高が変わる） |
| 実装量 | **案A の半分以下** |
| 代償 | **ページの 2〜3 割を捨てる** |

縦書きで実測すると代償が見える。

| | 現状 | 案B |
|---|---|---|
| 列幅 (12pt, NORMAL) | `cell x 1.3` = 32 px | + `cell/2` = **44 px** |
| 1 ページの列数 (464 px) | **14** | **10** |

**『最終戦争論』はルビ 47 個 / 323 行。**
その 47 行のために**残り 276 行ぶんのページを 28% 削る。**
ルビの無い本には影響が無いが、**ルビのある本ほど損をする**という
逆向きの性質になる。

### 案C — 行間に押し込む（領域を増やさない）— **却下**

`lineSpacing` の余白にルビを入れる。行高は変えない。

| | |
|---|---|
| ページモデル | **完全に無傷。**キャッシュの繰り上げも不要 |
| 必要条件 | ルビ 50% に対し、NORMAL (130%) の余白は 30%。**足りない。**WIDE (150%) が要る |
| 結果 | **「ルビを出すなら行間を広くしろ」という制約**になる |

**却下する。宿題② に反する。**

> 宿題②: **「設定に触るとき、`lineSpacing` への依存をこれ以上深めない」**
> (STATUS.md、2026-10-31)

縦書きの列幅が既に `COLUMN_RATIO_PERCENT[lineSpacing]` で
`lineSpacing` に依存しており、§19.5 の `static_assert` を要した。
**ルビの可否まで `lineSpacing` に繋ぐと、上流が値を足すたびに
「ルビが出なくなる設定」が増える。**安さの代償が大きすぎる。

### 2.4 判断 — **案A**

| | 案A | 案B | 案C |
|---|---|---|---|
| `pageOffsets` の意味 | 保たれる | 保たれる | 保たれる |
| F-9 がそのまま使えるか | **使える** | 使える | 使える |
| ページの代償 | ルビのある行だけ | **全行 8〜38%**（実測） | 無し |
| `lineSpacing` への依存 | 無し | 無し | **増える（宿題②違反）** |
| 傍点 (A7) の足場 | **できる** | できる | **できない** |
| 実装量 | 多い | 中 | 少ない |
| 上流との一致 | **同じ形** | 別 | 別 |

**案A。**代償が「ルビのある行だけ」に閉じるのが決め手で、
**上流の EPUB 側と同じ形**になるので、
将来 EPUB 側の修正を読むときに対応がつく。

### 2.5 ★ 行の高さの決め方 — `max()` で案C と同じ動作になる (2026-11-05 実測)

紙の本ではルビがあっても行の高さは変わらない。**行間に収まるなら
広げる必要がない。**だから案A の行高はこう決める。

    行の高さ = max(通常の行送り, 升目 + ルビの幅 + 1)

**行間が十分なら右の項が左を超えないので、行は伸びず、案C と同じ動作になる。**
案C を却下した理由（`lineSpacing` への依存を深める = 宿題②違反）は
避けられている。ここでは `lineSpacing` に**依存していない** —
通常の行送りを下限として使うだけで、収まるかどうかの判定には使わない。

UDEVGothic の `.cpfont` から読んだ実測値（計算値ではない）。

| | 12pt | 14pt | 16pt | 18pt |
|---|---|---|---|---|
| 升目 (em) | 25 | 29 | 33 | ~~37~~ → **38** |
| ルビの送り | ~~13~~ | ~~15~~ | ~~17~~ | ~~19~~ → 実際は全サイズ **17**（8pt 固定） |
| 伸び（縦・広い） | ~~+2~~ | ~~+7~~ | ~~+11~~ | ~~+11~~ |

> **この表は §2.5-2 で置き換わっている。**「ルビの送り」は
> `(升目+1)/2` の見積りで、実装はそうなっていない（8pt 固定の 17px）。
> 18pt の升目 38 もここでは 37 と誤っていた。以下の不揃いの数値も
> すべて §2.5-2 の実測表が正しい。

**縦書き・行間「広い」（羅闇さんの設定）では +2px。**升目の 5% で、
画面では見えない。設定ごとの不揃いの大きさ:

| 設定 | 行の不揃い | 1 列減り始める本数 |
|---|---|---|
| 縦・広い | **5%** | **11 本** |
| 縦・普通 | 22% | 3 本 |
| 縦・狭い | 39% | 2 本 |
| 横書き | 34%（横書きは `lineSpacing` を適用しないため） | 2 本 |

1 ページの列（行）が 1 つ減るのは、**12 列のうち 11 列以上がルビを持つとき**
だけである。実際の本ではまず起きない。

> **2026-11-07 訂正。**ここは最初「10 列以上」と書いていた。
> 正しい式は `余り / 増分 + 1` で、余り 20 px / 増分 2 px から **11 本**である。
> 2c の全数検証で数え直した（`『最終戦争論』`の実測の最大は 3 本）。
> 横書きの不揃いも 38% ではなく **34%**（行送り 29 px、ルビ行 39 px の実測）。

### 2.5-2 ★ 実装された形 — ルビの面は **8pt 固定**、送りは 47px (2026-11-10 実機実測)

`(升目+1)/2` は**二度まちがえた。**まず「半分の大きさの面で描ける」と
置いたのが誤りで（家族は整数 pt の面しか持たない）、
次に実測値と称して **16px** を使ったのが誤りだった。**実機は 17px である。**

| | |
|---|---|
| ルビに使う面 | `findNearestSize(本文 pt / 2)` → この家族では**本文 12/14/16/18pt のすべてで 8pt** |
| 8pt の全角 em | **17px**（`toPixel(16.6875)`。16.6875 は §7.1 の計測表の値そのもの） |
| ルビ行（列）の送り | `max(通常の送り, 升目 + 17 + 1)` |
| 追加の RAM | **0。**8pt は `kUiFontSizes` で既に常駐している |

em の px 換算を全 6 サイズで引き直した（2026-11-10）。
**§7.1 の計測表そのものは正しかった** ── 壊れていたのは
そこから `toPixel` を取るのに使った自作の読み取りだけである。

| 本文 pt | 格納値 (12.4) | 理論値 `pt×150/72` | 差 | `toPixel` = `(fp+8)>>4` |
|---|---|---|---|---|
| 8 | 16.6875 | 16.6667 | +0.0208 | **17** |
| 10 | 20.8125 | 20.8333 | −0.0208 | **21** |
| 12 | 25.0000 | 25.0000 | 0 | **25** |
| 14 | 29.1875 | 29.1667 | +0.0208 | **29** |
| 16 | 33.3125 | 33.3333 | −0.0208 | **33** |
| 18 | 37.5000 | 37.5000 | 0 | **38** |

**6 サイズすべてが理論値と一致する。**差は最大 0.0208px =
ちょうど 1/48 で、これは 12.4 固定小数点の刻み 1/16 の 1/3 ──
`pt×150/72` を 1/16 に丸めた値が格納されている、ということである。
丸めの例外は無い。`toPixel` も 6 サイズすべてで `round(理論値)` に一致する
（18pt の 37.5 は切り上げで 38）。

**誤りの原因は glyph レコードの大きさだった。**`EpdGlyph` は
`__attribute__((packed))` が付いていない（[EpdFontData.h:131-139](../lib/EpdFont/EpdFontData.h)）ので、
`uint32_t dataOffset` の前に 2 バイトの詰めが入り **`sizeof(EpdGlyph)` は 16** である
（ファイル上の位置も `computeStyleFileOffsets` が `sizeof(EpdGlyph)` で計算している。
[SdCardFont.cpp:496](../lib/EpdFont/SdCardFont.cpp)）。
自作の読み取りは 12 バイトと 16 バイトを推定で選んでいて、12 を選んでいた。
12 バイトで読むと索引が進むほどずれが溜まるので、
**字によって当たる字と外れる字が混ざる** ── `０`『本』『あ』は正しい送りを返し、
`一` だけ 16.3125 を返し、『戦』『ア』は advance 0 と幅 77px という
あり得ない値を返していた。`getFullWidthAdvance()` が見るのは
よりによって `一` (`U+4E00`) である。

| 字 | 12B で読む | 16B で読む（正） |
|---|---|---|
| `０` U+FF10 | 16.6875 ✅ | 16.6875 |
| `一` U+4E00 | **16.3125 ❌** | 16.6875（字形 17×2px の横棒 1 本） |
| `本` U+672C | 16.6875 ✅ | 16.6875 |
| `戦` U+6226 | **0.0000 ❌**（幅 77px） | 16.6875 |

**1 字だけ読んで信じたことが誤りだった。**同じファイルの別の字を
読めば食い違いがその場で出た。§8.7-23 の運用規則に
「複数の字で読んで、1 つでも食い違ったら読み取り自体を疑う」を加える。

§2.5 の表は 8pt を 16、18pt を 37 としていた。**どちらも 1px 低い。**
14pt は 29 で変わらないので、実機の測定（升目 29px）と矛盾しなかった。

ルビ行の送り、14pt 本文での実測と全数検証（『最終戦争論』）:

| 設定 | 通常→ルビ行 | 1 列減り始める | 列数が減ったページ |
|---|---|---|---|
| 縦・広い | 43 → 47 (+9%) | 9 本 | **0 / 230** |
| 縦・普通（実機の設定） | 37 → 47 (+27%) | 3 本 | **2 / 192**（87, 146 ページ） |
| 縦・狭い | 33 → 47 (+42%) | 1 本 | 29 / 167 |
| 横書き | 42 → 47 (+12%) | 2 本 | 8 / 69 |

> **以前の表（45px）も、その訂正（46px）も誤り。**47px が実機である。
> 変わるのは不揃いの率と「減り始める本数」で、
> **ページ数と切れ目は 4 設定すべてで旧実装（本数で切る）と一致し、
> 組まれた本文の総バイトも 163,785 B で一致する**（§5.5 の不変条件）。
> 横書きだけ「列数が減ったページ」が 4 → 8 に増えた。

**`CACHE_VERSION` 8 → 9。**ルビ行の送りが変わればページの切れ目が動くので、
索引を作り直させる必要がある。

### 2.5-3 ★ ルビの面が取れないときは帯を取らない (2026-11-11)

`rubyEm` には**面が読めなかったときの見積もり** `(cellSize + 1) / 2` が
入っていた。14pt で 15px、つまり帯が 45px になる。
**しかし描画経路はすべて `rubyFontId` で守られている**ので、
面が無いときに描かれる字は 0 件である。
**描けない字のために 1 ページぶんの余白を取っていた。**

しかもそれを引くのは、**SD に和文フォントが無い読み手**
── 行を失う余裕が最も無い側である。

| | 旧 | 新 |
|---|---|---|
| 面が取れる | `rubyEm` = 実測 17px、送り 47px | **同じ** |
| 面が取れない | `rubyEm` = 見積もり 15px、送り **45px** | `rubyEm` = **0**、送り = 通常の送り |

#### 対照実験 — 面が取れる経路で 1 箇所も動かない

字下げ 0 の対照実験と同じ形で、縦書き 3 設定 × 4 ファイル = 12 通り。

| 本 | 設定 | 旧の送り | 新の送り | ページ |
|---|---|---|---|---|
| 最終戦争論 | 狭い / 普通 / 広い | 47 / 47 / 47 | 同じ | 167 / 193 / 231 |
| 戦争史大観 | 同 | 47 / 47 / 47 | 同じ | 328 / 376 / 451 |
| 新日本の進路 | 同 | 47 / 47 / 47 | 同じ | 28 / 33 / 39 |
| 試験ファイル | 同 | 47 / 47 / 47 | 同じ | 33 / 37 / 39 |

**12/12 一致。**面が取れるときの式は `max(normalPitch, cellSize + rubyEm + 1)` の
まま触っていないので、これは当然そうなるべきもので、
**そうなっていることを確かめた**という意味の表である。

#### 面が取れない場合に動く量（これが修正の中身）

| 本 | 狭い | 普通 | 広い |
|---|---|---|---|
| 送り | 45 → **33** | 45 → **37** | 45 → **43** |
| 最終戦争論 | 167 → 165 | 193 → 192 | 231 → 231 |
| 戦争史大観 | 328 → **322** | 376 → 376 | 451 → 451 |
| 試験ファイル | 33 → **28** | 35 → 33 | 39 → 39 |

**最大 6 ページぶんの余白が戻る**（戦争史大観・狭い、1.8%）。
`CACHE_VERSION` は 2g で既に 10 に上げているので据え置き

## 3. 記法の解析

### 3.1 いま何をしているか

`AozoraStrip` は**ルビを捨てている**（`《…》` も `｜` も）。
段階1.5 でも捨てたままである。

### 3.2 何を `content.u8` に残すか

**★ ここがバイト位置の問題に直結する。**

> 表示時に剥がすとバイト位置がずれ、**ページ索引と
> `.md` のチェックボックス書き戻しが壊れる** (`AozoraStrip.h` の先頭)。

| 案 | 中身 | 評価 |
|---|---|---|
| **(i) 記法をそのまま残す** | `content.u8` に `親文字《るび》` を残し、読む側が毎回解析する | **採用。**ファイル形式が増えない。バイト位置は「記法を含んだ位置」で一貫する |
| (ii) 別索引に出す | `(offset, rubyText)` の表を別ファイルに | 形式が 1 つ増え、`content.u8` と同期を取る必要が出る |
| (iii) 独自の印に置換 | 制御文字で囲む | 本文に現れない保証が要る。(i) と利点が同じで危険だけ増える |

**(i) を採る。**`AozoraStrip` は**ルビだけ落とさない**ようになる
（`［＃…］` の除去や外字の復元は変わらない）。
`ENCODING_VERSION` は **4 → 5**。

代償は**読むたびに解析すること**で、折り返しの走査の中で起きる。
`loadPageAtOffset()` は既にチャンクを舐めているので、
**同じ走査に `《` の判定を 1 つ足す**形になる。

### 3.3 親文字の決定

| 形 | 親文字 |
|---|---|
| `｜漢字かな《るび》` | **`｜` から `《` まで**。明示 |
| `漢字《るび》` | **直前の漢字の連続。**ひらがな・記号で止まる |

`｜` は段階1 から既に認識されている（同じ行に `《` があるときだけ
範囲指定として扱い、無ければ普通の全角縦棒として素通し）。
**この判定はそのまま使える。**

### 3.3-1 ★ 「これはルビか」の判定は 1 つだけ書く (2026-11-06)

**同じ判定を 2 箇所に書かない。**2b は「閉じの `》` があれば無条件に落とす」、
2f は「親文字が無ければルビではない」という**別の規則**で同じことを
判定していた。規則が 2 つあれば必ず食い違う。

食い違いの実害: 親文字の無い `《るびだけ》`（行頭）や `、《てん》` は
2f から見てルビではないが、2b は落とす。**ルビでないものが黙って消える。**

**2f の判定が正しい。焼き 3 で 1 つにまとめ、2b と 2f の両方から呼ぶ。**
焼き 1（2a+2b）は合格済みなので、それまでは
「親文字の無い `《》` が消える」中間状態が残る。許容する。

これにより、青空文庫が本文中の literal な `《` を `※《` と書く約束を
**守っているかどうかを調べる必要がなくなる。**守られていなくても
親文字の有無で正しく判定できる。

### 3.3-2 親文字判定の標本 — 規則を変えるときの回帰試験 (2026-11-06)

文法の形を並べた 23 件で全数確認した。**23/23 正解。**
規則を触るときはこの標本を通すこと。

| 入力 | 判定 | 親文字 |
|---|---|---|
| `漢字《かんじ》` | auto:kanji | 漢字 |
| `｜日本国憲法《にほんこくけんぽう》` | bar | 日本国憲法 |
| `カタカナ《かたかな》` | auto:kata | カタカナ |
| `ゴルバチョフ《ソ連書記長》` | auto:kata | ゴルバチョフ |
| **`お父《とう》さん`** | auto:kanji | **父**（ひらがなで止まる） |
| `其処《そこ》から見《み》える` | auto:kanji ×2 | 其処 / 見 |
| **`｜一《いち》｜二《に》`** | bar ×2 | **一 / 二** |
| `ＡＢＣ《…》` / `abc《…》` | auto:latin | ＡＢＣ / abc |
| `々《おなじ》` | auto:kanji | 々 |
| `、《てん》` / 行頭 `《るびだけ》` | **empty** | 無し（ルビではない） |
| `開かない《かっこ`（閉じ無し） | 対象外 | 手を付けない |

**連続ルビが 1 条件で通るのが要点。**`｜` を後ろから探すとき
「`｜` と `《` の間に別の `》` が無いとき」だけ対応させる。
この条件が無いと 2 つ目の `《` が `一《いち》｜二` を親文字にしてしまう。

### 3.3-3 ★ 2f の全数検証 — 本編 44 件で `｜` は 3 件とも効いている (2026-11-10)

実装した `rubyParentStart()` を『最終戦争論』の `content.u8`（ファーム自身が
書いたもの）全体に通した。

| | |
|---|---|
| 注記 | **44 件** |
| 親文字の種類 | **44 件すべて漢字** |
| 走査した字数 | 1〜4 字（中央値 2。1 字 15 件 / 2 字 21 件 / 3 字 4 件 / 4 字 4 件） |
| 行頭まで走査した例 | **0 件** |
| 親文字が 1 字も無い例 | **0 件**（試験ファイルには 2 件ある） |

**`｜` は 3 件あり、3 件とも省略できない。**本編の `｜` は走査を**狭める**側で効く。

| 入力 | `｜` 無しで走査すると | `｜` が与える親文字 |

試験ファイルには**逆向き**の例がある。`｜` が走査を**広げる**側で、
種類の境界を越える。

    霧の｜ロンドン警視庁《スコットランドヤード》
    走査だけでは「警視庁」しか取れない

**走査と `｜` はどちらも要る。**片方だけでは本編と試験ファイルの
どちらかが崩れる。

### 3.4 ルビが親文字より広いとき

上流 #4204 (`ad53eb64`) が W3C「日本語ルビの簡便な配置」に寄せた。

| | |
|---|---|
| ルビが**広い** | 親文字の**字間**にも両端にも空きを入れて長さを揃える。**字間は両端の 2 倍** |
| 隣への**食い込み** | 「ルビ端文字の半分」と「隣語の 1/4」の**小さい方**まで |

#### 3.4-1 ★ 決定 — はみ出しを許し、**後ろだけ**に掛ける (2026-11-06)

日本語の組版には**「ルビの掛け」**（JIS X 4051）があり、ルビが親文字より
長いとき**隣の仮名に掛けてよい。妥協ではなく規格どおり**である。

実測した限界:

    ルビの送り 13px / 升目 25px = 0.52
    -> ルビの字数が親文字の 1.92 倍までは親文字の幅に収まる

日本語のルビはほぼこの範囲に入る。超える例:

    大東亜戦争《だいとうあせんそう》   親 5 字 / ルビ 10 字 = 2.0 倍
    -> 125px に 130px。超過 5px（親文字 1 字につき 1px）

**掛ける方向は「後ろだけ」。**理由は実装の単純さである。
縦書きは列を上から下へ 1 字ずつ進める（`renderPageVertical()`）ので、
**後ろへ掛けるぶんはまだ描いていない領域**である。前にも掛けると、
すでに置いた字の位置を遡って見る必要が出る。端のクランプも、
後ろだけなら**列（行）の終端 1 箇所**で済む。

規格は前後の仮名に掛けられるとしているので、**理由を残しておけば
後から前方にも広げられる。**

> ### ★ 3.4-2 決定の上書き — **中央に寄せる** (2026-11-10)
>
> **上の「後ろだけ」は撤回する。**実装の都合で決めた案を、実データで覆した。
>
> | 実測（『最終戦争論』44 件） | |
> |---|---|
> | ルビが親文字より広い | 21 件（48%） |
> | 同じ行で隣り合うルビの衝突 | **0 件。**いちばん詰まっても 15 px 空く |
> | 列の帯からはみ出す | **0 件**（帯は `升目+1+ルビ em` ちょうど） |
>
> **「後ろだけ」を選んだ理由は、前に掛けると置いた字を遡って見る必要がある、
> だった。それは起きない。**ルビは親文字の中央に置くだけで、
> 親文字の位置は `prefix` の送りを測れば前向きに求まる。遡りはない。
>
> そして**中央寄せが正しい組版**である。後ろに寄せると、
> 親文字 1 字にルビ 4 字のようなとき（`侍《さむらい》`）
> **ルビの重心が親文字から外れて、次の字に付いて見える。**
>
> 代わりに必要になったのは**両端のクランプ**で、これは後ろだけでも要った。
> 実測で**境界試験ファイルの 18 本が頁の外に出た**（最大 72 px）。
> 中央寄せにしたから増えたのではなく、
> **ルビが半分の大きさではない（8pt = 17px、本文 14pt = 29px の 59%）**
> からである。§2.5 の `(em+1)/2` を実測値に置き換えたときに初めて見えた。

## 5.5 ★ 2c で `linesPerPage` が消える — 索引の検証項目を作り直す

**行高が可変になると `linesPerPage` という定数が存在しなくなる。**
いまそこに `viewportHeight` が畳み込まれているので、
**畳み込む先が消える。**

### 5.5-1 いまの検証項目

索引キャッシュの先頭 (`TxtReaderActivity.cpp:1048-1140`) はこれを突き合わせる。

| 項目 | 種類 | 何が畳み込まれているか |
|---|---|---|
| `fileSize` | 入力 | — |
| `viewportWidth` | **入力** | — |
| `linesPerPage` | **結果** | **横書き: `viewportHeight`** / 縦書き: 列数（`viewportWidth` と列幅） |
| `charsPerUnit` | **結果** | 縦書き: `viewportHeight` と升目 |
| `fontId` | 入力 | — |
| `screenMargin` | 入力 | — |
| `paragraphAlignment` | 入力 | — |

コード中のコメントがそのまま言っている。

> 横書きでは `viewportHeight` は既に `linesPerPage` に畳み込まれているので、
> `viewportWidth` とその 2 つで、ページ境界を動かしうるものは全部覆える。
> 縦書きでは `viewportWidth` が列数に畳み込まれ、
> **高さには行き場が無いので、そのまま保存している。**

**`lineSpacing` と縦書きの切り替えに専用の項目が無いのは、
どちらも上の 2 つのどちらかを動かすからである。**

### 5.5-2 2 回目である

縦書き (F-5) でも同じ形を踏んだ。
`viewportWidth` が列数に畳み込まれ、**`viewportHeight` の畳み込み先が無かった。**
そのとき `charsPerUnit` を項目に足して塞いだ。

| | 畳み込み先が消えるもの | そのとき足したもの |
|---|---|---|
| F-5 縦書き | `viewportHeight`（縦書きのとき） | `charsPerUnit` |
| **F-8 ルビ 2c** | **`viewportHeight`（横書きのとき）** | **？** |

**2 回目なので、場当たりに 1 項目足すのをやめる。**

> **1 回目（縦書き）で `charsPerUnit` を足したのは場当たりだったが、
> それが間違いだったとは言えない。**そのときは 1 件であり、
> 「畳み込み先の無い入力が 1 つある」という個別の話に見えた。
>
> **2 回目で同じ形が出たことで、個別の話ではなく
> 構造の問題だと分かった。**「結果を検証項目にすると、
> 結果の作り方を変えるたびに畳み込み先が消える」という一般の性質である。
>
> **1 件目で構造を疑うのは早すぎ、3 件目では遅い。**

### 5.5-3 いまの項目は「結果」と「入力」が混ざっている

| | 利点 | 欠点 |
|---|---|---|
| **結果だけ**を検証する | 項目が少ない | **結果が同じで入力が違う場合を見逃す。**例: 余白とフォントが同時に変わって `linesPerPage` がたまたま一致すると、**行の折り返し位置は違うのに索引が通る** |
| **入力だけ**を検証する | 見逃しが無い。**何を検証しているか読んで分かる** | 項目が増える |

いまは混在しており、**どちらの性質も保証していない。**

### 5.5-4 ★ 2c での方針 — **入力だけに揃える**

`CACHE_VERSION` 7 → 8 で、**結果の項目をやめて入力に置き換える。**

| 旧 | 新 |
|---|---|
| `viewportWidth`（入力） | `viewportWidth` |
| `linesPerPage`（結果） | **`viewportHeight`** |
| `charsPerUnit`（結果） | **`lineSpacing`**（列幅と行間の素） |
| `fontId` / `screenMargin` / `paragraphAlignment` | そのまま |
| — | **`verticalWriting`** |

**項目数は 7 で変わらない。**結果 2 つが入力 3 つに置き換わり、
`viewportWidth` と `viewportHeight` が**対称**になる。

採る理由:

| | |
|---|---|
| **行高が可変でも成立する** | 入力はページの切り方に依らない。**次に切り方を変えるとき、検証項目を触らなくてよい** |
| **見逃しが無くなる** | 偶然の一致で通る経路が消える |
| **読んで分かる** | 「この索引はこの設定で作られた」と直接書いてある。畳み込みの説明が要らない |
| **ぶら下げにも効く** | §7 のぶら下げは行の属性を増やすが、**入力は 1 つも増えない** |

### 5.5-5 実装して分かったこと (2026-11-07)

**項目数は 7 のままにならなかった。8 になった。**
`fileSize` を数え忘れていた。結果 2 つ（`linesPerPage` / `charsPerUnit`）が
入力 3 つ（`viewportHeight` / `lineSpacing` / `verticalWriting`）に替わるので、
**7 − 2 + 3 = 8** である。方針は変わらないが、
**「項目数は変わらない」は数えずに書いた数字だった**（§8.7-22 の形）。

`charsPerUnit` は項目から外れたが**実行時には残る** ──
縦書きの折り返しが升目を数えるのに使う。
検証項目から外すことと、計算に使わなくなることは別である。

### 5.5-6 ★ 高さで切ると「1 行も組まないまま満杯」が新しく生まれる (2026-11-07)

本数で切る形では、内側の繰り返しが `do { 組む } while (…)` だったので、
**1 行は必ず組んでから数を見ていた。**
高さで切ると、組む前に「入るか」を見るので、
**その行から 1 バイトも組まないまま満杯になれる。**

これが `.md` のチェックボックスを壊した。
`lineBytePos` は記法を飛ばした位置（`prefixLen`）から始まるので、
何も組まずに満杯になった行で `pos` をそこまで進めると、
**`- [ ] ` の 6 バイトを飛び越える。**
次のページはその行を「記法の無い行」として組み、
チェックボックスが消え、`toggleSelectedCheckbox()` が
括弧の中でないバイトを指す。

    if (lineBytePos > prefixLen) pos += toSourceOffset(lineBytePos, rubySpans);

**「何も組まなかったなら位置を動かさない」**で済む。
重要なのは、これを**焼く前に PC の全数検証が捕まえた**ことである。
実機では「チェックボックスがときどき消える」という形で出て、
ルビの作業と無関係に見えたはずである。

代償は `lineSpacing` と `verticalWriting` が**設定の値そのもの**になることで、
上流が `LINE_COMPRESSION` に値を足すと**索引が 1 度作り直される。**
`static_assert` (§19.5) が止めるのはビルドで、
**キャッシュは版の不一致で安全に捨てられる。**これは退化ではない。

> **宿題② との関係**: これは `lineSpacing` への**依存を深めない。**
> 検証項目に値を**記録する**だけで、
> **`lineSpacing` を見て挙動を変える場所は増えない。**
> 却下した案C は挙動が変わる話だった。

#### 字形 — ★ `U+FE45` は搭載フォントに無い

6 サイズすべて（UDEVGothic 8/10/12/14/16/18pt、各 24,803 字）を実際に引いた。

| **`U+FE45` ﹅ ゴマ点（縦書き用の正式な字）** | **6 サイズすべてに無い** | — |
| `U+FE46` ﹆ 白ゴマ点 | **同じく無い** | — |
| `U+30FB` ・ 中点 | ある | 送り **29px（全角）**、ink 7×6px、左 11px |

**→ 手描きを推す。**根拠は上の 3 点と、次の帯の実測である。

#### (c) 帯の確保 — ★ ルビ帯と共用してはいけない

| 本文 | 升目 | 設定 | 通常の送り | **ルビ帯と共用 (17px)** | em/6 の点 | 固定 4px |
|---|---|---|---|---|---|---|
| 14pt | 29 | 狭い | 33 | 47 **(+14)** | 5px → 35 (+2) | 34 (+1) |
| 14pt | 29 | 普通 | 37 | 47 **(+10)** | 5px → **37（吸収）** | **37（吸収）** |
| 14pt | 29 | 広い | 43 | 47 **(+4)** | 5px → **43（吸収）** | **43（吸収）** |
| 18pt | 38 | 普通 | 49 | 56 **(+7)** | 6px → **49（吸収）** | **49（吸収）** |
| 12pt | 25 | 普通 | 32 | 43 **(+11)** | 4px → **32（吸収）** | **32（吸収）** |

**結論: 別に取る。**点は em/6 程度（4〜6px）で足り、

## 7. ぶら下げ — ルビの設計が兼ねる

```
［＃ここから１字下げ、折り返して２字下げ］
```

**「折り返して N 字下げ」がぶら下げの指定そのものである**
(`f8-aozora-notation.md` §5.5-6)。
『戦争史大観』の 29 ブロック中 27 がこの形を使う。

ぶら下げは**変換時には書けない** (§5.5-4)。
折り返した 2 行目を下げるには、
**組む側が「この行は N 字下げ」という情報を持つ必要がある。**
それは `loadPageAtOffset()` の仕事で、
**ルビが触る場所そのものである。**

> **案A で `loadPageAtOffset()` が「行ごとの属性」を扱うようになる。**
> ぶら下げはその属性の 2 つ目として乗る。
> **入力は記法の側に既にある。**推測で既定値を決める必要は無い。

### 7.1 ★ 「横書きでは字下げを無効にできないか」への答え

羅闇さんの質問。**いまの形ではできない。そしてぶら下げができれば不要になる。**

#### なぜいまの形ではできないか

段階1.5 は**全角スペースを `content.u8` に焼き込む。**
読書位置も索引も `content.u8` への**バイト位置**である。

```
横書き用のバイト列と縦書き用のバイト列を別に持つ
  → 同じ数字が別の場所を指す
  → 完了条件⑦ が壊れる
```

> **完了条件⑦**（F-5、2026-10-31 実機合格）:
> **横書きで進めた位置から縦書きに切り替えても同じところから始まる。**
> 仕様書 §2.4 の「バイトオフセットは組み方に依らず意味を保つ」が
> 実装でも成立していることの確認だった。

**字下げを「文字」として焼き込んでいる限り、
その性質はモードを分けた瞬間に失われる。**
しかも失い方が悪い ── 位置が**少しずれる**のであって、
エラーにはならない。

#### 字下げを「行の属性」にすると 3 つが同時に解ける

| | |
|---|---|
| モードごとの切り替え | **可能になる。**バイト列は 1 つで、組むときに量を決める |
| ぶら下げ | **可能になる。**折り返しの 2 行目以降にも量を渡せる |
| バイト位置 | **ずれなくなる。**字下げを入れても `content.u8` は変わらない |

#### ★ そして、ぶら下げができればモード別の切り替えは要らない

**いま横書きで不格好なのは、折り返した行が行頭に戻るからである。**

見出しが 2 行に割れること自体は**1 行の字数の問題**で避けられない
（12 pt で 18 字、18 pt で 12 字）。
しかし**折り返しが字下げに揃っていれば「2 行になっただけ」に見える。**
揃っていないから、2 行目が見出しに見えなくなる。

**→ モード別の切り替えは実装しない。ぶら下げで解決する。**

設定を 1 つ増やさずに済み、完了条件⑦ も守られる。

### 7.2 字下げは 2c に相乗りできるか — **できない。独立した段階にする**

2c はルビのために**行ごとの属性**を持つ仕組みを作る。
字下げとぶら下げの量はそこに乗る**形**をしている。
しかし**同じ段階に入れるべきではない。**

| | 2c（ルビ） | 字下げ |
|---|---|---|
| 属性が効く軸 | **縦**（行高・ページの切れ目） | **横**（行の開始位置・折り返し幅） |
| 必要な版上げ | `CACHE_VERSION` 7→8 | **`ENCODING_VERSION` 4→5 も要る** |
| なぜ | ページの切り方が変わる | **段階1.5 が焼き込んだ全角スペースをやめる**ため、`content.u8` が変わる |

**版が 2 つ同時に上がるのが決定的である。**
索引と変換結果が同時に作り直されるので、
**何かおかしくなったときにどちらのせいか言えない。**
これは「1 回の焼きで 1 つだけ確かめる」に正面から反する。

加えて 2c の確認項目が増えすぎる:

| | 2c 単独 | 字下げ込み |
|---|---|---|
| 確認すること | ページ送りと索引が壊れていないこと | 左に加えて、字下げが出ること・ぶら下げが揃うこと・**段階1.5 と見た目が一致すること** |

**→ 字下げは独立した段階 2g とし、2e の後に置く。**

| # | 内容 | 焼いて確かめること | 版 | 目安 |
|---|---|---|---|---|
| **2g** | 字下げを行の属性にする。段階1.5 の焼き込みをやめ、ぶら下げを実装 | **段階1.5 と同じ見た目に戻り、折り返しが字下げに揃うこと** | `ENCODING_VERSION` 4→5 | **100〜140 行** |

2b と同じ形をしている ──
**「前の段階と同じ画面に戻る」ことを合格条件にする。**
戻れば、属性に移しても何も失っていないと言い切れる。

#### 2c の設計で用意しておくこと（費用ゼロ）

**行の属性を `bool` ではなく小さな構造体にする。**

```cpp
// 2c で導入する。ルビは hasRuby だけを使う
struct LineAttr {
  bool hasRuby;      // 2c: 行高に effect
  // 2g で足す: uint8_t indent; uint8_t hangingIndent;
};
```

`bool` 1 つで始めると 2g で全ての受け渡しを書き直すことになる。
**構造体にしておけば 2g はフィールドを足すだけ**で、
2c の実装行数は変わらない。
